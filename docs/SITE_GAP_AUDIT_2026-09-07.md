## 남아 있는 부족 사항과 권장 순서

### P1 — 경제 관측과 자동 경보

현재 원장은 복식부기와 시스템 소각 계정을 갖추고 있지만, 운영자가 한 화면에서 아래 지표를 비교하고 임계치 경보를 받는 기능은 부족하다.

- 최근 1일·7일·30일 작업 발행량
- 상점·카지노·사업 운영비 등 소비처별 소각량
- 활성 사용자당 중앙값 잔액과 상·하위 분위수
- 발행/소각 비율, 통화 유통 속도, 상품별 구매 전환율

보상을 다시 제한하기 전에 실제 발행/소각 비율을 관찰해야 한다. 7일 이동 발행량이 소각량을 지속적으로 크게 웃돌 때는 작업 보상을 일괄 삭감하지 않고, 인기 소비 상품 추가·가격대 확장·기간 한정 장식 상품 순으로 대응하는 것을 권장한다.

### P1 — 실제 모바일 관리자 E2E

모바일 메뉴의 관리자 표시 여부와 권한 분기에는 컴포넌트 테스트가 있지만, 실제 OAuth 세션 쿠키를 가진 Android Chrome 및 iOS Safari에서 로그인→메뉴→관리자 진입→로그아웃을 자동 수행하는 브라우저 테스트는 없다. 일반 사용자에게 관리자 메뉴가 숨겨지는 반대 조건도 같은 E2E에 포함해야 한다.

### P1 — 활동 로그 전달 상태 가시성

브라우저는 이벤트 ID, 로컬 재시도 큐, 서버 중복 제거를 사용하지만 다음 정보가 회원·관리자 화면에 없다.

- 클라이언트 큐에 남은 이벤트 수
- 마지막 성공 전송 시각
- Discord 전달 지연 및 실패 이유
- 200건 로컬 큐 상한에 도달했을 때의 명시적 운영 경보

모바일 종료 시 `unload`가 발생하지 않을 수 있으므로 `visibilitychange`를 우선하고 `pagehide`는 보조 수단으로 유지한다. 이는 [MDN Beacon 안내](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/sendBeacon)의 권고와 일치한다.

### P2 — 소비 상품의 사용 경험

상점 구매와 원장 소각은 구현되어 있지만, 편의·연출 상품마다 구매 이후 어디서 사용되는지, 사용 완료 여부가 무엇인지 명확한 안내와 기능별 소비 확인 테스트가 더 필요하다. 상품을 추가하는 것만으로는 반복 소비가 발생하지 않으므로 프로필·지갑·작업 완료 화면에서 바로 사용할 수 있는 진입점을 연결해야 한다.

가상 구매는 통화와 구매 항목을 명시적으로 연결하고 서버에서 결과를 확정하는 형태가 적절하다. 참고: [Unity Virtual Purchase](https://docs.unity.com/en-us/economy/add-virtual-purchase), [PlayFab Economy](https://learn.microsoft.com/en-us/xbox/playfab/economy-monetization/economy-v2/quickstart).

### P2 — 네트워크 복구 검증

요청 재시도는 같은 이벤트/거래 ID를 재사용해야 중복 지급을 피할 수 있다. 현재 활동 로그와 주요 경제 거래는 이 원칙을 사용하지만, 네트워크 단절·응답 유실·재접속을 묶은 브라우저 E2E와 장애 주입 테스트가 부족하다. [Stripe 멱등성 요청](https://docs.stripe.com/api/idempotent_requests)처럼 동일 키 재시도 결과가 최초 처리와 같음을 경제 기능별로 검증해야 한다.

### P2 — CI 및 이미지 성능 경고

- GitHub Actions의 일부 공식 액션이 Node.js 20 기반이라 강제 Node.js 24 전환 경고가 발생한다. 해당 액션의 다음 주 버전으로 갱신해야 한다.
- 8개 화면에서 원시 `<img>` 사용 경고가 남아 있다. 사용자 업로드처럼 크기를 알 수 없는 경우의 정책을 정한 뒤 `next/image` 또는 명시적 크기·로더로 전환해야 한다.
- PostCSS 기본 내보내기 경고 1건이 남아 있다.

### P3 — 오래된 제한 필드 제거

`daily_limit`, `daily_cap`, `weekly_cap`, `repeat_decay_percent`는 감사·API 호환을 위해 당장은 남지만 더 이상 직업 보상 계산에 적용되지 않는다. 외부 소비자가 없음을 확인한 후 새 API 버전에서 필드를 제거하고, DB 열은 별도 마이그레이션으로 정리해야 한다. 기존 적용 마이그레이션은 수정하지 않는다.

## GitHub 통합 점검 결과

- 점검 시점의 로컬 `main`과 `origin/main` 차이는 0건이다.
- `origin/main`에 병합되지 않은 원격 브랜치 커밋은 0건이다.
- 최근 다른 작업자의 AI 뉴스, Discord 로그, 사진 승인, 관리자 모바일 접근 변경은 모두 `main` 역사에 포함되어 있다.
- 이후 작업도 항상 `git fetch --prune` → `origin/main` 차이 확인 → 새 브랜치 → 테스트 배포 → PR 병합 순서를 따른다.

## 완료 판정 기준

1. DB 마이그레이션 연속성·권한·멱등성 테스트 통과
2. 기존 배정 경로와 즉시 완료 경로 모두 제한 횟수 이후 전액 지급
3. 관리자와 회원 화면에 일일 제한 문구가 남지 않음
4. 신규 소비 상품이 상점 카탈로그와 무제한 재고에 노출됨
5. 프런트 테스트, 백엔드 DB 테스트, 타입 검사, 빌드, 의존성 감사 통과
6. 테스트 서버 적용 및 운영 DB와 분리 확인 후에만 `main` 병합과 운영 배포
