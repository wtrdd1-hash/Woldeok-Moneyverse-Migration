## 1. 목적

이 문서는 Woldeok Moneyverse 모바일 앱의 **화면 구조, 네비게이션, 화면별 상태, API 연결, 권한, 오류처리, 모바일 UX 규칙, 구현 순서**를 정의한다.

앱은 웹사이트 화면을 그대로 복제하는 것이 아니라, 기존 일반 사용자 기능을 모바일에 맞는 정보 구조로 재구성한다. 다만 인증·경제·개인정보·권한 판단은 기존 서버 보안 모델을 그대로 유지한다.

기본 구조:

`모바일 앱 -> HTTPS -> /app-api/v1/* BFF -> NestJS /api/v1/* -> PostgreSQL`

앱 내부에는 `INTERNAL_API_TOKEN`, DB 비밀번호, 서버 secret, 관리자 내부 API 자격정보를 넣지 않는다.

## 2. 앱 전체 네비게이션 구조

### 2.1 하단 기본 탭

앱의 기본 하단 탭은 5개로 구성한다.

1. **홈** — 대시보드, 자산 요약, 일일 상태, 빠른 실행
2. **경제** — 지갑, 은행, 주식, 사업, 상점
3. **플레이** — 근무, 성장, 보상, 시즌, 조건부 카지노
4. **커뮤니티** — 게시판, 프로필, 미디어, 활동
5. **MY** — 계정, 개인정보, 보안, 설정

세부 기능은 하단 탭을 추가하지 않고 각 탭 내부의 화면 스택으로 이동한다.

### 2.2 전역 공통 화면

모든 탭 위에서 사용할 수 있는 전역 UI를 둔다.

- 알림센터
- 지원되는 경우 통합 검색
- 서비스 장애/점검 배너
- 세션 만료 안내 시트
- 재인증 모달
- 공통 확인 다이얼로그
- 네트워크 끊김 배너

### 2.3 탭 상태 유지

각 하단 탭은 자체 네비게이션 스택을 유지한다. 다른 탭으로 갔다가 돌아와도 읽던 목록 위치나 상세 화면을 가능한 유지한다.

단, 다음 정보는 임시저장 금지다.

- 비밀번호
- 세션 토큰
- 인증 토큰
- CSRF 토큰
- 이메일 인증 원문 토큰
- 보안용 secret

일반 게시글 초안, 검색 조건처럼 민감하지 않은 입력만 로컬 임시저장을 허용한다.

## 3. 모든 데이터 화면의 공통 상태

모든 API 기반 화면은 최소한 아래 상태를 구현해야 한다.

- `initial_loading` — 최초 로딩
- `refreshing` — 새로고침
- `content` — 정상 데이터
- `empty` — 데이터 없음
- `recoverable_error` — 재시도 가능한 오류
- `permission_denied` — 권한 없음
- `reauth_required` — 재인증 필요
- `session_expired` — 세션 만료
- `offline` — 네트워크 끊김

API 응답을 기다리는 동안 빈 흰 화면만 보여주지 않는다.

### 3.1 로딩 규칙

- 목록/카드: skeleton 사용
- 로그인/구매 확정처럼 원자적 작업: blocking spinner 허용
- Pull-to-refresh는 현재 화면 데이터만 갱신
- 한 카드 API가 실패했다고 홈 전체를 오류화하지 않음

### 3.2 오류 표시 규칙

| 오류 종류 | 화면 처리 |
| --- | --- |
| 입력 오류 | 해당 필드 아래 오류 표시 |
| 세션 만료 | 로그인 복귀 안내 후 인증 화면 이동 |
| 권한 없음 | 접근 불가 사유 표시 |
| 재인증 필요 | 재인증 모달 실행 |
| 충돌/중복 처리 | 서버 최신 상태 다시 조회 |
| Rate Limit | 재시도 가능 안내 |
| 네트워크 오류 | 재시도 버튼 |
| 서버 오류 | 일반 오류 메시지 + 재시도 |

사용자에게 SQL, stack trace, 내부 exception, secret header, 서버 내부 경로를 노출하지 않는다.

# 4. 인증 및 신규 사용자 화면

## AUTH-001 — 시작 화면

### 목적

앱 최초 실행 및 로그아웃 상태의 진입점.

### 화면 구성

- 서비스 로고/이름
- `회원가입`
- `로그인`
- `Google로 계속하기`
- `Discord로 계속하기`
- 이용약관
- 개인정보처리방침
- 서비스 상태 표시

### 연결 API

- `POST /app-api/v1/auth/prelogin-session`
- `GET /app-api/v1/auth/policy`
- `GET /app-api/v1/auth/providers`

### 구현 규칙

OAuth 버튼 노출 여부를 앱에 하드코딩하지 않고 서버가 내려주는 provider 상태를 기준으로 한다.

---

## AUTH-002 — 약관/개인정보 동의

### 화면 구성

- 필수 이용약관
- 필수 개인정보 동의
- 선택 동의 항목
- 각 문서 버전
- `동의하고 계속`

### API

- `GET /app-api/v1/auth/policy`
- `PUT /app-api/v1/auth/consent`

### UX 규칙

- 선택 동의는 기본 체크하지 않는다.
- 서버가 성공 응답한 동의 상태만 최종 확정한다.
- 약관 버전이 바뀌면 기존 사용자에게 재동의를 요구할 수 있어야 한다.

---

## AUTH-003 — 자체 이메일 회원가입

### 입력항목

- 이메일
- 비밀번호
- 비밀번호 확인
- 현재 API 계약에서 필요할 경우 표시명

### UX

- 비밀번호 길이 안내
- 붙여넣기 허용
- 비밀번호 관리자/autofill 허용
- 무의미한 대문자+숫자+특수문자 강제 조합 규칙 금지
- 이메일 가입 여부를 직접 노출하는 오류 메시지 금지

### API

- `POST /app-api/v1/auth/local/register`

### 성공 시

`AUTH-004 이메일 인증 대기` 화면으로 이동.

---

## AUTH-004 — 이메일 인증 대기

### 화면 구성

- 마스킹된 이메일 주소
- 인증메일 확인 안내
- `인증 완료 확인`
- 서버 지원 시 `인증메일 다시 보내기`
- 다른 계정으로 다시 시작

### API

- `POST /app-api/v1/auth/local/verify-email`

### 중요 규칙

운영 앱은 회원가입 API에서 이메일 인증 원문 token이 내려올 것이라고 가정하지 않는다. 실제 운영은 이메일 발송 경로를 통해 token을 전달한다.

---

## AUTH-005 — 자체 이메일 로그인

### 입력

- 이메일
- 비밀번호

### 버튼

- 로그인
- 비밀번호 찾기 — 백엔드 복구 기능 완료 후만 노출
- Google 로그인
- Discord 로그인

### API

- `POST /app-api/v1/auth/prelogin-session`
- `POST /app-api/v1/auth/local/login`

### UX

존재하지 않는 계정과 잘못된 비밀번호는 사용자에게 같은 계열의 일반 오류로 표시한다.

요청 처리 중 로그인 버튼 연타를 막는다.

---

## AUTH-006 — Google / Discord 로그인

### API

- `GET /app-api/v1/auth/google/authorize`
- `GET /app-api/v1/auth/discord/authorize`

### 앱 흐름

1. 앱이 authorize API 호출
2. 서버가 인증 URL 제공
3. 시스템 브라우저 또는 안전한 인증 세션 열기
4. OAuth 인증
5. 승인된 callback/deep link로 앱 복귀
6. 서버 session 상태 재조회
7. 인증 성공 시 홈 진입

PKCE/state 등 보안 값은 현재 서버 인증 설계를 따른다.

---

## AUTH-007 — 재인증 모달

다음 작업에서 공통으로 사용한다.

- 로그인 수단 연결 해제
- 계정 보안 설정 변경
- 개인정보 내보내기
- 계정 삭제
- 기타 서버가 고위험 작업으로 표시하는 기능

기능마다 새 재인증 화면을 만드는 대신 재사용 가능한 공통 모달/시트로 구현한다.

# 5. 홈 화면

## HOME-001 — 회원 대시보드

### 목적

사용자가 앱을 켜자마자 자신의 경제·진행 상황을 한 화면에서 확인한다.

### 권장 구성

1. 인사말 + 프로필
2. 사용 가능 지갑 잔액
3. 은행 예금/대출 요약
4. 오늘 보상 수령 상태
5. 현재 직업/근무 가능 상태
6. 레벨/경험치
7. 사업 현황
8. 주식 포트폴리오 요약
9. 시즌/이벤트
10. 최신 공지
11. 빠른 실행

### 빠른 실행

- 근무하기
- 입금/출금
- 송금
- 보상받기
- 주식 매수/매도
- 사업 정산

### 연동 API

- `/app-api/v1/profile/*`
- `/app-api/v1/wallet/*`
- `/app-api/v1/banking/*`
- `/app-api/v1/rewards/*`
- `/app-api/v1/work/*`
- `/app-api/v1/progression/*`
- `/app-api/v1/businesses/*`
- `/app-api/v1/stocks/*`
- `/app-api/v1/content/announcements`

### 초기 구현 방식

홈 전용 aggregation API가 없으면 각 카드 API를 병렬 호출한다.

예:

- 지갑 API 실패 -> 지갑 카드만 오류
- 사업 API 실패 -> 사업 카드만 오류
- 공지는 정상 표시

한 API 실패로 홈 전체가 열리지 않는 구조는 피한다.

# 15. 앱 API 클라이언트 규칙

## 15.1 기본 경로

일반 사용자 앱 기능은 모두 아래 BFF 경로를 사용한다.

`/app-api/v1/*`

앱에서 직접 호출하지 않는 경로:

- `/api/v1/admin/*`
- Discord webhook/interactions
- health endpoint
- scheduler/worker 내부 API
- DB 직접 API

---

## 15.2 Session/CSRF

- 서버 session 체계를 그대로 사용
- 변경 요청은 CSRF 규칙 적용
- 앱이 자체적으로 로그인 상태를 만들어내지 않음
- 서버가 session을 무효화하면 사용자 cache를 정리하고 로그아웃 상태로 이동

---

## 15.3 Retry 규칙

- GET: 일시적 네트워크 오류에 제한적 retry 가능
- 송금/구매/매도/정산 등 경제 mutation: 무조건 자동 재시도 금지
- 멱등성이 서버 계약으로 보장되는 요청만 안전한 retry 고려
- 중복 탭 방지를 위해 요청 처리 중 버튼 잠금

---

## 15.4 캐시

장기 캐시 가능:

- 공지
- 상품 이미지
- 비교적 고정적인 카탈로그

짧은 캐시 또는 mutation 후 즉시 재조회:

- 지갑 잔액
- 은행 잔액
- 주문
- 사업 정산
- 로그인/보안 상태
- 권한
- 대출 상태

# 23. 현재 알려진 구현 주의사항

앱 API 범위는 구축되어 있지만, UI를 만들 때 아직 서버/운영 측에서 완성되지 않았을 수 있는 부분을 구분해야 한다.

### 23.1 이메일 인증

자체 이메일 가입 API는 있지만 실제 운영에서 완전한 가입경험을 제공하려면 outbound email sender와 SPF/DKIM/DMARC 설정이 필요하다.

### 23.2 보안센터

활성 session 관리/보안 이벤트 API가 완성된 범위까지만 화면에 노출한다.

### 23.3 비밀번호 찾기

비밀번호 reset token 발급, 이메일 전송, reset 완료까지 전체 lifecycle이 구현되기 전에는 동작하는 메뉴처럼 노출하지 않는다.

### 23.4 Push 알림

Push를 구현하려면 별도의 device token 등록/해제, notification preference, delivery backend 설계가 필요하다.

### 23.5 홈 API

초기에는 여러 API를 조합할 수 있지만 앱 호출량 최적화를 위해 나중에 전용 dashboard aggregation endpoint 추가를 검토한다.

# 24. 핵심 화면 흐름 예시

## 신규회원

`앱 실행 -> 시작 -> 약관 -> 이메일 가입 -> 이메일 인증 -> 세션 확정 -> 홈 -> 초반 미션`

또는

`앱 실행 -> 시작 -> Google/Discord -> OAuth -> 세션 확정 -> 홈`

## 송금

`홈/경제 -> 지갑 -> 송금 -> 수취인/금액 -> 검토 -> 최종확인 -> 서버 처리 -> 영수증 -> 지갑 최신화`

## 주식 구매

`경제 -> 주식 -> 종목 -> 매수 -> 수량 -> 주문검토 -> 서버처리 -> 체결결과 -> 포트폴리오 갱신`

## 사업 구매

`경제 -> 사업 -> 카탈로그 -> 사업상세 -> 조건확인 -> 구매확인 -> 서버처리 -> 내 사업`

## 계정 삭제

`MY -> 개인정보 -> 계정삭제 -> 경고 -> 재인증 -> 최종확인 -> 서버 요청 -> 상태 화면`

---

# 25. 화면 번호 체계

개발/QA/이슈 제목에서 동일한 화면 ID를 사용한다.

- `AUTH-*` 인증
- `HOME-*` 홈
- `ECO-*` 경제 허브
- `WAL-*` 지갑
- `BNK-*` 은행
- `STK-*` 주식
- `BUS-*` 사업
- `SHP-*` 상점
- `PLY-*` 플레이
- `WRK-*` 근무
- `PRG-*` 성장
- `ERY-*` 초반 진행
- `RWD-*` 보상
- `SEA-*` 시즌
- `CAS-*` 카지노
- `COM-*` 커뮤니티
- `BRD-*` 게시판
- `PRF-*` 프로필
- `CNT-*` 콘텐츠
- `MY-*` 마이페이지
- `ACC-*` 계정
- `SEC-*` 보안
- `PRV-*` 개인정보
- `SET-*` 설정

예:

- GitHub Issue: `[APP][WAL-002] 송금 확인 화면 구축`
- QA: `[APP-QA][AUTH-005] 잘못된 비밀번호 처리`
- 버그: `[APP-BUG][STK-003] 주문 중복 제출`

이 규칙을 사용하면 문서, 개발, QA, 이슈를 같은 화면번호로 추적할 수 있다.
