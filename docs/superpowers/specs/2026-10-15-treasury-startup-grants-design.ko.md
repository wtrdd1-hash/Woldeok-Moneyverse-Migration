# 창업 지원금 신청·심사·원자적 지급 설계 검토 — v2026.10.15.675

**상태:** 기획 검토 / 실제 지급 차단. [English canonical](2026-10-15-treasury-startup-grants-design.md). 구현 및 운영 배포 완료가 아님.

## 목적·권위
시민의 창업 지원금 접수 → 관리자 심사 → 검증 가능한 국고 출금·수령인 입금 → 영수증·감사를 구현한다. 현재 화면의 안내는 **최대 100,000 WLD / 분기 1회 심사**이나, 이는 정책 확정을 거쳐야 한다. 상위 기준은 PROJECT_PLAN, INTEGRATED_PLANNING_MASTER, v523 Economy Core/중앙국고 명세와 문서정책이다. 기존 v629는 허위 성공을 방지하기 위해 기능을 안전 차단했다.

**2026-10-15 읽기 전용 실측**
- 기준 main `f2bf939e53482721ee8bbf1074bd7ebf1922b13e`.
- Next 신규 신청·관리자 심사는 HTTP 503. 관리자 버튼도 강제 비활성화. 기존 JSON 3건은 **실신청/실지급 확인이 되지 않은 과거 기록**.
- 별도 범용 Nest API와 DB `treasury_disburse_grant`가 존재하나 해당 신청서와 연결되지 않았고, 지급 SQL이 계정 잔액을 직접 변경하여 Economy Core의 검증된 복식분개를 통하지 않는다.

- 운영 반영 migration은 종전 점검에서 268까지로 보고됐고, 최신 main에는 269~271이 있다. 체크섬·Test 복원·DB 권한을 재검증하기 전 신규 migration을 운영에 적용하지 않는다.

## 검토한 대안과 선택
1. 기존 관리자 승인 버튼과 범용 지급 API를 단순 연결: **폐기**. 인증·중복·원장 보존 불충분.
2. JSON 신청 저장을 유지하고 잠금만 보완: **폐기**. 신청자 UUID·이력·원자성 결여.
3. **선택: DB 권위 신청/심사와 실제 지급을 분리하는 단계적 구현.** 신청·승인은 원장 영수증 없이 지급 완료라고 하지 않으며, 정합성 증거가 확보되기 전 실제 이체를 막는다.

## 신규 신청·관리자 심사 계약
- `treasury_grant_applications`: DB 서버에 검증된 신청자 UUID, 회사명, 기획서, 신청 WLD 정수 문자열/정확수, 분기, 제출 멱등키, 현재 상태, 결정자 UUID, 승인/반려 사유, 시각, 정산 멱등키, 원장 거래 ID를 보관한다.
- 상태: `PENDING_REVIEW → REJECTED` 또는 `APPROVED_AWAITING_SETTLEMENT → PAID`. **승인과 지급 완료는 서로 다른 상태**.
- 본인확인·약관동의된 활성 사용자의 세션 UUID로 신청자를 확정. 요청 본문의 신청자 ID는 사용하지 않는다. 제안 한도 100,000 WLD / 분기 동일인 1건을 확정 전에 검증한다.
- 관리자 권한·최근 재인증 세션·CSRF·의견 최소길이를 검사하고 셀프승인 및 동시에 두 번 심사하는 행위를 방지한다. 심사 요청에서 지급 계정이나 금액을 새로 받지 않는다.
- 관리자 큐와 본인 조회는 액터 검증 `SECURITY DEFINER` 조회 함수로 구성. 과거 JSON 3건은 검증 완료 자료로 승격하지 않고 별도 과거 기록으로 표시한다.
- 기존 Next→Nest 서버전용 API 경계를 지킨다. 영어 정본·한국어 보조 언어 처리 및 320px 모바일 목록 접근성을 검증한다.

## 돈 이동 전제조건
- 신청/심사/지급의 별도 기능 스위치를 기본 OFF로 둔다. 정산 검증 전에는 지급 API가 항상 실패하도록 한다.
- 국고 `VAULT_MAIN`의 표시 금액을 `account_balances`로 단순 복사하지 않는다. 발행·세입·재정 금고·부채·원장 기록의 출처별 일치 여부를 먼저 추적해 **0 잔액 대 184,460,884 차이**를 해결할 근거를 확보한다.
- 검증 완료 시에도 DB 트랜잭션 하나에서 신청 행, 금고·계정의 행잠금, 관리자 재권한, 중복 심사/멱등 검증, 30% 비축·최소 100,000 WLD·확정 부채, 수령인 활성 지갑을 확인한다. Economy Core 복식분개로 국고 차감과 지갑 입금, 상태, 국고 보조원장, 감사·아웃박스 및 거래 영수증을 함께 커밋한다.
- 금액 우회, 직접 잔액 UPDATE, 허위 발행, 중복 키로 중복 지급, 비인가 관리자는 금지. DB 직접 DML 권한 확대도 금지. 함수 `PUBLIC EXECUTE` 명시 회수.

## 5단계 작업 및 승인 기준
1. **G0 원장/실행상태 진단:** 정확한 Test/운영 SHA·기존 migration checksum·실제 권한 확인, 복원 DB에서 원장 차이의 발생 원인 및 안전한 보정 방법 조사. 운영 DB 수정 금지.
2. **G1 신청:** 기존 JSON 경로 대체, 신뢰 가능한 액터 기반 DB 기록, 신청자 조회, 정밀 금액·중복 제출 검사.
3. **G2 심사:** 별도 운영 콘솔 인증, 승인대기/반려 상태, 감사 의견, 재시도·동시 심사 방어. 이 단계에서 원장 지급 없음.
4. **G3 지급:** G0 통과 후 독립 DB 정산 함수 + 원자 복식분개 + 보호 비축액 검증 + 불변 영수증, 실패/중복/경합/장애 테스트.
5. **G4 운영:** 전용 브랜치→실제 CI·DB/보안 테스트→같은 SHA Test 프론트·백엔드 정상 작동 및 세션·모바일 검증→최신 main 재동기화/PR→복구 가능한 무중단 운영 승격과 지급 영수증 재검증. 하나라도 실패하면 운영 승격 BLOCKED 유지.

## 확정해야 할 정책
- 최대 100,000 WLD, 분기 1회, 반려 후 재신청 허용 여부.
- 심사 승인 뒤 자동 지급인지, 별도 재정 집행 승인인지(현재는 분리 권고).
- 85% 현금유동성 문구와 30% 안전비축 준칙의 적용 분모·우선순위, 확정 부채 정의.
