> **프로젝트명:** 월덕 머니버스 (Woldeok Moneyverse)

> **목표:** Discord 커뮤니티와 웹에서 같은 가상경제를 안전하게 이용하는 경제·게임 플랫폼
> 

# 1. 제품 정의

월덕 머니버스는 Discord 계정 또는 Google 계정으로 로그인해 가상 자산, 상점, 사업, 시장 활동을 즐기는 커뮤니티형 경제 플랫폼이다. Discord 봇은 Discord 안에서 핵심 활동과 알림을 제공하고, 웹은 자산·거래내역·시장·관리 기능을 제공한다.

모든 화폐·보상은 **게임 내 가상 데이터**이며 현금, 환전, 투자 수익 또는 실제 자산을 제공하지 않는다.

# 2. 해결할 문제와 설계 결정

| 기존 문제 | 새 설계 결정 |
| --- | --- |
| 직접 잔고 수정과 원장이 혼재 | 모든 가치 변동은 단일 Economy Core만 통과 |
| 국고·사용자 지급이 분리됨 | 사용자 계정과 국고를 한 DB 트랜잭션으로 처리 |
| 여러 건강 모니터의 기준 충돌 | 지표 엔진 하나와 버전 관리만 사용 |
| 재시작 시 정책값이 달라짐 | 정책·버전·발효시각을 DB에 저장 |
| 테스트·운영 데이터가 섞임 | 테스트/운영 DB, 비밀값, 도메인, 봇을 완전히 분리 |
| 광범위한 관리자 기능 | 단일 최고관리자 통제·강제 재인증·불변 상세 감사 로그 |

# 3. 서비스 범위

## MVP — 반드시 제공

- Discord OAuth와 Google OAuth 로그인
- 동일 사용자의 Discord/Google 계정 연결 및 계정 탈퇴
- 이용약관·개인정보처리방침 전체 확인 후 동의 기록
- 지갑, 거래내역, 일일 보상, 작업 보상, 유저 간 송금
- 상점과 소비처
- Discord 봇: 자산 조회, 일일 보상, 송금, 알림
- 마인크래프트 운영 봇: 상태, 시작, 중지, 재시작, 로그 조회
- 사진/공지 페이지, 서비스 상태 페이지
- 관리자: 사용자 조회, 제한, 공지, 경제 대사, 감사 로그

## 2단계 — 경제 확장

- 사업 소유·매출·운영비
- 주식 시장과 보유분
- 은행 예금·대출
- 시즌 랭킹과 소비 이벤트

## 3단계 — 검증 후에만 활성화

- 카지노·확률형 게임
    - [ ]  카지노의 경우 확률을 정확히 공개하는것을 원칙으로 한다. (근거:게임물 관련 법에 명시됨)
- 주식 분할·병합
    - [ ]  관리자가 직접적인 관여를 하지 않는다. (근거: 애덤 스미스의 보이지 않는 손)
- 자동 물가·금리 정책
    - [ ]  관리자가 직접적인 관여를 하지 않는다. (근거: 애덤 스미스의 보이지 않는 손)

3단계 기능은 테스트 서버에서 수익률, 동시성, 악용 방지, 원장 대사가 통과하기 전까지 운영에서 비활성화한다.

# 4. 사용자 흐름

1. 사용자는 홈페이지에서 서비스, 정책, 체험판을 본다.
2. 정책 전문을 끝까지 확인하고 필수 동의·14세 이상 확인을 완료한다.
    1. 14세 미만의 경우 관리자가 무통보 계정 삭제/IP 차단 등의 조치를 취할 수 있다.
3. Discord 또는 Google로 로그인한다.
4. 최초 로그인 시 내부 계정을 만든다. 두 로그인 제공자는 사용자가 로그인한 상태에서만 연결한다.
5. 웹과 Discord 봇은 동일한 내부 사용자 ID와 지갑을 사용한다.
6. 모든 잔고 변동 후 거래 영수증 ID와 최신 잔액을 보여준다.

# 5. 인증 및 개인정보 원칙

- Discord/Google OAuth는 PKCE, state, nonce를 사용한다.
- OAuth 접근 토큰·Google 프로필·이메일은 장기 보관하지 않는다.
- 저장 최소 항목: 내부 사용자 ID, 제공자 고유 ID, 표시명, 동의 버전·시각, 보안 감사 이벤트.
- 홈페이지의 일반 익명 방문은 앱 수준 IP 저장 없이 제공한다.
- 로그인·권한상승·보안 공격 징후만 최소 기간으로 기록한다.
- 세션 쿠키: HttpOnly, Secure, SameSite=Lax 또는 Strict, 서버 측 회전·폐기.
- `.env`와 OAuth/Discord 비밀값은 GitHub에 절대 올리지 않는다. 기존에 노출 가능성이 있는 OAuth Client Secret은 배포 전 재발급한다.

# 6. 경제 코어 설계

## 불변 규칙

- 잔액을 직접 UPDATE하는 경로를 금지한다.
- `EconomyCore.postTransaction()`만 잔액을 바꾼다.
- 하나의 경제 이벤트는 **원장 행 + 계정 잔액 + 경제 로그 + 국고 변동**을 하나의 DB 트랜잭션으로 커밋한다.
- 금액은 부동소수점이 아닌 정수 최소단위로 저장한다.
- 모든 요청에는 멱등성 키를 둬 재시도·중복 클릭·웹훅 중복을 막는다.
- 잔액은 음수가 될 수 없으며, 실패 시 전체 롤백한다.

## 계정 체계

- USER_CASH: 사용자 현금
- USER_BANK: 사용자 예금
- TREASURY: 국고
- MINT: 신규 발행 전용 계정
- SINK: 소각 전용 계정
- ESCROW: 거래·주문 보관 계정

## 주요 거래 유형

- MINT_TO_USER
- USER_TO_USER
- USER_TO_TREASURY
- TREASURY_TO_USER
- USER_TO_SINK
- BANK_DEPOSIT / BANK_WITHDRAW
- MARKET_ESCROW / MARKET_SETTLEMENT
- ADMIN_ADJUSTMENT

관리자 조정은 최고관리자 1인이 실행할 수 있다. 단, 직접 잔액 수정이나 원장 삭제는 허용하지 않고 반드시 ADMIN_ADJUSTMENT 보정 거래를 생성한다. 사유, 관리자 ID, 대상, 전후 값, 원거래 ID, 새 거래 ID, 재인증 시각을 강제 기록한다.

# 7. 경제 건강성과 대사

단일 `Economy Health Engine`이 다음을 매일 산출한다.

- M2 = 사용자 현금 + 예금 + 시장 예치금
- 순발행 = MINT 유입 − SINK 유출
- 국고 순변동과 실제 국고 잔액
- 상위 보유자 집중도
- 보상/소비/세금의 24시간 흐름
- 원장 합계와 계정 잔액의 일치 여부

대사 실패 시 자동 보상·국고 지급·시장 정산을 안전 모드로 제한하고 관리자에게 경보한다. 건강 지표는 `engine`, `metric_version`, `calculated_at`을 함께 저장한다.

# 8. 데이터·인프라

- 운영 데이터: 별도 SSD `/data/wtrdd/moneyverse/`
- MVP DB: SQLite WAL 모드, 단일 쓰기 큐, 암호화된 일일 백업
- 성장 시: 검증된 마이그레이션을 통해 PostgreSQL로 전환한다. MySQL은 새 시스템에서 사용하지 않는다.
- 사진: `/data/wtrdd/moneyverse/photos/`에 저장, DB에는 메타데이터만 저장
- 백업: DB 스냅샷 + 사진 메타데이터 + 복구 절차를 별도 SSD에 보존
- 테스트/운영은 컨테이너, 데이터 경로, OAuth 클라이언트, Discord 봇 토큰을 분리한다.

# 9. Discord 봇 권한

| 역할 | 가능 작업 |
| --- | --- |
| 사용자 | 잔액, 일일 보상, 송금, 내 거래내역 |
| 운영자 | 공지 발송, 제한 요청 |
| 최고관리자 | 사용자·경제·상점·사업·주식·은행·대출·작업·직업·카지노·시즌·공지·Discord·Minecraft·시스템 정책의 전체 조회·설정·중지·복구·보정 |
| 서버 운영자 | 마인크래프트 상태/시작/중지/재시작/로그 |

임의 서버 콘솔 명령 전달 기능은 제공하지 않는다. 봇 명령은 역할 검증, 길드 검증, 요청 제한, 감사 로그를 거친다.

# 10. 보안 기준

## 단일 최고관리자 원칙

- 최고관리자 계정 1개가 관리자 페이지의 모든 운영 기능을 사용할 수 있다.
- 최고관리자는 사용자·경제·콘텐츠·게임·정책·서버 운영 기능을 조회, 변경, 중지, 재개, 복구할 수 있다.
- 관리자 권한 위임이나 다중 승인 없이 최고관리자 본인이 단독 실행할 수 있다.
- 일반 사용자 세션과 관리자 세션을 분리하고 관리자 페이지 진입 시 재인증한다.
- 비밀번호 외에 WebAuthn 보안키 또는 TOTP 2단계 인증을 필수로 한다.
- 경제 조정, 계정 삭제, 카지노 정책, 대출 정책, 대량 지급, 서버 중지 같은 고위험 작업은 실행 직전 다시 인증한다.
- 관리자 세션은 짧은 만료시간, 유휴시간 잠금, 세션 회전, 원격 강제 로그아웃을 적용한다.
- 등록된 관리자 계정·기기·IP 정책에서 벗어난 로그인은 차단하거나 추가 검증한다.

## 관리자 통제 범위

- 사용자: 조회, 검색, 상태 변경, 로그인 제한, 정지, 해제, 소프트 삭제, 복구, 세션 종료, 연결 계정 확인
- 경제: 지갑·예금·원장 조회, 보정 거래, 일괄 지급, 지급 취소용 반대 거래, 발행·소각 정책, 안전 모드
- 보상: 출석·작업 보상액, 일일·주간 상한, 쿨다운, 정책 버전, 기능 활성화
- 작업·직업: 카탈로그, 난이도, 보상, 경험치, 완료 승인·거절, 직업 활성화, 레벨 기준
- 상점·사업: 상품, 가격, 재고, 구매 제한, 사업 가격·매출·운영비·활성화
- 주식: 종목, 거래시간, 거래 중지·재개, 상장·폐지, 분할·병합, 시장 안전장치
- 은행·대출: 이자율, 신용등급, 한도, 만기, 연체, 신규 사용자 제한, 대출 중지
- 카지노: 게임 활성화, 베팅 한도, 손실 한도, 공개 확률·배당, 전체 긴급 중지
- 시즌: 시즌 생성·수정·종료, 이벤트, 점수 정책, 보상, 순위 재계산
- 콘텐츠: 공지·사진·게시판·신고·숨김·삭제·복구
- Discord: 명령 활성화, 공지, 역할 정책, 사용자 연결 상태, outbox 재처리
- Minecraft: 상태·시작·중지·재시작·허용된 운영 작업·로그 조회
- 시스템: 기능 플래그, 점검 모드, 정책 버전, 백업 상태, 대사 실행, 캐시·작업 큐 상태

## 통제 제한과 안전한 수정 방식

- 최고관리자라도 기존 원장 행과 감사 로그를 수정·삭제하지 않는다.
- 잘못된 거래는 원거래를 참조하는 반대 방향의 보정 거래로 수정한다.
- 카지노의 개별 결과, 주식의 과거 가격, 과거 작업 완료 기록을 사후 조작하지 않는다.
- 정책 변경은 새 버전과 발효시각으로 저장하고 이전 버전을 보존한다.
- 대량 작업은 대상 건수·예상 금액·변경 미리보기를 보여준 뒤 확인 문구와 재인증을 요구한다.
- 긴급 중지 기능은 신규 요청만 막고 진행 중 DB 트랜잭션을 훼손하지 않는다.

## 공통 웹·서버 보안

- CSRF 방어, 입력 검증, 출력 인코딩, 콘텐츠 보안 정책, 보안 헤더
- 로그인·송금·보상·관리 API에 사용자별·세션별 속도 제한
- 비밀값은 서버 환경변수 또는 비밀 저장소에만 보관
- CI에서 비밀값 탐지, 의존성 점검, 테스트 실행
- SSH는 키 기반·최소 계정만 허용, 불필요 sudo 제거
- 컨테이너는 비root 사용자, 읽기 전용 파일시스템 우선, 최소 볼륨 마운트
- DDoS 공격은 인증·속도 제한·엣지 방어로 대응

# 12. 단계별 일정

1. **기획 확정** — 범위, 역할, 경제 시작 잔액, 정책 확정
2. **기반 구축** — 새 테스트 DB·백업·CI·환경변수 분리
3. **인증/계정** — Discord/Google 로그인·정책 동의·계정 연결
4. **경제 코어** — 원장, 지갑, 송금, 보상, 대사
5. **웹/봇** — 사용자 화면, 관리자 화면, Discord 명령
6. **시장 기능** — 상점·사업, 이후 주식/은행을 기능 플래그로 추가

## 14.9 최고관리자 통합 운영 화면

최고관리자 1인이 관리자 페이지에서 전체 기능을 조회·통제한다. 화면은 현황, 사용자, 경제, 작업·직업, 상점·사업, 주식, 은행·대출, 카지노, 시즌, 콘텐츠, Discord·Minecraft, 시스템, 감사 로그 메뉴로 구성한다.

### 관리자 대시보드

- 현재 M2: 사용자 현금 + 예금 + 시장 예치금
- 1시간·24시간·7일 발행량, 소각량, 순발행량
- 출석·작업·사업·은행 이자별 지급량
- 사업 운영비, 세금, 수수료, 카지노 순회수량
- 상위 보유자 집중도와 신규·기존 사용자 자산 격차
- 원장 합계와 계정 잔액의 대사 상태
- 실패한 outbox, 정산, 작업 지급, 관리자 작업
- 로그인·권한 거부·속도 제한·이상 거래 경보
- 각 기능의 활성·중지·점검 상태

### 실행 방식

- 모든 변경 화면에 현재 값과 변경 후 예상 값을 함께 표시한다.
- 변경 사유는 필수이며 빈 값이나 너무 짧은 사유는 거절한다.
- 고위험 작업은 대상, 금액, 영향 범위, 되돌리는 방법을 확인한 뒤 재인증한다.
- 성공·실패·부분 실패를 각각 기록하고 처리된 대상과 제외된 대상을 구분한다.
- 정책 변경은 즉시 적용 또는 예약 발효를 선택할 수 있고 이전 버전으로 복구할 수 있다.
- 원장 이상 시 최고관리자가 보상·시장·은행·카지노를 개별 또는 전체 안전 모드로 전환할 수 있다.

### 불변 상세 감사 로그

모든 관리자 화면 조회와 실행을 audit_logs에 기록한다. 경제 원장과 별도 저장하되 삭제·수정할 수 없는 append-only 구조와 무결성 해시 연결을 사용한다.

각 로그에는 다음 정보를 가능한 한 모두 기록한다.

- audit_id, request_id, trace_id, session_id
- 관리자 내부 ID, 표시명, 인증 수단, 역할, 재인증 시각
- 발생 시각 UTC와 Asia/Seoul, 서버 수신 시각, 완료 시각, 처리시간
- IP 주소, 신뢰 프록시 체인에서 확정한 원본 IP, 국가·지역 추정값
- User-Agent, 브라우저, 운영체제, 기기 식별용 안전한 해시
- HTTP 메서드, 경로, 화면 메뉴, 실행한 관리자 액션 코드
- 대상 종류, 대상 ID, 대상 표시명, 대상 건수
- 변경 사유, 티켓·공지·장애 번호, 관리자 입력 메모
- 변경 전 값, 요청 값, 검증 후 값, 변경 후 값
- 정책 버전 전후, 기능 플래그 전후, 발효시각
- 경제 작업의 원거래 ID, 보정 거래 ID, 계정 ID, 금액, 통화, 차변·대변 요약
- 대량 작업의 전체 대상, 성공 대상, 실패 대상, 제외 대상과 각각의 사유
- 응답 상태, 성공·실패 코드, 안전하게 정제된 오류 분류
- DB 트랜잭션 ID, 적용된 함수·정책 코드, 멱등성 키
- 이전 감사 로그 해시, 현재 로그 해시, 무결성 검증 상태

### 민감정보 기록 제한

- 비밀번호, 세션 쿠키, OAuth 토큰, Discord 토큰, Client Secret, DB 비밀번호는 절대 로그에 남기지 않는다.
- 요청 본문 전체를 무조건 저장하지 않고 허용된 필드만 구조화해 기록한다.
- 개인정보는 목적에 필요한 최소 범위로 기록하고 열람 권한과 보유기간을 적용한다.
- 로그 화면에서 민감값은 마스킹하며 원본 접근도 별도의 감사 로그를 남긴다.

### 로그 검색·보존·경보

- 기간, 관리자, 사용자, 기능, 액션, 대상, 거래 ID, 요청 ID, IP, 성공 여부로 검색한다.
- 한 작업의 관리자 요청 → API → DB 함수 → 원장 거래 → outbox 전달을 trace_id로 연결한다.
- 관리자 로그인 실패, 권한 변경, 대량 지급, 큰 보정 거래, 로그 무결성 실패를 즉시 경보한다.
- 운영 감사 로그는 온라인 검색용과 장기 보관용을 분리하고 암호화 백업한다.
- 보존기간 종료도 자동 삭제가 아니라 정책에 따른 보관·파기 기록을 남긴다.
- 매일 감사 로그 해시 체인 검증과 경제 원장 대사를 실행하고 결과를 별도 검증 로그에 저장한다.

지표와 관리자 조작은 원장을 기준으로 한다. 최고관리자가 모든 기능을 단독 통제하되 과거 기록을 덮어쓰지 않고 정책 버전·보정 거래·상세 감사 로그를 통해 변경한다.

- 작업 보상이 전체 신규 발행의 50%를 지속적으로 넘지 않도록 관리
- 일일 소각량이 일일 발행량의 60~90% 범위에 드는지 관찰
- 상위 보유자 집중도와 신규·기존 사용자 자산 격차 확인

# 15. 자동 경제 조정 엔진

경제 지표를 주기적으로 분석해 보상, 소비 비용, 세금, 이자와 콘텐츠 공급량을 자동 조정한다. 자동화는 과거 원장을 수정하지 않고 다음 정책 버전을 생성하는 방식으로만 동작한다.

## 15.4 자동화 안전장치

- 보상·가격은 하루 단위로 직접 흔들지 않고 주 1회만 변경
- 한 정책은 최소 7일 유지하고 긴급상황 외 연속 변경 금지
- 초반 필수품은 기준가의 80~120%, 일반품은 70~150% 안에서만 자동 변동
- 작업 보상은 기준값의 80~120% 범위만 허용
- 세금·수수료는 0~10%의 사전 승인 범위 안에서만 변경
- 카지노 확률과 과거 결과는 자동 조정 대상에서 제외
- 대출 원금과 기존 계약 이율은 변경하지 않고 신규 계약 정책에만 적용
- 정책마다 version, reason, source_metrics, previous_values, new_values, effective_at, rollback_version 기록
- 최고관리자는 자동조정 전체 또는 항목별 중지, 수동 실행, 승인 범위 변경, 이전 버전 복구 가능
- 자동 변경 전후와 계산 근거를 상세 감사 로그에 기록

# 16. 성장 단계 전체 설계

단계는 가입일만으로 판단하지 않고 누적 작업, 직업 레벨, 정상 수입, 소비, 사업, 업적과 시즌 활동을 함께 본다. 대출·관리자 지급·카지노 수익만으로 단계를 건너뛸 수 없다.

## 16.0 흥미 유지 공통 원칙

- 접속할 때 오늘 할 일 3개, 이번 주 목표 3개, 다음 해금 1개를 항상 보여준다.
- 같은 작업만 반복하지 않도록 작업 후보와 보너스 조건을 매일 변경한다.
- 돈 외에도 경험치, 수집품, 칭호, 프로필 장식, 사업 도감, 시즌 점수를 제공한다.
- 짧은 활동 5분, 중간 활동 20분, 장기 목표 7일 이상을 동시에 제공한다.
- 놓친 출석 때문에 성장이 영구적으로 뒤처지지 않도록 복귀 임무를 제공한다.
- 무한 반복 보상 대신 일일 상한 뒤에는 경험치·도감·커뮤니티 기여만 지급한다.
- 다음 단계 콘텐츠를 잠금 화면에서 미리 보여주고 정확한 해금 조건을 표시한다.
- 운에만 의존하지 않고 누적 진행도로 반드시 보상을 얻을 수 있는 천장 규칙을 둔다.

# 15. 레퍼런스 기반 기술 검토 — 2026-08-26

## 핵심 결론

**운영 경제 원장은 PostgreSQL로 시작한다.** 이전 초안의 SQLite MVP 제안은 사진 메타데이터나 단일 프로세스 테스트에는 유효하지만, 웹·Discord 봇·관리자 작업이 동시에 송금과 보상을 수행하는 경제 서비스에는 적합하지 않다. SQLite WAL은 읽기와 쓰기의 동시 진행을 개선하지만 한 시점에 작성자는 하나뿐이고, 네트워크 파일시스템을 지원하지 않는다. PostgreSQL의 행 잠금과 트랜잭션을 사용해 계정 행을 잠그고 원장·잔액·국고를 한 번에 커밋한다. [SQLite WAL](https://www.sqlite.org/wal.html) · [PostgreSQL Explicit Locking](https://www.postgresql.org/docs/17/explicit-locking.html)

## 경제 시스템 레퍼런스와 적용

- 가상경제는 개발자가 거래세·아이템 소각 같은 정책 충격을 즉시 줄 수 있으므로, 실서비스에 바로 큰 정책을 적용하지 않고 실험군·기간·지표·롤백 기준을 둔다. Old School RuneScape의 세금·소각 개입 연구를 정책 검증 참고 자료로 사용한다. [Market Interventions in a Large-Scale Virtual Economy](https://arxiv.org/abs/2210.07970)
- 게임 통화 연구는 통화 설계와 게임 메커니즘의 연결을 다룬다. 월덕 머니버스에서는 보상 배출(faucet)마다 대응 소비처(sink)를 먼저 설계하고, 신규 콘텐츠는 경제 시뮬레이션 후 기능 플래그로 켠다. [Understanding Currencies in Video Games](https://arxiv.org/abs/2203.14253)
- 인플레이션·변동성은 하루 단위 현금흐름, M2, 상위 보유자 집중도, 거래량, 소비/소각 비율로 모니터링한다. 거래세·보상 배율은 자동으로 즉시 바꾸지 않고 승인된 정책 버전으로만 배포한다. [Virtual Goods Statistical Analysis](https://arxiv.org/abs/1905.06721)

## 운영 DB 스키마

```
users(id, created_at, status)
identities(id, user_id, provider, provider_subject, linked_at)
consent_versions(id, terms_version, privacy_version, published_at)
user_consents(user_id, consent_version_id, agreed_at, age_confirmed)

account_balances(account_id PK, available_amount, updated_at)

outbox_events(id, aggregate_id, type, payload, delivered_at)
audit_logs(id, actor, action, target, request_id, created_at, integrity_hash)
```

- `ledger_transactions`와 `ledger_postings`는 변경하지 않는 원장이다.
- 각 거래는 차변·대변 합계가 0이어야 하며, DB 제약과 서비스 검증을 모두 둔다.
- `account_balances`는 빠른 조회를 위한 파생값이고 원장이 진실의 원천이다.
- 모든 쓰기는 `idempotency_key`의 고유성, `SERIALIZABLE` 또는 필요한 행의 `SELECT … FOR UPDATE`, 짧은 트랜잭션, 재시도 정책을 사용한다.
- 봇 알림은 DB 커밋 뒤 `outbox_events`로 전달한다. 따라서 Discord API 실패가 금전 거래를 되돌리거나 중복 처리하지 않는다.

## Google·Discord 인증 기준

- Authorization Code Flow + PKCE S256, 거래별 state·nonce, 서버 세션 결합을 필수로 한다.
- 콜백 URI는 등록 값과 정확히 일치해야 하며, 임의 `returnUrl` 리다이렉트는 금지한다.
- Google ID Token은 발급자, 대상, 만료, nonce, 서명을 JWKS로 검증한다.
- 기존 노출 가능성이 있는 OAuth Client Secret은 재발급하고, 비밀값은 Git·빌드 로그·오류 화면에 절대 남기지 않는다.

근거: [RFC 9700 OAuth 2.0 Security BCP](https://datatracker.ietf.org/doc/html/rfc9700) · [Google OIDC Reference](https://developers.google.com/identity/openid-connect/reference) · [OWASP Secrets Management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)

## Discord 봇 최적화·안전성

- 애플리케이션 명령은 슬래시 명령 중심으로 최소화하고, 명령 등록을 배포마다 반복하지 않는다. Discord는 길드별 일일 명령 생성 제한을 둔다.
- 필요한 Gateway Intent만 켜고 Message Content, Presence, Guild Members 같은 privileged intent는 기능상 꼭 필요할 때만 사용한다.
- Discord HTTP는 고정 수치로 재시도하지 않고 `Retry-After` 및 rate-limit 헤더를 존중한다.
- 상호작용 수신은 Gateway 또는 서명 검증된 HTTP endpoint 중 하나로 결정한다. HTTP 방식이면 Ed25519 요청 서명 검증·PING 처리·수 초 내 defer 응답을 구현한다.
- 마인크래프트 제어는 허용된 고정 작업만 제공하며 임의 콘솔 명령 전달은 제공하지 않는다.
- 각 명령은 guild·역할·대상 서버·요청자·멱등 키를 검증하고, 결과는 감사 로그에 남긴다.

근거: [Discord Gateway](https://docs.discord.com/developers/events/gateway) · [Discord Rate Limits](https://docs.discord.com/developers/topics/rate-limits) · [Discord Application Commands](https://docs.discord.com/developers/interactions/application-commands) · [Discord Interactions](https://docs.discord.com/developers/interactions/receiving-and-responding)

근거: [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/) · [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) · [OWASP Transaction Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html) · [OWASP Secure Code Review](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Code_Review_Cheat_Sheet.html)

# 16. 환경변수(.env) 운영 가이드

## .env란 무엇인가

`.env`는 코드와 분리해 **환경마다 달라지는 설정과 비밀값**을 서버에 전달하는 파일이다. 소스 코드에 비밀번호, Discord Bot Token, OAuth Client Secret, DB 접속 정보를 직접 넣지 않기 위해 사용한다.

- GitHub에는 올리지 않는다. `.gitignore`에 `.env`, `.env.*`를 등록한다.
- 저장소에는 값이 비어 있는 `.env.example`만 둔다.
- 운영·테스트는 각각 다른 `.env`와 다른 OAuth/Discord 키를 쓴다.
- 값 변경 뒤에는 검증된 무중단 재배포로 새 컨테이너에만 적용한다.
- 토큰·비밀번호·연결 문자열은 채팅, 스크린샷, 오류 페이지, 로그에도 남기지 않는다.

## 파일 위치와 권한

| 환경 | 파일 위치 | 용도 |
| --- | --- | --- |
| 운영 | `/home/wtrdd/wolduk-moneyverse/.env` | 운영 웹·봇·DB 설정 |
| 테스트 | `/home/wtrdd/wolduk-moneyverse-test/.env` | 테스트 웹·봇·DB 설정 |
| 예시 | 저장소 `.env.example` | 키 이름과 설명만 공유 |

새 프로젝트 전환 후의 표준 경로다. 현재 기존 WTRD 프로젝트의 환경파일은 이전 경로에 남아 있으므로, 새 프로젝트에 값만 안전하게 이관하고 기존 파일을 Git에 추가하지 않는다.

권한은 소유자 `wtrdd`만 읽도록 `chmod 600 .env`로 설정한다. Docker Compose는 `env_file` 또는 서버 환경 주입으로만 읽고, 이미지 안에 복사하지 않는다.

## 필수 변수

| 범주 | 변수 | 설명 |
| --- | --- | --- |
| 공통 | `NODE_ENV` | `production` 또는 `test` |
| 공통 | `APP_BASE_URL` | 현재 도메인의 HTTPS 기본 URL |
| 세션 | `SESSION_SECRET` | 최소 32바이트 이상의 무작위 서버 세션 서명 키 |
| DB | `DATABASE_URL` | PostgreSQL 전용 접속 문자열 |
| Discord OAuth | `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET` | 웹 Discord 로그인용 |
| Discord Bot | `DISCORD_TOKEN`, `DISCORD_APPLICATION_ID`, `DISCORD_GUILD_ID` | 봇 연결·테스트 명령 등록용 |
| Google OAuth | `GOOGLE_OAUTH_ENABLED`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Google 로그인용 |
| OAuth | `OAUTH_ALLOWED_REDIRECT_URIS` | 두 도메인의 사전 등록 콜백 URL 목록 |
| 보안 | `TRUST_PROXY`, `CSRF_SECRET` | 역프록시·CSRF 설정 |
| 운영 | `BACKUP_ENCRYPTION_KEY` | 백업 암호화 키 |
| 운영 | `LOG_LEVEL` | 운영 기본값은 `info`; 비밀값 출력 금지 |

## 운영 절차

1. 새 키는 OAuth/Discord 관리 화면에서 발급 또는 재발급한다.
2. 관리자만 서버의 `.env`에 추가한다. 파일 내용은 복사·공유하지 않는다.
3. `env.example`에는 **키 이름만** 갱신한다.
4. 배포 전 CI 비밀값 검사와 `git status`로 노출 여부를 확인한다.
5. 테스트 서버에서 로그인·봇·DB 연결을 먼저 확인한다.
6. 운영 배포 뒤 상태 점검을 하고, 노출 의심 시 해당 키를 즉시 폐기·재발급한다.

## 주의

- `SESSION_SECRET`은 OAuth Client Secret과 별개다. 현재 운영 설정에서 누락된 것으로 확인되어, 새 시스템 배포 전에 반드시 새 난수 값으로 추가한다.
- Google Client Secret은 화면 노출 가능성이 있었으므로 기존 값을 재사용하지 않고 재발급한다.
- `.env`는 데이터 백업에 평문으로 포함하지 않는다. 필요 시 접근권한이 분리된 암호화 비밀 백업만 사용한다.

## 17.2 신뢰 경계

1. **브라우저/Discord 사용자**는 모두 신뢰하지 않는다. 사용자 ID, 금액, 역할, 파일명, 화면의 “성공” 표시는 서버가 재검증한다.
2. **웹 앱·봇**은 별도 서비스 계정을 사용하고, DB에 관리자·superuser 권한으로 접속하지 않는다.
3. **경제 DB**는 외부 인터넷에 포트를 열지 않고 앱 네트워크에서만 접근한다.
4. **역프록시·Cloudflare**는 TLS 종료와 DDoS 완화를 담당하지만, 앱도 인증·권한·입력 검증을 수행한다.
5. **테스트와 운영**은 도메인, DB, Bot Token, OAuth Client, 저장소 경로, 백업 키를 공유하지 않는다.

## 17.3 로그인·계정 연결

### Discord·Google OAuth

- Authorization Code Flow만 사용하고 PKCE는 `S256` 방식으로 구현한다.
- 로그인 시작마다 암호학적으로 안전한 `state`, PKCE verifier/challenge, OIDC `nonce`를 새로 만들고 짧은 만료시간으로 서버 세션에 결합한다.
- 콜백은 사전 등록한 URI와 **정확히 일치**하는 경우만 허용한다. `returnUrl`, `next`, `redirect` 등 사용자가 넣은 외부 리다이렉트는 허용하지 않는다.
- Google ID Token은 서명(JWKS), `iss`, `aud`, `exp`, `nonce`를 서버에서 검증한다.
- OAuth 제공자 ID가 이미 다른 내부 사용자에게 연결돼 있으면 자동 병합하지 않고 차단·감사한다.
- 제공자 연결/해제, 이메일 변경, 관리자 권한 부여, 백업키 발급은 최근 재인증을 요구한다.
- OAuth access/refresh token은 장기 저장하지 않는다. 꼭 필요한 경우에는 암호화·최소 범위·만료·폐기 절차를 문서화한다.

근거: [RFC 9700](https://datatracker.ietf.org/doc/html/rfc9700) · [Google OIDC](https://developers.google.com/identity/openid-connect/reference)

### 자체 웹 로그인

- 자체 비밀번호 로그인은 OAuth 외의 보조 방식으로만 제공한다.
- 비밀번호는 복호화 가능한 “암호화”가 아니라 **Argon2id 해시**로 저장한다. 최소 기준은 memory 19 MiB, iterations 2, parallelism 1이며 서버 성능 측정 뒤 상향한다.
- 최소 15자, 최대 64자 이상 허용, 유출·상용 비밀번호 차단 목록, 실패 횟수 제한과 지연을 적용한다. 불필요한 문자 조합 규칙·정기 변경 강제·보안 질문은 적용하지 않는다.
- 비밀번호 재설정 토큰은 1회용·짧은 만료·해시 저장이며, 성공 시 기존 세션을 모두 폐기한다.
- 운영자/관리자 계정은 Discord 역할만으로 완결하지 않고 추가 재인증 또는 별도 강력 인증을 적용한다.

근거: [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) · [NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html)

## 17.4 세션·CSRF·브라우저 보안

- 세션 ID는 충분히 긴 난수이며 로그인·권한상승 직후 회전한다.
- 인증 토큰, JWT, OAuth refresh token은 `localStorage`·`sessionStorage`에 저장하지 않는다.
- 쿠키는 `HttpOnly; Secure; SameSite=Lax`를 기본으로 하고, 관리·송금 등 민감 경로는 Origin 검증과 CSRF 토큰을 추가한다.
- 상태를 바꾸는 API는 GET으로 제공하지 않는다.
- CSRF는 세션에 결합한 토큰 또는 서명된 double-submit 패턴을 쓰며, 토큰 누락·불일치는 실패로 처리한다.
- HTTP 보안 헤더: HSTS, CSP(스크립트 nonce 기반), `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` 최소화.
- 두 도메인은 쿠키를 공유하지 않는다. 각 도메인은 자체 host-only 세션 쿠키와 정확한 OAuth 콜백을 사용한다.

근거: [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) · [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

## 17.5 API·권한 통제

- API는 `/me` 같은 현재 사용자 컨텍스트에서 대상을 해석하고, URL/본문의 `userId`만 믿지 않는다.
- 모든 객체 조회·수정·삭제마다 “현재 사용자/역할이 이 레코드에 접근 가능한가”를 서비스 계층에서 검사한다. UUID 사용은 보조 수단일 뿐 권한 검사를 대체하지 않는다.
- DTO 허용목록을 사용해 입력 가능한 필드만 명시한다. 요청 본문을 DB 모델에 그대로 병합하지 않는다.
- 관리자 라우트는 일반 사용자 라우트와 분리하고, 기본 거부·역할 허용목록·서버 측 매 요청 검증을 적용한다.
- 정책 변경·국고 조정·대량 지급은 요청자와 승인자를 분리한다. 승인자는 본인 요청을 승인할 수 없다.
- API 버전·도메인·노출 endpoint를 인벤토리로 관리하고, 디버그·문서 endpoint가 운영에 우연히 열리지 않게 한다.
- 사용자별·계정별·세션별·IP 기반 다층 rate limit을 둔다. 정상 사용자를 과도하게 잠그지 않도록 짧은 지연, 한도 안내, 보안 이벤트 검토 절차를 함께 둔다.

근거: [OWASP API Security Top 10](https://owasp.org/API-Security/editions/2023/en/0x11-t10/) · [BOLA 예방](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)

## 17.6 경제 거래 보안

- 클라이언트는 금액·대상·수수료·보상·정책값을 제안만 할 수 있고, 서버가 DB 내 최신 상태와 정책 버전으로 다시 계산한다.
- 송금, 시장 체결, 국고 지급, 관리자 조정에는 `Idempotency-Key`를 의무화한다. 동일 키의 재전송은 동일 영수증만 반환한다.
- 트랜잭션 안에서 계정 행을 잠그고 잔액·한도·정책·중복 키를 검사한 뒤 원장 posting과 파생 잔액을 함께 커밋한다.
- 원장 posting의 합계가 0이 아니면 DB 제약 또는 서비스 검증에서 실패하게 한다.
- Discord 메시지 전송, 웹훅, 통계 집계는 DB 커밋 이후 outbox worker가 처리한다. 외부 API 실패가 거래 중복·부분 완료를 만들지 않게 한다.
- 대량 보상·정책 변경은 실행 전 요약(대상 수, 총액, 정책 버전)을 표시하고 승인 후 실행한다.
- 지급·송금·관리자 조정은 사용자에게 영수증 ID를 제공하며, 운영자는 그 ID로 원장·감사 로그·outbox 결과를 대사할 수 있다.

근거: [OWASP Transaction Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html)

## 17.7 Discord 봇 보안

- 봇 토큰은 웹 OAuth Client Secret과 분리하고, 토큰 노출 의심 시 즉시 재생성·교체한다.
- 필요한 Gateway Intent만 활성화하고 Message Content·Presence·Guild Members intent는 필요성과 영향 평가 후에만 켠다.
- 모든 슬래시 명령은 설치된 guild, 요청자 Discord ID, 역할, 대상 Minecraft 서버를 서버에서 확인한다.
- 마인크래프트 제어는 상태·시작·중지·재시작·로그처럼 허용된 고정 동작만 제공한다. 임의 콘솔 명령 문자열 전달은 금지한다.
- HTTP Interaction 방식을 선택하면 Ed25519 서명을 원문 body와 timestamp로 검증하고, 실패 요청을 처리하지 않는다. Gateway 방식과 HTTP 방식은 동시에 사용하지 않는다.
- 오래 걸리는 작업은 즉시 defer 응답 후 큐에서 처리한다. Discord rate-limit의 `Retry-After`를 준수하며 고정 지연값으로 무한 재시도하지 않는다.
- 사용자 입력을 Discord 메시지로 보낼 때 mention 허용목록을 사용해 예기치 않은 @everyone/@role 알림을 막는다.

근거: [Discord Interactions](https://docs.discord.com/developers/platform/interactions) · [Discord Rate Limits](https://docs.discord.com/developers/topics/rate-limits)

## 17.8 사진·파일 업로드

- MVP 허용 형식은 JPEG, PNG, WebP로 한정한다. SVG, HTML, JavaScript, 실행파일, 압축파일은 받지 않는다.
- 파일명·MIME header를 신뢰하지 않고 매직바이트·이미지 디코딩으로 실제 형식을 확인한다.
- 파일 크기·가로세로·업로드 횟수·총 저장용량을 제한하고, 서버가 생성한 무작위 파일명만 쓴다.
- 파일은 웹 루트 밖 별도 SSD 경로에 저장한다. 공개 파일도 애플리케이션의 매핑 URL을 통해 제공하며 디렉터리 열람을 금지한다.
- 비공개 사진은 권한 검증 뒤 짧은 만료의 서명 URL 또는 앱 스트리밍으로 제공한다.
- 업로드·조회·삭제는 감사 이벤트로 기록한다. 악성코드 검사 도입 가능성을 남겨 두고, 개인정보가 담긴 이미지를 외부 검사 API로 보내지 않는다.

근거: [OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

## 17.9 PostgreSQL·컨테이너·서버

### PostgreSQL

- 역할 분리: migration 전용, 앱 읽기/쓰기 전용, 읽기 전용 리포트, 백업 전용. 앱 역할에는 SUPERUSER·CREATEDB·CREATEROLE·BYPASSRLS를 주지 않는다.
- DB는 Docker 내부 네트워크 또는 loopback에만 노출하고 공인 포트를 열지 않는다.
- 앱↔DB가 호스트 경계를 넘는 경우 TLS와 SCRAM-SHA-256 인증을 사용한다.
- 연결 풀의 최대 연결 수와 DB role connection limit을 설정해 폭주를 제한한다.
- 일일 논리 백업, 주기적 복구 테스트, 중요 데이터는 WAL 아카이빙/PITR 도입 여부를 운영 규모에 맞춰 결정한다.

근거: [PostgreSQL Role Attributes](https://www.postgresql.org/docs/17/role-attributes.html) · [PostgreSQL SASL/SCRAM](https://www.postgresql.org/docs/17/sasl-authentication.html) · [PostgreSQL Backup](https://www.postgresql.org/docs/17/backup.html)

### Docker·호스트

- 컨테이너는 비root 사용자로 실행하고, 필요한 경로만 읽기/쓰기 마운트한다.
- 앱 컨테이너에 Docker socket, host network, privileged 권한, 불필요 Linux capability를 주지 않는다.
- 이미지 태그는 고정 digest 또는 검증된 버전으로 관리하고, 빌드 단계와 실행 단계를 분리한다.
- 호스트 커널·Docker Engine·이미지·Node 의존성의 보안 업데이트를 정기 점검한다.
- SSH는 키 기반, 최소 사용자, sudo 최소화, root 직접 로그인 정책은 비상 복구 필요성과 별도로 정기 검토한다.
- 상태 점검은 비밀값·DB 연결 문자열을 응답에 포함하지 않는다.

근거: [OWASP Docker Security](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html)

## 17.10 로그·감사·백업·사고 대응

### 로그 원칙

- 거래 원장, 감사 로그, 애플리케이션 보안 로그, 인프라 로그를 목적·권한·보존기간별로 분리한다.
- 기록 항목: 시각, 요청 ID, 내부 사용자 ID, 역할, action, 대상 ID, 결과, 정책 버전, 거래 ID, 오류 분류.
- 기록 금지: 비밀번호, 세션 ID, access/refresh token, DB URL, OAuth Client Secret, Bot Token, 암호화 키, 전체 개인정보, 원문 업로드 파일.
- 로그 입력은 줄바꿈·제어문자를 정규화해 log injection을 막고, 모든 서버 시간은 동기화한다.
- 관리자 작업, 권한 거부, 인증 실패 급증, 고액 거래, 정책 변경, 키 회전, 백업 복구는 경보 대상이다.
- 로그·감사 레코드는 권한 분리와 해시 연결로 변조 탐지를 지원한다.

근거: [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

### 백업과 복구

- 별도 SSD에 암호화된 DB 백업과 사진 메타데이터를 저장한다. 운영 DB와 같은 볼륨만 백업 위치로 사용하지 않는다.
- 백업 암호화 키는 백업 파일과 분리해 보관한다.
- 매일 자동 백업, 주간 복구 리허설, 월간 전체 장애 복구 훈련을 실시한다.
- 복구 성공 기준: 지정 시점의 원장 합계, 계정 잔액, 사진 메타데이터, 서비스 로그인, 봇 기본 명령이 모두 검증되는 것.
- 비밀값은 일반 DB 백업과 로그에 포함하지 않는다.

### 사고 대응

1. 탐지: 경보·감사 로그·사용자 신고로 이상을 분류한다.
2. 격리: 의심 세션 폐기, 해당 API/명령 feature flag 중단, 손상 계정·키 비활성화.
3. 보존: 로그·원장·컨테이너 상태·DB 스냅샷을 보존하되 비밀값을 외부에 노출하지 않는다.
4. 복구: 안전한 시점으로 복구하고 원장 대사 후 제한적으로 재개한다.
5. 재발 방지: 원인·영향·조치·키 회전·테스트 항목을 기록한다.

# 18. Google Search Console·SEO·Google AdSense·대한민국 법률 준수 계획

> **주의:** 이 절은 출시 전 준수 설계와 검증 목록이다. 법률 자문이나 Google의 승인 보증이 아니며, 실제 유료화·확률형 기능·광고 게재 전에는 최신 정책과 국내 전문 검토를 다시 확인한다.
> 

## 18.1 현재 점검 상태와 한계

- Search Console 시작 화면까지는 확인했지만, 연결된 Google 계정이 로그인되어 있지 않아 실제 속성 소유권, 색인 범위, 성능, 수동 조치, 보안 문제, sitemap 처리 결과는 확인하지 못했다.
- 공개 robots.txt/sitemap의 직접 읽기는 현재 브라우저 확장 차단으로 검증되지 않았고, 일반 검색의 결과 부재만으로 “색인되지 않았다”고 단정할 수 없다.
- 따라서 현재 결론은 **기술·정책 설계 점검 완료 / Search Console 실측 점검은 속성 인증 후 수행 필요**이다.

## 18.2 SEO의 기본 결정

### 대표 도메인

두 도메인 [easy-scraping.com](http://easy-scraping.com), [weoldeog.com](http://weoldeog.com)에 같은 공개 콘텐츠를 동시에 노출하면 중복 콘텐츠가 될 수 있다. 출시 전에 하나를 **대표 공개 도메인**으로 확정하고 다음을 적용한다.

- 비대표 도메인의 동일 공개 URL은 대표 URL로 영구 리다이렉트(301)한다.
- 각 공개 페이지는 자기 자신 또는 대표 URL 하나만 canonical로 선언한다.
- 로그인·세션 쿠키는 두 도메인 간에 공유하지 않으며 host-only로 유지한다.
- OAuth 콜백은 각 도메인에 정확히 등록하되, SEO 대상과 인증 콜백을 혼동하지 않는다.

### 색인 허용/차단 경로

| 분류 | 예시 | 검색 처리 |
| --- | --- | --- |
| 공개 정보 | /, /about, /guide/*, /news/*, /privacy, /terms, 사진 공개 갤러리 | 색인 허용·sitemap 포함 |
| 개인/거래 화면 | /login, /auth/*, /account/*, /wallet, /transfer, /market/* | noindex·sitemap 제외·인증 필요 |
| 운영 화면 | /admin/*, /api/*, /status/*, preview/test 경로 | 외부 색인 금지·인증 또는 네트워크 제한 |

robots.txt는 크롤링 관리 보조 수단일 뿐 이미 알려진 URL을 색인에서 제거하지 않는다. 민감 페이지에는 HTTP X-Robots-Tag: noindex 또는 meta robots와 인증을 함께 적용한다.

## 18.3 구현 체크리스트

- 서버가 200 응답의 HTML에서 페이지별 고유 제목, 한 개의 명확한 H1, 설명문, 사람이 읽을 수 있는 본문, 의미 있는 내부 링크를 제공한다. 핵심 콘텐츠를 로그인 뒤 JavaScript만으로 숨기지 않는다.
- 콘텐츠는 사람이 검토한 고유 안내·게임 규칙·안전성·운영 정책 중심으로 작성한다. 자동 생성한 얇은 페이지, 키워드 반복, 숨김 텍스트, 링크 조작, 검색 순위만을 위한 대량 페이지를 만들지 않는다.
- 모든 공개 URL은 HTTPS, 단일 canonical, 정상 상태코드, 모바일 반응형, 빠른 이미지 제공(크기 지정·지연 로딩·대체 텍스트)을 충족한다.
- sitemap.xml은 대표 도메인의 정규 공개 URL과 lastmod만 포함해 자동 생성한다. 페이지 삭제·리다이렉트 시 sitemap도 함께 갱신한다.
- 구조화 데이터는 실제 화면에 보이는 정보만 JSON-LD로 표시한다. 초기에는 Organization, WebSite, BreadcrumbList, 사실 기반 Article만 사용하며, 가짜 평점·후기·할인·숨겨진 내용은 표시하지 않는다.
- 배포마다 canonical, robots/noindex, sitemap URL, title/H1, 404/리다이렉트, 이미지 alt, Core Web Vitals를 자동 검사한다.

근거: [Google Search Essentials](https://developers.google.com/search/docs/essentials) · [Google Structured Data Policies](https://developers.google.com/search/docs/appearance/structured-data/sd-policies) · [Google Search Spam Policies](https://developers.google.com/search/docs/essentials/spam-policies)

## 18.4 Search Console 운영 절차

1. 대표 도메인의 **도메인 속성**을 DNS 방식으로 인증한다. 두 도메인을 실제로 계속 제공하면 각각 별도 속성도 인증한다.
2. 대표 도메인의 sitemap.xml을 제출하고, 새 공개 페이지와 주요 정책 페이지는 URL 검사로 색인 가능 여부를 확인한다.
3. 매주 다음을 검토한다: 페이지 색인 보고서, Core Web Vitals, HTTPS, 리치 결과, 수동 조치, 보안 문제, 검색 성능(클릭·노출·검색어·국가·기기).
4. noindex가 필요한 개인/관리/거래 화면이 실수로 색인되지 않았는지와, 대표 공개 페이지가 비대표 도메인으로 색인되지 않았는지를 배포 게이트로 검사한다.
5. 404 급증, 비정상 리다이렉트, 색인 제외 급증, 수동 조치, 보안 경고가 발생하면 해당 배포를 중지·롤백하고 원인을 기록한다.

Google은 요구사항 충족이 크롤링·색인·순위를 보장하지 않는다고 명시한다. 성과 수치는 인증된 속성에서만 판단한다.

근거: [Google Search Essentials](https://developers.google.com/search/docs/essentials)

## 18.5 AdSense 안전 설계 — 기본값은 비활성화

ADS_ENABLED=false를 기본값으로 둔다. AdSense 승인과 정책 검토가 끝나기 전에는 광고 코드를 로드하지 않는다.

### 광고를 둘 수 있는 영역

- 독립된 공개 정보·가이드·FAQ·운영 안내·원본 뉴스/콘텐츠 페이지처럼 실질적인 본문이 있는 화면만 경로 allowlist로 허용한다.
- 광고와 본문·내비게이션·버튼 사이를 명확히 분리하며, 게임 조작·로그인·결제·송금 버튼 가까이에 광고를 배치하지 않는다.
- 광고 클릭을 유도하는 문구, 보상, 퀘스트, 포인트, 화살표, 다운로드 버튼 위장, 자동 클릭·새로고침·트래픽 구매를 금지한다.
- 광고 차단 사용자를 우회·강제하거나 광고를 콘텐츠·버튼으로 위장하지 않는다. 광고가 차단되어도 핵심 공개 정보는 접근 가능해야 한다.

### 광고를 절대 두지 않는 영역

- 카지노, 베팅, 룰렛, 슬롯, 확률형 보상, 가상자산 잔액·거래·송금·시장·주식·대출 화면
- 로그인/가입/OAuth/계정/지갑/관리자/상태/오류/빈 화면
- 게임 플레이 캔버스·대기실·결과·보상 수령·상호작용 버튼이 있는 화면
- 미성년자 접근 가능성이 높은 화면, 사용자 업로드가 검토되지 않은 사진/게시물 옆, 약관·개인정보 동의 화면

가상화폐가 실제 환전되지 않더라도 카지노·확률형·도박 연상 화면과 결합한 광고는 AdSense 정책·브랜드 안전성에 높은 위험이 있으므로 MVP에서는 해당 모든 경로의 광고를 금지한다. 개인화 광고는 경제 잔액·거래·취향 또는 도박 관련 관심사를 기준으로 타기팅하지 않는다.

근거: [Google AdSense Program Policies](https://support.google.com/adsense/answer/48182?hl=en) · [AdSense Publisher Restrictions](https://support.google.com/adsense/answer/10437795?hl=en) · [Google Ad Policy — Gambling](https://support.google.com/adspolicy/answer/16701250?hl=en)

### 개인정보·광고 고지

- Google 광고 또는 광고 태그가 쿠키/식별자를 사용하기 전에 실제 적용 방식에 맞는 개인정보처리방침과 쿠키·광고 고지를 제공한다.
- 고지에는 Google 등 제3자 공급자, 쿠키 사용 목적, 개인화 광고 여부, 선택/거부 방법, 처리방침 링크를 실제 기능과 일치하게 기재한다.
- ads.txt는 실제 승인된 AdSense 게시자 ID가 발급된 뒤에만 추가한다. 임의·예시 ID는 게시하지 않는다.

근거: [Google AdSense Privacy Policy Requirements](https://support.google.com/adsense/answer/1348695?hl=en) · [Google Cookie Consent Guidance](https://support.google.com/adsense/answer/7549925?hl=en)

## 18.6 대한민국 법률 준수 설계

### 개인정보보호

- 개인정보는 계정 생성·인증·자산 원장·보안·고객지원에 꼭 필요한 최소 항목만 수집한다.
- 동의를 근거로 수집할 때는 목적, 항목, 보유·이용 기간, 동의 거부권과 거부 시 불이익을 분명히 고지한다. 계약 이행 등 다른 법적 근거를 쓰는 경우도 근거와 범위를 문서화한다.
- 개인정보처리방침에는 처리 목적·항목·보유기간, 제3자 제공/처리위탁, 국외 이전, 파기, 정보주체 열람·정정·삭제·처리정지 요청 방법, 안전성 조치, 개인정보 보호책임자와 연락처, 변경 이력을 실제 운영에 맞게 공개한다.
- 익명 홈페이지 방문은 앱 수준 IP 저장을 하지 않는다. 로그인·보안 이벤트에서 IP 또는 식별정보를 필요 최소한으로 처리할 경우에는 목적·보유기간·접근권한을 별도로 명시한다.
- 14세 미만의 가입·개인정보 처리는 법정대리인 동의와 연령 확인 절차가 검증되기 전까지 허용하지 않는다. 단순 체크박스만으로 처리하지 않는다.

근거: [개인정보 보호법 제15조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029335387) · [동의 고지 사항](https://www.law.go.kr/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=900079620) · [개인정보처리방침 작성지침](https://m.pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS217&mCode=D010030000&nttId=12018)

### 가상경제·게임·소비자 보호

- 서비스 화폐는 게임 내에서만 사용하며 현금 환전, 출금, 외부 자산 교환, 양도 대가 지급, 실제 상품·경품을 위한 베팅을 제공하지 않는다.
- MVP에서 카지노·베팅·슬롯·룰렛·확률형 유료 보상은 비활성화한다. 확률 또는 유료 요소를 검토하는 경우에는 게임물 등급·사행성·청소년 보호 관련 전문 검토와 별도 승인 없이 출시하지 않는다.
- 실제 돈을 받는 구독, 디지털 상품, 광고성 결제, 유료 확률 요소를 도입하면 전자상거래 소비자 보호 의무, 사업자 정보·청약철회/환불·고객지원 정책, 세무·결제·게임 규제 검토를 별도 릴리스 게이트로 적용한다.
- 운영자 조정·시세 개입·보상 정책은 공개 정책과 감사 로그로 남기며, 실제 투자·수익·금융상품처럼 오인될 표현을 사용하지 않는다.

근거: [게임산업진흥에 관한 법률](https://www.law.go.kr/LSW/lsInfoP.do?ancYnChk=0&chrClsCd=010202&efYd=20260324&lsiSeq=284663&urlMode=lsInfoP) · [전자상거래 등에서의 소비자보호에 관한 법률](https://www.law.go.kr/LSW/lsLawLinkInfo.do?chrClsCd=010202&lsId=009318&lsJoLnkSeq=1000527507&print=print)

## 18.7 운영 환경변수와 광고 경로 제어

PUBLIC_CANONICAL_ORIGIN=[https://CHOSEN_PRIMARY_DOMAIN](https://CHOSEN_PRIMARY_DOMAIN)

SEARCH_CONSOLE_VERIFICATION=...

ADS_ENABLED=false

ADSENSE_PUBLISHER_ID=

ADS_ALLOWED_PATHS=/guide,/news,/about

ADS_BLOCKED_PATHS=/login,/auth,/account,/wallet,/transfer,/market,/game,/casino,/admin,/status

- 위 값은 예시이며 비밀값을 담지 않는다.
- 광고는 서버 측 allowlist와 배포 검증을 모두 통과한 페이지에서만 로드한다. 클라이언트 쿼리값으로 광고 노출 경로를 바꿀 수 없게 한다.
- SEARCH_CONSOLE_VERIFICATION 값은 공개 meta/DNS 검증용일 수 있으나, OAuth Client Secret·AdSense 접근 권한·쿠키 키는 절대 여기에 포함하지 않는다.
