# Shop Weekly Upkeep Cap — Bounded Design

Status: engineering candidate; release hold until all exact-SHA gates pass.

Member and guest shop visitors need a transparent way to exclude products with recurring weekly upkeep above a chosen WLD limit. The existing `shop_catalog`/`shop_public_catalog` PostgreSQL SECURITY DEFINER read model returns `maintenance_cost::text`; no schema or financial mutation is necessary. Use a single optional `maxUpkeep` query argument on both existing catalogue endpoints, validated as canonical nonnegative decimal integer (up to 30 digits), and compare with `BigInt`, never floating point. An empty form field is absence; malformed, signed, decimal, scientific and oversized inputs receive 400. Preserve the existing `q` search. The web GET form submits `q` and `maxUpkeep`, displays the active bound, and provides reset. Android `/app-api/v1/shop/catalog` and `/public-catalog` forward the identical query, with `private, no-store` for shop responses. The DB actor is always taken from the session; no new table grants, migrations, or ledger writes. Tests: red/green filter unit tests, controller guard and invalid query tests, web URL and accessibility tests, Android forwarding/privacy test, and isolated PostgreSQL catalogue smoke with a no-direct-table-SELECT check. Rollback is code-only: remove the optional parameter; unchanged DB functions remain authoritative. Never merge or deploy without full CI, exact-SHA isolated Test and release gates.
