# Verified P2P Transfer Receipt — Bounded Implementation Plan

**Goal:** Prevent fabricated P2P transfer confirmations and accidental repeat attempts after an ambiguous response.

**Architecture:** Keep the existing authenticated NestJS ledger-backed transfer endpoint. Validate and forward the per-intent UUID through Next BFF, require a UUID receipt from the backend, and show the client a success receipt only on verified confirmation. An uncertain network/5xx response is not proof of failure; require checking the wallet before starting another transfer. Preserve B #1117 atomic metadata fix as an unmerged dependency.

**Tech Stack:** Next.js 16 App Router, React 19, Vitest, NestJS wallet contract.

**Constraints:** No migrations, no changes to main or other worktrees, no synthetic transaction IDs, no automatic retry, no Production without full gates.

1. RED: Add BFF tests for authentication, malformed amount/key, missing/malformed transaction ID, upstream failure, private headers, and UUID forwarding. Add UI tests for success/unknown state, no fabricated ID or notification claims, accessibility.
2. GREEN: Implement input validation and receipt parsing in Next route, preserve client idempotency key per transfer intent, handle ambiguous outcomes without implying failure, and render actual receipt UUID.
3. VERIFY: Run focused Vitest, lint/typecheck/build, security/app-api, full tests and CI, isolated PostgreSQL exact-SHA Test if safe. Re-fetch origin/main and planning documents mid and before integration; record blockers.
4. REVIEW: Inspect diff for privacy and duplicate transfer risks, open Draft PR, never merge on failed gates.
