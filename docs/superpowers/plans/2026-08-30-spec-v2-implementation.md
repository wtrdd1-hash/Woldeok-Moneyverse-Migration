# 기획서 v2 구현 계획 — 2026-08-30

기획서 개정판(단일 최고관리자 · 자동 경제 조정 엔진 · 성장 단계 · 상점 카탈로그)을
현재 코드베이스에 얹는 계획이다. 코드베이스 전수 조사(10개 축) 결과를 근거로 한다.

## 1. 이 계획의 형태를 결정한 두 제약

### 1.1 마이그레이션은 002부터 빈틈없이 이어져야 한다

`packages/database/test/migration-parity.test.ts`

```
it('carries a contiguous, duplicate-free sequence from 002')
  expected = [2, 3, …, n]        // 빠진 번호도, 겹친 번호도 실패
```

디렉터리는 지금 **055**에서 끝나므로 다음 번호는 **056**이다. 그리고 이 규칙 때문에
**브랜치를 main에서 각자 따면 안 된다.** PR-A가 056–058, PR-B가 059–061을 쓰면
PR-B 단독 트리에는 056–058이 없어 `[2..55, 59, 60, 61]`이 되고 테스트가 깨진다.

→ **PR은 스택으로 쌓는다.** 각 PR의 base는 바로 앞 PR의 브랜치다. 그러면 어느 층에서도
   002..N이 연속이고, CI가 각 PR에서 실제로 통과한다. 병합 순서 = 스택 순서 = 번호 순서.

### 1.2 ROUTE_MAP은 원본 라우트 전용이고 92개로 못박혀 있다

`expect(originalRoutes()).toHaveLength(92)` — **새 기능의 새 라우트는 여기 넣지 않는다.**
`route-map.ts`를 건드리는 PR은 기존 `POST /api/v1/rewards/work` 행의 replacement를
고치는 작업 PR 하나뿐이다. PR 간 충돌 지점이 아니다.

## 2. 전 PR 공통 규약

조사에서 확인된 것들이며, 어기면 리뷰에서 되돌아온다.

- **비즈니스 로직은 SQL에 둔다.** `moneyverse_app`은 잔액을 UPDATE할 수도, 감사 행을
  DELETE할 수도 없다. 새 읽기 경로에는 GRANT가 아니라 **함수**를 만든다.
- **함수 템플릿** — 예외 없이 이 순서다.
  ```sql
  REVOKE ALL PRIVILEGES ON TABLE public.<t> FROM PUBLIC, moneyverse_app;
  CREATE OR REPLACE FUNCTION public.<f>(…) RETURNS … LANGUAGE plpgsql
    SECURITY DEFINER SET search_path = pg_catalog, pg_temp AS $$ … $$;
  ALTER FUNCTION public.<f>(…) OWNER TO moneyverse_migrator;
  REVOKE ALL PRIVILEGES ON FUNCTION public.<f>(…) FROM PUBLIC, moneyverse_app;
  GRANT EXECUTE ON FUNCTION public.<f>(…) TO moneyverse_app;
  ```
  `SET search_path` 누락은 패리티 테스트가 잡는다.
- **멱등성은 045가 정본이다.** 입력 검증 → `pg_advisory_xact_lock(hashtextextended
  ('moneyverse:<fn>:' || p_key::text, 0))` → 재생 조회 → **소유자 확인(28000)** → 본작업.
  045가 빠뜨린 `economy_claim_work`·`business_settle_daily`·`economy_transfer`는
  PR4에서 같이 맞춘다.
- **SQLSTATE 규약** — `22023` 잘못된 요청/불균형/잔액부족, `23505` 이미 처리/쿨다운,
  `55000` 기능 중지/append-only 위반, `28000` 남의 영수증, `42501` 역할 거부.
  `backend/src/core/pg-error.ts`가 HTTP로 옮긴다. 새 코드를 쓰면 여기도 같이 고친다.
- **금액은 정수다.** `bigint`, 문자열로 왕복, `Number`로 옮기지 않는다. 자리수 구분은
  `lib/money.ts`가 문자열을 걸어서 한다.
- **돈은 `economy_post_transaction`만 움직인다.** 앱 역할에는 EXECUTE가 없고,
  마이그레이션이 소유한 래퍼 함수만 호출한다. 새 기능도 예외 없다.
- **원장은 고치지 않는다.** 잘못된 거래는 원거래를 참조하는 **보정 거래**로 되돌린다(PR4).
- **글은 영어로.** 주석·커밋·PR 제목/본문·테스트 이름. `docs/`만 한국어 허용.
  사용자에게 보이는 한국어 문구는 제품 결정이므로 임의로 바꾸지 않는다.
- **커밋에 Claude 흔적을 남기지 않는다.** `Co-Authored-By`·`Claude-Session`·
  "Generated with" 문구 전부 금지.
- **DB 테스트는 CI에서만 돈다.** 이 머신에는 Postgres도 Docker도 없다. 새 SQL 함수마다
  `*.db.test.ts`를 쓰되, 로컬에서 통과했다고 말하지 않는다 — CI가 실행처다.

### PR1 — 카지노 동전 확률 (056)

**지금 프로덕션에 있는 실제 버그다.** `casino_play_coin`은
`get_byte(gen_random_bytes(1),0) < 48`로 앞면을 정한다. 바이트는 0..255이므로
앞면 48/256 = **18.75%**, 뒷면 81.25%다. 기획서 §14.3이 `< 128`을 명시한다.

- 042는 이미 적용됐으므로 고치지 않고 **056에서 함수를 교체**한다(기획서 지시).
- 최소/최대 베팅·일일 총베팅·일일 손실 한도를 DB 정책 행으로 옮긴다.
- 브라우저는 선택과 베팅액만 보낸다. 결과·확률·지급액은 서버가 정하고,
  확률·배당·**최대 손실 가능성**을 반환값에 실어 화면이 공개한다(§3 게임물법 근거).
- **분포 시험 하네스**(§14.3): 100만 회를 돌려 이항 신뢰구간 안에 드는지 검증한다.
  CI에서 도는 통계 테스트이지 눈으로 보는 스크립트가 아니다.
- **기능 스위치에 `casino` 행을 운영 기본 disabled로 등록**한다(§18.6 — MVP에서
  카지노는 비활성이고, 게임물 등급·사행성 전문 검토 없이 켜지 않는다). 활성화 조건은
  분포 시험 기록 · 원장 대사 · 법률 검토 세 가지를 행이 참조한다.
- 지금 카지노는 컨트롤러도 라우트도 없어 HTTP로 닿지 않는다. **그 상태를 유지한다.**

  빈 값이나 너무 짧은 사유는 거절한다. 고위험 작업은 대상·금액·영향 범위와
  **되돌리는 방법**을 확인시킨 뒤 재인증한다(§14.9 실행 방식).
- 프론트: `/admin/approvals` → `/admin/controls`(기능 스위치·안전모드·정책 버전).

### PR3 — 감사 로그 (061–063)

지금 `audit_logs`는 해시가 붙지만 **불변 트리거가 없고, 조회를 기록하지 않으며,
검증 함수도 검색도 없다.** 해시 자체도 재현 불가능하다 — `jsonb_build_object`가
`timestamptz`를 세션 TimeZone으로 직렬화하는데 함수는 `search_path`만 고정한다.

- **061** — 재현 가능한 해시로 교체(UTC 고정 직렬화), 단조 증가 `sequence bigint`
  추가(지금은 `(created_at, id)` 정렬이라 전순서가 아니다), `economy_reconciliation_snapshots`가
  이미 쓰는 **BEFORE UPDATE OR DELETE 트리거**를 그대로 복사해 붙인다.
- **062** — 기획서 §14.9가 요구하는 상세 필드: request_id/trace_id/**세션 해시**
  (§17.10이 세션 ID 원문을 기록 금지 목록에 올렸다 — 상관에 쓸 단방향 해시만 남긴다),
  인증 수단·재인증 시각, 원본 IP(신뢰 프록시 체인 확정값 — `fa09ce8`의 결론을 재사용),
  User-Agent 파생값, 대상 종류/ID/건수, 변경 전·요청·검증 후·변경 후 값,
  정책 버전 전후, 원거래/보정거래 ID, 대량 작업의 성공/실패/제외 집계, 응답 상태.
  **민감값은 구조화된 허용 필드만 기록한다** — 비밀번호·쿠키·토큰·Client Secret 금지.
  **`privacy-document.tsx`의 보안·감사 처리 항목을 실제 기록 항목과 일치시킨다.**
  지금 방침에는 IP도 User-Agent도 없다 — 필드를 늘리면서 방침을 안 고치면 §18.6 위반이다.
- **063** — `admin_search_audit_events`(기간·관리자·기능·액션·대상·거래ID·요청ID·IP·성공여부,
  커서 페이지네이션)와 인덱스, `admin_verify_audit_chain`, 검증 결과 별도 테이블,
  **보존기간과 파기 기록**(자동 삭제가 아니라 정책에 따른 보관·파기를 기록으로 남긴다).
- 조회 감사는 Nest 인터셉터로 관리자 라우트에 건다. **볼륨이 폭증하므로**
  프론트는 반드시 페이지네이션과 limit 컨트롤을 갖춰야 한다(지금은 전부 렌더).
- 로그 화면에서 민감값은 마스킹하고, **마스킹 해제 열람 자체도 감사 행을 남긴다.**
- 인증 실패·권한 거부·정책 변경·경제 거래·계정 연결 변경을 감사 대상에 넣는다.
  지금 감사 행을 쓰는 액션 15개는 전부 관리자 쓰기뿐이다.

## 4. 실행 방식

에이전트는 **워크트리에서 코드만 쓴다.** 이 머신은 RAM 3.6GB·4스레드라
병렬 빌드가 곧 프리즈다 — `pnpm typecheck`/`lint`/`build`는 브랜치마다 직렬로 돌린다.

- **웨이브 A**: PR1 · PR2 · PR3 · PR4 — 카지노 · 관리자 권한 · 감사 · 원장
- **웨이브 B**: PR5 · PR6 · PR7 · PR8 — 백업 · Discord · 스케줄러 · 자동정책
- **웨이브 C**: PR9 · PR10 · PR11 — 작업 · 상점 · 성장
- **웨이브 D**: PR12 · PR13 — 프로필 · 흥미 유지

워크플로 동시 실행 상한은 `min(16, nproc-2)` = **2**로 CPU에서 나온다. 웨이브마다
워크플로를 2개로 쪼개 4슬롯을 쓴다. 에이전트는 병렬로 main에서 따고, 스택 조립
(브랜치 base를 앞 PR로)과 검증은 직렬로 한다.

**서브에이전트 용량은 세션 한도에 걸린다.** 감사 워크플로가 실제로 그렇게 죽었다 —
164건 중 150건의 검증이 실패했다. 웨이브 하나를 통째로 띄우기 전에 남은 용량을
확인하고, 결과를 모으는 코드는 **실패를 조용히 걸러내지 않게** 쓴다(`null` 필터가
150건을 지웠다).

## 6. 검증 게이트

PR마다 다음이 모두 통과해야 병합한다.

1. `pnpm lint` — 단독 실행(파이프에서 종료 코드가 삼켜진다)
