## Required information architecture (Spring MVC + Thymeleaf, browser website; not Android/iOS app)
- Persistent responsive navigation: Home, Wallet, **Banking**, Transfers, Cards, Investments, Quests, Shop, Community, Support, Account. Existing routes must be inventoried before adopting any suggested new route; no collisions or silent link rewrites.
- /wallet: existing canonical balances, recent activity, source timestamp, clearly labeled cash versus bank; quick actions **Send WLD**, **Deposit**, **Withdraw**, **Manage cards**. Keep a clear privacy/real-data notice and owner-scoped records.
- Proposed /banking: account overview, demand deposit and savings pockets, interest and product terms, loans/bonds with risks/limits; transaction list, filters, receipts and loading/empty/failure states. Group products by existing API capability rather than showing a fake available balance.
- Proposed /banking/transfers: recipient lookup → verified recipient preview → amount and available-funds validation → fees/limits and confirmation → CSRF and step-up if applicable → single idempotent submit → server ledger receipt with traceable transaction ID. Insufficient funds, unknown recipient, duplicate submit, stale session, rate limit, network timeout and 5xx must display true status; never announce success on timeout.
- Proposed /banking/deposits: deposit/withdraw cash↔bank, product detail with rate/basis/accrual period, maturity, early withdrawal policy, confirmation, reconciled owner ledger receipt. Pockets: create, rename/theme, fund, withdraw, archive with explicit settlement. Loans and bonds use existing authoritative terms rather than invented APRs.
- Proposed /banking/cards: **Moneyverse virtual WLD payment card** (not a real bank or Visa/Mastercard card). Show eligibility, design picker, issue request, pending/active/frozen/expired/revoked states, card controls, purchase limit and in-platform WLD payment history. Do not promise external payments, cash withdrawals or physical issuance. PAN/CVV, card credentials, physical shipping and card-network settlement are OUT OF SCOPE unless separately approved and technically/regulatorily validated.
- Card state machine proposal: requested → issued/active → frozen/unfrozen → expired/revoked. Each transition server-authorized and audited; issue/reissue and payment require a formal scoped API contract, risk review and PostgreSQL SECURITY DEFINER functions with the existing double-entry ledger. Never derive card spend from UI-only math.
