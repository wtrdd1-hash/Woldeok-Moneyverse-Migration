# v2026.09.23.398 — Work reward window/reset planning delta

> Type: planning/docs only
> Baseline: `4812a99b0a78da736e477d0a3a2f02ed4ea66283`
> Runtime deployment: not claimed

## Findings
The current Work quota surface combines finite daily/weekly WLD counters with copy that can state midnight/UTC 00:00. Runtime evidence shows the dashboard already receives `day_ends_at` and `week_ends_at` from the server-authoritative Moneyverse game clock, including accelerated-clock behavior. Therefore hard-coded reset copy can contradict the timestamps actually shown.

The product policy also says ordinary Jobs participation is unlimited by default. A finite daily/weekly WLD cap must therefore be treated as a temporary/versioned reward-issuance protection window, not as a generic work/play cap.

## Planning changes
- Canonical reset boundaries are server `day_ends_at` / `week_ends_at`.
- Daily and weekly explanatory copy must be separate and derived from the active clock policy.
- Never hard-code UTC/local midnight unless the active policy actually uses it.
- Unlimited reward policy uses `null`; no magic large number or ambiguous zero.
- Finite caps require policy version, reason class, reevaluation/expiry metadata, and a path back to unlimited.
- Work/mastery may continue when WLD reward headroom is exhausted unless an independent protection state blocks it.
- Web/mobile must use the same summary/API contract.
- Settlement/read-model/UI boundary parity is an exact-SHA Test gate.

## Required implementation follow-up
P1 runtime follow-up should update the Work summary API metadata and UI copy, then verify DB/backend/frontend boundary parity, concurrent last-headroom settlement, idempotent retries, restart continuity, responsive layout and EN/KO parity on isolated Test before Production promotion.
