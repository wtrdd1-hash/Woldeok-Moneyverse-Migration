## 3. ECON-128-01 — P0 — REDESIGN_REQUIRED — platform casino headroom is effectively unbounded policy

**Severity / first/latest evidence:** P0 economy-abuse/trust risk; first observed in PR #343 on 2026-09-15; latest reproduction is code/migration evidence at current main.

**Affected flow:** authenticated member → casino terms → repeated coin/dice plays → WLD debit/credit → casino-scoped balance/ledger → daily counters. Per-play max remains 200, but platform daily stake/loss ceilings are now near `9e18`, so the platform-level daily guard is practically unreachable.

**Risk:** this does not directly create real-money gambling because WLD is simulation-only, but it removes a meaningful platform loss/stake guard. Automated high-frequency play, compromised accounts, multi-accounting, replay/idempotency defects, reward/casino arbitrage or future balance-policy changes could accumulate extreme virtual losses/ledger volume. It can also create support/trust problems and make a nominal "daily limit" misleading.

**Required redesign:** keep the member-owned self-limit/self-exclusion as a strict user safety control; add a separate server-owned `casino_platform_risk_policy` with finite configurable `daily_stake_cap`, `daily_loss_cap`, `plays_per_minute`, `plays_per_day`, optional account-age/risk tiers, effective-from/version fields and emergency disable flag. The UI must distinguish `per-play limit`, `member self-limit`, and `platform risk cap`; it must never display 9e18 as a meaningful user allowance. Policy is server authoritative and cannot be raised by the client.

**API contract:** `GET /casino/terms` returns canonical decimal strings and machine codes; mutation endpoints return stable `409` for self-limit/platform-limit/insufficient-funds/idempotency conflict and `429` for rate/automation limits. Do not overload 409 for transport validation (400) or authorization (401/403). Retryable value mutations require idempotency keys bound to actor+operation+payload hash.

**DB/transaction:** policy/counter read, eligibility check, debit/credit ledger postings, casino balance, daily counters, idempotency record and audit/outbox commit atomically. Use row/advisory locking or equivalent serialization so concurrent plays cannot exceed a cap. Constraints reject negative/overflow-invalid counters. Migration 198 is immutable; any correction is migration 199+.

**Abuse/security:** BOLA/BFLA, replay, concurrent duplicate play, multi-account burst, bot loops, oversized numeric input, tampered outcome/stake, stale terms, clock-boundary abuse and admin policy mutation require negative tests. Detect `casino_plays_per_actor_minute`, cap rejection rate, duplicate-idempotency attempts, anomalous net issuance/sink, ledger rows/play and multi-account/device/IP correlation only where privacy/legal policy permits. Raw secrets/session IDs are never logged.

**UX/accessibility:** empty/loading/error/offline/timeout states must not imply a bet succeeded. Disable duplicate CTA while a mutation is unresolved; after timeout, reconcile by idempotency/status before allowing another value-changing request. Screen-reader text must announce stake, possible simulated result, refusal reason and updated WLD without color-only meaning. Mobile/tablet/desktop use the same server policy.

**QA:** unit boundary tests at cap−1/cap/cap+1; real-DB concurrent plays; midnight/timezone boundary; retry after network timeout; duplicate idempotency; self-exclusion; account/session revocation; 409-code localization; 429 backoff; ledger double-entry reconciliation; migration 001→199+ fresh and upgrade path; rollback to prior immutable application only while DB compatibility is proven.

**Test acceptance / Production gate:** exact-SHA Test proves finite policy, atomic cap enforcement under concurrency, no duplicate value, no misleading UI allowance, and all casino ledger postings reconcile. Production promotion is blocked if the deployed policy is near-unbounded without an explicitly approved experiment/risk record.

**Business hypothesis:** casino is a retention/economy-sink feature, not real-money revenue. Measure sessions/user, D1/D7/D30, voluntary self-limit adoption, casino WLD sink/source ratio, support contacts, rage-quit/churn after losses, abuse/fraud-like incidents and infra cost per 1k plays. `SCALE` only if retention improves without higher support/abuse/churn; `ITERATE` if engagement rises but guardrails worsen; `KILL/disable` on ledger duplication, cap bypass, material trust harm or policy ambiguity.
