## P0/P1 QA and development planning changes

### REL-122-01 — P0 — OPEN — release evidence adapter can misclassify exact-SHA CI

**First/latest evidence:** 2026-09-15. Exact SHA legacy status API is `pending` with zero statuses while exact-SHA GitHub Actions contains completed successful release workflow evidence.

**Impact:** release automation or operators that consume only `/commits/{sha}/status` can false-block a good candidate or, symmetrically, miss required Checks/Actions semantics. This weakens exact-SHA release truth.

**Fix design:** define one machine-readable `ReleaseEvidence` aggregator keyed by SHA. Required jobs are enumerated by workflow/check identity and expected GitHub App/source. Each record stores workflow/check id, attempt, conclusion, started/completed timestamps, artifact/provenance ids and SHA. `missing`, `skipped`, `neutral`, `cancelled`, `stale-SHA`, and `success` are distinct. Legacy commit status is supplemental only. A release is green only when every applicable required gate for that exact SHA is present and successful.

**Targets:** release workflow, GitHub evidence collector, release manifest/schema, admin/release dashboard. No DB migration unless evidence is persisted; if persisted, use append-only run/evidence rows with unique `(sha, gate, attempt)`.

**Tests:** zero legacy statuses + successful Actions; failed required check; cancelled rerun; workflow from wrong SHA; success from untrusted source; duplicate attempts; stale artifact; missing required gate; docs-only applicability; API rate-limit/timeout. E2E must prove candidate SHA -> required Actions/Checks -> immutable artifacts -> Test exact-SHA.

**Acceptance / promotion:** Production promotion blocks unless exact-SHA evidence aggregator is complete; empty legacy status alone can neither pass nor fail the candidate. Monitor `release_gate_missing_total`, `release_gate_stale_sha_total`, `release_gate_source_mismatch_total`.

### ECON-122-01 — P0 — OPEN — arbitrary-precision WLD expands abuse/resource and compatibility surface

**Trigger:** v121 changed core ledger/banking money columns to arbitrary-precision PostgreSQL `numeric`, public monetary requests to canonical decimal strings, and removed implementation-only amount ceilings.

**Risk scenario:** an authenticated or automated client submits extremely long canonical digit strings. Even if mathematically valid, parsing, validation, DB numeric arithmetic, JSON/OpenAPI serialization, logs, audit payloads and UI rendering can consume excessive CPU/memory/storage or create pathological values that bypass gameplay-policy assumptions. Old clients may also assume JSON numbers or safe-integer bounds.

**Required design:** separate *representation capacity* from *business policy*. Keep canonical string transport, but introduce endpoint-specific policy maxima and a transport digit-length ceiling derived from the largest legitimate game-economy value plus migration headroom. Reject leading zeros, signs, decimals, exponent notation, whitespace and over-length values before DB access. Server remains authoritative for price/loan/risk limits. Logs store normalized bounded metadata, never unbounded raw amount bodies. OpenAPI/App API contracts explicitly mark money as decimal integer strings and publish compatibility behavior for legacy safe-integer clients.

**DB/concurrency:** numeric columns may remain arbitrary precision, but value-changing procedures validate policy before arithmetic and retain row/account locking, non-negative guards, double-entry reconciliation and idempotency. Add constraints only when they encode invariant rather than mutable gameplay policy. Existing migration 193 is immutable; corrections use a new migration.

**Security tests:** 1 digit, policy max-1/max/max+1, transport max digits/max+1, 10k/1M-digit body, leading zero, `+1`, `1.0`, `1e9`, Unicode digits, JSON number above safe integer, repeated idempotency key with different amount, concurrent transfer/repay, BOLA actor mismatch, rate/resource exhaustion. Verify bounded 4xx response time and no DB query for rejected oversized input.

**Compatibility QA:** web/mobile/Discord/App API; safe-integer legacy client; canonical-string new client; OpenAPI generated SDK; large balance display; sorting/pagination/export/admin audit; no precision loss through analytics events.

**Observability:** `money_input_rejected_total{reason}`, bounded amount-digit histogram, DB numeric-operation latency, ledger reconciliation failures, idempotency conflicts, old-client numeric-request share. Never label or log raw giant values.

**Rollback:** do not downcast stored values to bigint/numeric(38,0). Roll back application acceptance through feature flag/policy ceilings while preserving numeric storage; if schema correction is needed, forward-fix with a new migration after proving all stored values fit the target domain.

**Business:** direct revenue = 0. Benefit is avoidance of fraud/abuse, DB cost spikes, support incidents and precision-loss disputes. Guardrail: no measurable P95/P99 regression or increase in fraud loss after enabling larger legitimate balances.
