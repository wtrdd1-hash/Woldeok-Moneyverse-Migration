## 확인된 화면과 미확인 원인
첨부 화면에는 지갑 카드의 큰 '실제 데이터 조회 중...', 주식의 '내 보유 종목' 및 계정 검증 안내, 퀘스트 바로가기 카드가 있다. 화면만으로 실제 폴링, API 오류, 고정 데이터, 구현 코드의 결함을 단정할 수 없다. 현재 Spring 핸들러/세션/API 응답/프론트 상태/브라우저 네트워크 실측 후 원인을 규명한다.

## 적용해야 할 UX·데이터 원칙
1. 인증된 최초 접속: REST로 원장 기반 서버 스냅샷(`revision/asOf/userScope/requestId`) 로드. 검증된 이전 데이터가 없을 때만 카드 높이 고정형 skeleton. 메인 잔액 자리에 커다란 '조회 중' 문구를 쓰지 않는다.
2. 백그라운드 갱신: 같은 회원에게 속한 **검증된 이전 값**을 유지하며 작은 최신화 표시만 제공. 로그아웃·계정 변경 즉시 비공개 캐시 삭제. 오래된 값을 실시간 값이라고 속이지 않는다.
3. 수신 성공: 해당 카드와 숫자만 변경, 권장 150~250ms 절제된 애니메이션. 수시 시세에 과도한 숫자 애니메이션 금지. 화면 전체 재마운트·깜빡임·레이아웃 이동·포커스 손실 금지. reduced motion 지원.
4. 지갑 송금·예금·보상: DB 원장 커밋과 검증된 영수증/리비전 확정 후 UI 갱신. 브라우저에서 임의 계산한 금액을 최종 잔액으로 표시 금지. WLD 정수 문자열 유지.
5. 주식 보유종목·퀘스트: `loading/ready/empty/permission-denied/stale/error`를 분리한다. 권한 실패를 '보유 없음'으로 표시 금지. 공개 시세와 개인 보유 내역 구분.
6. 연결 문제: 최소 크기의 '연결 복구 중/마지막 확인 시각'만 표시. 행동을 막는 오류 또는 현저한 정보 노후화에만 눈에 띄는 알림. 복구 후 조용히 최신화.

## 통신 설계 결정 절차
- 먼저 실제 Spring MVC/Spring WebSocket·SSE·Socket.IO, 웹 클라이언트, 리버스 프록시, 세션 구조 전수 파악. 실시간화를 이유로 Node.js나 불필요한 별도 서버를 추가하지 않는다.
- 서버→브라우저 이벤트 중심이면 Spring SSE 우선 검토, 양방향 채팅·구독·ACK 필요 시 Spring WebSocket/STOMP 우선 검토. Java netty-socketio는 프로토콜 호환성, 독립 포트/수명 관리, 인증, 프록시, 다중 인스턴스 검토 통과 시에만 대안 채택. Socket.IO와 순수 WebSocket은 동일 프로토콜이 아니다.
- REST는 최초 스냅샷·변경 요청·재검증·장애 폴백의 기준. 실시간 이벤트는 서버 권위 데이터를 갱신할 트리거이며 원장의 대체물이 아니다.
- 제안 이벤트 계약: `{eventId,type,entityId,revision,occurredAt,scope,correlationId}`. 종류: `wallet.balance.changed`, `portfolio.positions.changed`, `quest.progress.changed`, `chat.message.created`, `system.notice.published`. 이벤트 누락, 재접속, 역전 revision, 세션 변경 시 권한 검사 후 REST 재조회.
- 개인별 Room/구독에는 서버 측 본인 권한 확인 필수. 타 회원 지갑·보유종목·관리자 이벤트 브로드캐스트 금지. CSRF/Origin/Cookie/세션·Rate limit·구독 권한 테스트.
- DB 커밋 후 outbox 발행 또는 동등한 전달 신뢰성; 이벤트 중복 제거·순서 검사; 백오프·지터 재연결, 탭 복귀 시 재동기화, 다중 서버 fan-out·프록시 타임아웃 검증.
