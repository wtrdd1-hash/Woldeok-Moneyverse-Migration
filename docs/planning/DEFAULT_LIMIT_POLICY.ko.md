> 영문 기준 문서: [DEFAULT_LIMIT_POLICY.md](DEFAULT_LIMIT_POLICY.md)

## 1. 제품 기본 원칙

머니버스는 **임의의 사용자 체감 하드 한도를 기본적으로 두지 않는다.**

구현이 편하다는 이유만으로 고정 상한을 만들지 않는다. 특별한 제품·무결성 사유가 없다면 다음 항목은 기본적으로 무제한을 지향한다.

- 일반 플레이/세션 횟수
- 퀘스트 완료 횟수
- 작업 수행 횟수
- 유효한 고유 활동을 통한 시즌 성장량
- 희소하지 않은 코스메틱 구매 횟수
- 중복 보유 의미가 있는 일반 수집품 수량
- 장기적으로 성장해 보유할 수 있는 사업체 수
- 인프라가 허용하는 범위의 관심종목/저장 화면 수
- 참가 가능한 시즌 횟수
- 일반 프로필/히스토리/아카이브 보존량

임의 상한 대신 성장 곡선, 비용, 반복 보상 체감 감소, 콘텐츠 해금, 경제 가격, 매칭, 이상행위 탐지를 우선한다.

## 2. 제한이 허용되는 경우

구체적인 보호 목적이 있을 때만 제한을 허용하고 이유를 문서화한다.

1. **보안/악용 방지** — rate limit, 봇 방지, 무차별 대입 방지, 스팸 억제, 이상행위 검토 기준.
2. **데이터 무결성** — 멱등성 고유성, 트랜잭션 원자성, 정산 잠금, 중복 보상 방지.
3. **시스템 안정성** — payload 크기, 동시성, 메모리/CPU/DB 보호, 큐 backpressure, API burst 보호.
4. **시장 무결성** — 자기거래 방지, 시세조작 방지, circuit breaker, 일시적 무결성 정지.
5. **법적/컴플라이언스** — 실제 요구사항이 있는 경우에만 적용.
6. **진짜 희소성** — 실제 유한 재고를 설계하고 구매 전에 명확히 고지하는 경우.

이러한 보호 장치는 일반 플레이 성장 한도처럼 보이게 해서는 안 된다.

## 3. 기본 설정 규칙

숫자형 제한 설정이 존재한다면 명시적인 `unlimited`/`null` 상태를 지원한다. 위 보호 목적에 해당하지 않는 경우 기본값은 `unlimited`다.

`0`을 비활성과 무제한 의미로 동시에 사용하지 않는다. 예:

- `null = 무제한`
- 양의 정수 = 실제 한도 적용
- 필요한 경우 별도 `enabled` 플래그 사용

## 4. 시즌 적용 원칙

시즌에는 다음 기본값을 적용한다.

- 계정별 시즌 참가 횟수 제한 없음
- 정상적인 시즌 XP 획득에 전역 하드캡을 기본 적용하지 않음
- 임의의 일일 횟수 도달만으로 캐치업 콘텐츠를 중지하지 않음
- 비희소 반복 상품은 시즌 상점에서도 기본적으로 구매 횟수 제한 없음
- 중복 수집품에 용도가 있다면 중복 구매 허용
- 시즌 연속성 재화 이월에 임의 상한을 기본 적용하지 않음
- 랭크 참가 횟수 제한 없음
- 과거 시즌 기록은 보존 개수 제한 없이 유지

시즌 종료일, 콘텐츠 기간, 정산 잠금, 악용 방지, 1회성 고유 보상은 플레이 횟수 제한이 아니라 상태/생명주기 규칙이므로 유지한다.

## 5. 하드캡 없는 경제 밸런스

한도를 없앤다고 경제 발행량을 무제한 방치하는 것은 아니다.

경제는 다음 방식으로 조절한다.

- 반복 저가치 행동의 한계 보상 감소
- 필요 시 점진적 운영비 증가
- 동적 sink
- 시간/가치 trade-off
- 시장 가격
- 성장 조건
- 위험·유지 비용
- 고가치 보상의 비반복 목표화
- 서버 측 이상행위 탐지와 개입

기본 방향은 **사용자 천장을 만드는 대신 소프트 경제 밸런싱**이다.

## 6. 기존 기획 수치 처리

기존 문서에서 `max`, `cap`, `limit`, `일일 최대`, `상위 보상 상한`, `이월 상한` 등으로 적힌 값은 보안·무결성 목적이 아닌 이상 **기본 제품 불변 규칙이 아니라 튜닝 예시**로 간주한다.

실제 구현 시 각 기능별로 다음 중 하나를 명시적으로 결정한다.

- 기본 무제한
- 1회성 고유성 규칙
- 실제 희소성 규칙
- 보안/무결성 보호 제한

숨은 제한을 조용히 추가하면 안 된다.

## 7. UX 요구사항

실제 제한이 있다면 화면에 다음을 표시한다.

- 제한 수치
- 사용자에게 관련 있는 제한 사유
- 필요 시 현재 사용량/진행도
- 임시 제한이면 초기화/만료 시각
- 플레이 제한인지, 재고 희소성인지, 안전장치인지 구분

제한이 없다면 가짜 재고 카운터나 가짜 긴급성으로 희소성을 연출하지 않는다.

## 8. 완료 조건

새 기능은 다음을 확인하기 전까지 제품 기획 완료로 보지 않는다.

- 임의 하드캡이 기본값으로 추가되지 않았는가
- 남은 제한마다 이유와 분류가 문서화되었는가
- 필요한 곳에 무제한 설정을 지원하는가
- 악용/시스템 보호는 서버 권위로 유지되는가
- 단순 상한에 의존하지 않고 경제 영향을 검토했는가
- 영문/한국어 문서가 동일한 정책을 반영하는가

## 9. AI 조절 가능 보호 제한

무제한 기본원칙은 등록된 불변조건이 실제로 위험할 때 한시적인 AI 관리 보호 제한을 금지하지 않는다. Economy AI는 명시적 범위, 근거 요구사항, 최대 지속시간, 롤백 의미가 등록된 policy key만 조정할 수 있다.

직업 시스템에서 일반 일일 완료수와 정상 보상 완료수 제한은 기본 `null = 무제한`이다. 유한값은 더 부드러운 수단을 검토한 뒤 제한형·공개형·가역적 보호조치로만 허용한다. 컨트롤러는 유한값을 완화하고 다시 `null`로 되돌릴 수 있어야 하며 일방향 영구 강화는 금지한다.

주직업 정체성 규칙은 일일 플레이 제한과 분리한다. 슬롯 수 정책은 미래 적용 기준으로 조정할 수 있지만 기존 선택과 획득 숙련도는 별도 승인된 migration이 없는 한 grandfathering한다.

AI가 조정하는 모든 사용자 노출 제한은 사유 분류와 재평가/reset 의미를 표시해야 한다. 민감속성, 숨은 지불의사, 광고 가치, 유료 상태를 이용해 개인화해서는 안 된다.


## 10. 직업 보상 윈도우·초기화 표시 규칙

이 절은 유한 일일/주간 WLD 카운터가 자동으로 일반 플레이 규칙이라는 해석을 명시적으로 대체한다.

### 10.1 정책 분류
- 일반 직업 참여/완료는 계속 기본 무제한이다.
- 유한 `daily_cap` 또는 `weekly_cap`은 사유 분류, 적용 기간, 재평가 규칙, 완화/롤백 경로가 있는 버전 관리형 **보상 발행 보호 정책**일 때만 허용한다.
- 유한 보상 한도를 "일일 작업 제한"처럼 표현하거나 작업 수행·숙련도·비WLD 진행 자체가 막히는 것처럼 보여서는 안 된다.
- `null`을 정식 무제한 값으로 사용하고, `0`을 무제한/비활성 두 의미로 혼용하지 않는다.

### 10.2 권위 게임 시계 윈도우
- 일일·주간 카운터는 보상 정산과 동일한 서버 권위 Moneyverse 게임 시계를 사용한다.
- 일일 윈도우 종료는 `day_ends_at`, 주간 윈도우 종료는 `week_ends_at`이며 클라이언트가 별도 계산하지 않는다.
- 실제 활성 게임 시계 정책이 정확히 그렇지 않다면 UI에 "UTC 00:00", "현지 자정", "매일 자정"을 하드코딩하지 않는다.
- 주간 카드는 일일과 별개의 주간 경계를 설명해야 하며 일일 초기화 문구를 재사용하지 않는다.
- 정책/시간대 변경 시 윈도우마다 하나의 권위 경계만 존재해야 하며 중복 충전, 누락 충전, 겹치는 발행 윈도우를 만들면 안 된다.

### 10.3 필수 read model/API 계약
직업 요약 read model/API는 최소한
`daily_paid`, `daily_cap|null`, `weekly_paid`, `weekly_cap|null`, `game_day_key`, `game_week_key`, `day_ends_at`, `week_ends_at`, `clock_policy_version`, 유한 보호 한도 활성 시 reward-policy 버전/사유 metadata를 제공한다.

클라이언트는 이 권위 필드만 표시한다. 퍼센트는 계산할 수 있지만 초기화 시각이나 한도 사유를 추정·생성해서는 안 된다.

### 10.4 UX 요구사항
- "일일 직업 보상 윈도우" / "주간 직업 보상 윈도우"로 표현해 작업 자체의 금지처럼 보이지 않게 한다.
- 사용량, 남은 WLD 보상 여유, 서버가 준 정확한 다음 초기화 경계를 표시한다.
- 무제한이면 무제한 상태를 표시하고 가짜 퍼센트/진행바를 만들지 않는다.
- 유한 보호 한도면 짧은 사유 라벨과 WLD 한도 소진 후에도 작업/숙련도 진행이 가능한지 표시한다.
- 초기화 시각에는 모순을 피할 수 있도록 충분한 시간대/게임시계 문맥을 표시한다.
- 서버 시계 데이터가 stale/불가이면 임의 시각을 만들지 말고 명시적인 unavailable/retrying 상태를 보여준다.

### 10.5 정산·동시성 불변조건
권위 정산 트랜잭션은 read model과 동일한 day/week key와 cap을 다시 검사한다. 마지막 잔여 한도에 대한 동시 완료, 재시도, 멱등 replay가 cap 초과나 중복지급을 만들면 안 된다. 요청 중 reset 경계를 통과하면 하나의 canonical 서버 시각/정책 버전으로 판정하고 감사 가능해야 한다.

### 10.6 QA 게이트
day/week 경계 -1초/정각/+1초, 가속 게임시계, timezone/display 변환, 정책 버전 변경, 서버 재시작, stale client, 마지막 잔여 한도 동시정산, retry/idempotency, unlimited/null 렌더링, 유한 한도 사유 표시, 영/한 문구 정합을 검증한다. 정산 경계와 화면 초기화 경계가 다르면 Production 승격을 차단한다.
