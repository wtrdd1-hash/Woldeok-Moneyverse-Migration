## 1. 기획 목적과 현재 구조의 관계

국고를 단순 보관함이나 관리자용 수치 카드가 아닌 **실제 WLD 거래에 연결되는 국가 재정 운영 기관**으로 구성한다. 국고 수입, 지출, 복지, 예산, 국채, 국가투자, 공기업, 연금, 은행, 중앙은행, 조폐국, 금융결제, 무결성 검증 및 국민 공개 기능을 하나의 경제 생태계로 연결한다.

현실 한국의 국고·한국은행·조폐공사, 미국 재무부와 연준, IMF, BIS, 노르웨이 국부펀드 등을 참고하지만 머니버스 WLD는 **가상 게임 화폐**다. 대한민국 원화, 법정화폐, 예금보호 대상 자산이나 정부 보증 상품으로 홍보하면 안 된다.

기존 v523 중앙은행/조폐국/국고 분리, v542 금융 통화량 불변식, 국고코어 v1618.2, 금융 무결성 코어 v1701을 **재사용**한다. 이미 main에 반영된 2026-11-05 국부펀드 처분, 공기업 배당, 국민연금 지급 코드는 중복 구축하지 않고 실제 배포 커밋·DB 전표·영수증을 점검한다. 과거 미검증 지급 기록은 새로운 거래로 소급 위조하지 않는다.

모든 기능에는 계획(PLANNED), 소스 구현(SOURCE_IMPLEMENTED), 단위시험(UNIT_TESTED), 복원DB검증(ISOLATED_DB_TESTED), 공식Test검증(OFFICIAL_TEST_VERIFIED), 실제운영검증(PRODUCTION_VERIFIED), 과거미검증(LEGACY_UNVERIFIED) 상태를 표시한다. **기능 버튼이 보이거나 서비스가 켜진 것과 돈이 실제 이동한 것은 다르다.**

## 2. 국가기관 구성과 권한

| 국가 경제기관 | 담당 기능 | 절대 금지 |
|---|---|---|
| 국가재정·중앙국고(CT) | 세금/수수료 징수, 회계, 예산 배정, 보조금, 복지, 공공사업, 국채 재원 관리, 재정 공개 | WLD 신규 발행, 재원 없는 지급, 사용자 잔액 직접 수정 |
| 중앙은행(MCB) | 금리·통화량·경기진단, 발행/소각 정책과 한도, 유동성 안정, 금융기관 감독 모델 | 국고 세금 임의 지출, 유저 잔액 직접 입금 |
| 국가조폐국(MMB) | 승인된 발행·환수·소각 명령의 실행과 인증서 발행 | 자체 발행 결정, 수혜자 임의 지정, 승인 없는 WLD 생성 |
| 경제결제·금융무결성 코어(ECSL) | 복식부기 원장·계좌·증빙·출납·회계 대사·정산·재시도 관리 | 통화·재정 정책 임의 결정, 누락 데이터 자동 조작 |
| 국가 금융결제·은행 | 예금·송금·대출·이자·담보·은행유동성·결제완결 | 원장과 별개인 숨은 돈 생성, 통제되지 않은 대출 |
| 국채·국부펀드·공기업·연금·보험 | 실제 부채와 자산, 재원 있는 투자·배당·연금·보험금 | 평가수익이나 가상 자산을 국고 현금으로 착각 |
| 경제감사·국민공시 | 대사 결과, 원장 증거, 부정 징후, 예산·재정위험 보고 | 원장 무단 수정, 문제 은폐 |

관리자 운영은 **기존 사용자 지시에 따른 슈퍼관리자 1인 결재 구조**를 유지한다. 예전 기획서의 2인 결재(Quorum)는 부활시키지 않으며, 15분마다 반복되던 별도 재인증 절차도 우회적으로 재도입하지 않는다. 유효한 관리자 로그인 세션, 역할 검증, 일회성 CSRF, 이유 기록, 위험별 한도, 불변 감사로그, DB 금융 권한 검사는 유지한다. 추가 보안정책 변경은 명시적 별도 결정사항이다.

## 3. 국고 통합계좌(TSA)와 금고 계층

IMF의 Treasury Single Account와 한국은행 국고 운영을 참고한다. **하나의 통합 국고 관리 화면**을 제공하되 보안상 별도 계좌 및 용도별 금고를 유지할 수 있다. 실제 원장은 기존 Economy Core 하나다.

- **실제 국고 현금(TREASURY_POSTED_CASH)**: 소유권이 국고에 속하고 원장 입금이 검증된 현금의 합계.
- **승인 예산(BUDGET_APPROPRIATED)**: 사업별 사용 승인 한도이며 입금 행위가 아님.
- **집행 약정(TREASURY_COMMITTED)**: 기존 현금에 대해 예약한 지급액. 한도를 초과해서 중복 예약 불가.
- **보호·용도 제한(TREASURY_RESTRICTED)**: 실제 국고 자금 중 비상/복지 등에 별도 지정한 현금. 별도 소유 에스크로와 이중 계산 금지.
- **가용액(TREASURY_AVAILABLE)**: 이미 입금된 현금에서 약정액과 용도제한 금액을 중복 없이 뺀 금액. 증빙 불명확하면 0이라고 확정하지 않고 미검증 처리.
- **예상 세입(TREASURY_FORECAST)**: 미래에 거둘 것으로 예상한 세금·배당이며 당장 지급 가능한 돈이 아님.
- **국채 부채(DEBT_OUTSTANDING)**, **연금의무(NPS_LIABILITY)**, **국부펀드 평가액(SWF_ASSETS)**은 국고 보유 현금과 별도 분류.

현재 VAULT_MAIN 및 다른 금고를 원장 계좌에 연결하는 정합성 매핑부터 수행한다. 이전 기획의 2,500만 WLD 준비금과 30% 보호준비금은 **정책 버전과 실제 재원 증빙이 필요한 조건부 유동성 정책**이다. 잔액이 0인데 강제로 목표액을 만들거나 발권으로 메우지 않는다.

금고마다 소유기관, 자금 출처, 지출 가능 목적, 제한 여부, 현재 실제 잔액, 사용약정, 연결된 원장 전표, 검증 시각 및 책임자를 기록한다. 국고로 지급됐다고 적힌 기록만으로 원장을 작성하면 안 된다.

## 4. 국고 수입 및 세금 엔진

### 4.1 세입 종류

거래세(주식·시장), 마켓 판매세, 소비세, 기업 이익세, B2B 거래세, 정책이 허용한 송금세, 수수료·벌금, 공기업 실제 배당, 국유자산 매각, 국부펀드 **실현** 수익, 환급금 회수 등. 국채 판매 대금은 **세수가 아니라 정부의 부채 조달**로 별도 기록한다.

### 4.2 세금 발생→수납의 7단계

1. 실제 거래 완료 이벤트를 식별한다. 사용자가 보낸 세율·계좌·거래종류 값을 그대로 신뢰하지 않는다.
2. 거래 시각에 유효했던 세율·면세·감면·최소/최대금액·정책 버전을 고정한다.
3. 거래 확정금액을 기준으로 정수·basis point 단위 계산을 한다. 예: 세액 = floor(실제 과세금액 × 세율bp / 10000).
4. 사용자/기업의 실제 원장 계좌에서 세액을 차감하고 해당 국고 계좌에 동일 금액을 입금한다.
5. 거래 원금과 세금까지 모두 복식부기 균형을 맞춰 한 DB 트랜잭션에서 확정한다.
6. 고유 거래 ID, 과세종류, 총액, 실수령액, 세액, 세율 버전, 거래원장 ID, 영수증을 남긴다.
7. 정기 대사에서 원거래·세액·국고입금·취소/환급 기록을 독립 검증한다.

동일 과세 이벤트와 세금 코드가 중복 호출되어도 세금은 한 번만 징수한다. 이미 확정된 거래는 삭제가 아니라 원거래를 가리키는 **반대 방향 보정 전표**로 환급한다. 과거 세금에 새 세율을 소급 적용하지 않는다.

세율 운영: 기존 계획 v323의 0~10% 범위와 일반적 7일 유지 원칙을 최신 권위 문서와 대조하고, 기준 거래량·물가 지표·실사용자 영향·예상 세입을 시뮬레이션한 후 새 버전 발효일을 지정한다. AI가 스스로 세금 명세를 조작하지 않는다.

## 5. 국가예산·국고지출·복지 정책

### 5.1 예산 편성과 승인

현실 dBrain+처럼 재정기간 → 프로그램 → 사업 → 세부 예산 → 수혜 대상 → 지급 약정 → 실제 집행 → 회계 결산 → 성과 평가로 설계한다. 사업별 책정액, 재원, 집행계획, 보유현금, 이미 사용한 금액, 예약액, 남은 금액, 승인자, 정책판본, 수혜 기준, 재정 효과를 관리한다.

지출 계층:
- 국고 징수 오류와 결제 피해 보상 등 **확정된 환불·복구**
- 실제 활동으로 지급이 발생한 **보상·공공수당**
- 자산·활동 조건이 증빙된 **복지·신규 사용자 정착 지원**
- 실제 잉여 재원에서만 실행하는 **시민 배당**
- 커뮤니티 공공 프로젝트·도시 기반시설·일자리 보조금
- 공개시장 안정화용 **실제 자금의 유동성 공급**
- 비상기금과 국가 재난·사고 대응
- 국채 이자 및 만기상환, 계약상 지급의무(원금·이자 모두 재원 필요)

지출 우선순위는 생계·정산 복구와 확정 부채부터 검토하고, 그 뒤에 임의 배당·지원금을 집행한다. 매 지급에는 부당 중복수혜 방지, 1인 상한, 지급 빈도, 정책상 제외, 이의신청, 부정수급 복구 등 세부 규칙을 둔다.

### 5.2 국고 지급 상태기계

DRAFT(기안) → SIMULATED(모의계산) → AUTHORIZED(단독 관리자/한도 내 자동정책 승인) → ENCUMBERED(자금 예약) → SETTLING(실제 원장 정산) → SETTLED(모든 해당 영수증 확정) → RECONCILED(독립 대사 완료).

예외 상태는 REJECTED(거절), CANCELLED_BEFORE_SETTLEMENT(미집행 취소), RETRY_PENDING(아직 미지급인 개인만 대기), QUARANTINED(증빙 불일치), REVERSED(새 보정 전표 완료)로 분리한다.

**실행 방법:**
1. 사전 모의계산에서 수혜자 목록 스냅샷, 지급액, 총액, 지출 후 국고잔액, 정책 버전, 원장 고수위 지점을 고정한다.
2. 슈퍼관리자 1명이 유효한 로그인 상태에서 사유와 금액을 확인해 승인한다. 이중 승인 절차를 요구하지 않는다.
3. 국고 실제 가용 현금이 충분한지 DB 잠금으로 판단한 뒤 예산 지급 약정을 원자적으로 예약한다.
4. 각 수혜자마다 지급 의도 ID, 요청 해시, 지급 전·후 잔액, 실제 원장 전표 및 불변 영수증을 하나의 DB 트랜잭션에서 확정한다.
5. 대량 지급의 일부 실패 시 성공한 수혜자에게 다시 지급하지 않는다. **영수증이 없는 미지급 대상만** 재시도한다.
6. 알림은 금전 정산 완료 후 이벤트 아웃박스로 처리하고, 텔레그램·디스코드 장애가 잔액을 되돌리거나 중복 지급하게 해서는 안 된다.
7. 운영자가 이미 지급한 금액을 취소해야 한다면 새로운 상쇄·회수 전표를 만들고 실제 회수 가능 금액과 권한을 검증한다.

**예시:** 국고에 실제 100 WLD가 있다. 시민에게 40 WLD를 지급하면 국고 -40, 시민 +40으로 하나의 복식부기 거래가 생성된다. 통화량 증가량은 0이다. 국고가 0이면 40 WLD 지급을 실행하지 않고 **재원 부족**을 정확하게 알린다.

가상국고의 부채나 미지급금을 한 번에 미지급자 지갑에 더해서 해결하지 않는다. 수혜자 500명 중 299명이 지급 확정된 뒤 장애가 발생한 경우, 재시작 시 299건의 전표와 영수증을 확인하고 나머지 미지급 건만 결제한다.

### 5.3 이용자에게 제공하는 기능

수당 신청·심사 상태, 신청 자격 설명, 국고 환급 예정/정산완료, 시민 배당 내역, 공공사업 지원, 지원금 한도, 원장 영수증 확인, 지급 지연 사유, 이의신청·복구 요청, 내역 CSV 내보내기(민감정보 제한) 등. 신청/승인과 돈 입금 완료를 혼동하지 않는다.

## 6. 중앙은행의 통화정책 기능

경제 상태를 측정하는 **경제정책 분석실**을 구성한다. 총발행·총소각·실제 유통 WLD, 이용자/기업/국고/은행/잠금 자금 분류, 경제활동 빈도, 가격지표의 표본 신뢰도, 상위 자산 집중, 금융기관 유동성, 국채 부담, 실업 또는 활동 둔화 지표 등을 분석한다.

실제 한국은행과 미국 연준처럼 금리·공개시장·준비금 개념을 게임경제에 적용하되, 그 자체로 WLD가 무한 발행되지 않도록 한다.

### 통화 정책 명령

명령에 고유 UUID, 명령 종류(MINT·RETIRE·FREEZE·RESUME), 최대 규모, 사용 가능 사유, 자금 도착 대상, 유효기간, 정책판본·서명, 승인 관리자, 통화량 시뮬레이션 결과, 정산원장 기준점, 이미 집행한 수량과 잔여 한도를 저장한다.

중앙은행은 새 통화량의 상한과 조건을 승인하며 **조폐국에만 집행명령을 전달**한다. 조폐국은 명령 위조·기한 만료·과한 발행·중복 집행·회계 불일치를 거부해야 한다.

조폐국 발행 절차: 명령 확인 → 유효기간/권한/한도 확인 → 같은 사건 중복 검사 → 계정 잠금 → MINT 원장 분개 → 화폐발행 증명서/감사 증거 → 아웃박스 → 확정. 전표가 실패하면 인증서도 없는 상태로 원자 롤백한다. 단순 기념주화·화폐 디자인 제작은 WLD 발행과 무관하다.

### 금융 불변식

- 각 거래의 모든 원장 차변·대변 합은 항상 0 (MINT/SINK 특수계정 포함).
- 미상환 통화량 = 검증된 기초 공급 + 증빙 있는 신규 발행 - 증빙 있는 폐기.
- 국고 이동, 세금 징수, 시민배당, 은행 간 송금, 국채 원금결제는 별도 인증된 발행/소각이 없으면 **통화량을 변경하지 않는다**.
- 조폐국 인증서 발행량 합계는 해당 중앙은행 명령 한도를 넘을 수 없다.
- 국고 부족, 연금 부족, 국부펀드 평가손실은 자동으로 발권하는 근거가 되지 않는다.

발행이 필요하다면 정책 승인과 경제적 영향 모의계산, 정확한 지급 목적, 상한, 원장과 인증서 동시 생성, 공급량 대사, 사후 공개가 모두 필요하다.

## 7. 국가 금융시장 연동 기능

### 은행

예금계좌, 입출금, 은행 간 송금, 이체 대기·완료, 대출, 담보, 만기, 이자, 연체, 지급제한, 결제완결 시점, 은행 유동성을 설계한다. 은행 내부 계좌와 유저 지갑 잔액은 단일 원장의 서로 다른 계정이지 서로 다른 독립 통화량이 아니다. 신용·대출 방식은 별도 건전성 정책과 자금 출처 증빙을 요구한다.

### 국채

국채 공고(금액, 만기, 쿠폰, 위험), 청약·입찰, 배정, 원금 수납, 증권원장, 이자 발생, 이자 지급, 만기 원금상환, 중도 매매/환매조건부 계약, 부채 잔액, 상환 재원 검사. 미국 TreasuryDirect의 공고→입찰→발행 절차를 참고한다. **청약금 입금은 정부 부채 증가를 동반**한다. 이자가 발생했다고 국고 밖에서 WLD가 생겨서는 안 된다.

### 국부펀드

국고 실제 출자→투자 가능 금액 예약→주식·채권 자산매입→평가손익 보고→매도 정산→실현 자금→국고 이체/재투자. 노르웨이 GPFG를 참고해 운용 권한, 투자 한도, 손실 한도, 성과지표와 감사를 분리한다. **기업가치 1억 증가와 국고 현금 1억 증가는 다르다.**

### 공기업

공기업별 실제 매출·원가·세금·금융비용·투자·지분·배당가능 현금을 구분한다. 기업의 가상 수익률로 계산한 예상 시간당 배당은 **수익 예상치**로만 표시하고, 실제 잉여자금 원장과 분개가 확인되어야 국고에 입금된다.

### 국민연금·보험기금

국민연금은 납입액, 납입 영수증, 소유권이 분명한 에스크로, 급여산정, 지급 예정, **실제 지급 가능한 적립금**, 인출/지급금, 유족·복지 관련 정책, 과거 미검증 급여를 분리한다. KDIC 형태의 금융보호는 보험료 납입, 보험기금, 가입 대상, 지급사유, 1인 보장 한도, 손해 회수까지 포함한다. **기금 부족이면 지급 완료로 속이지 않고 미지급 채무/대기 상태로 관리**한다.

### 외환·CBDC 장기 연구

국가외환보유고·외화거래·CBDC·오프라인 결제는 별도 기획 후보로 제한한다. 실제 법정화폐나 한국은행 CBDC처럼 표시하면 안 된다. 오프라인 WLD 거래는 이중지불 방지, 기기 신뢰, 한도와 재접속 대사가 검증되지 않으면 지원하지 않는다.

## 8. 원장 및 데이터베이스 설계

### 기존 코어 재사용

accounts, account_balances, ledger_transactions, ledger_postings, outbox_events, economy_post_transaction, treasury_core_receipts 및 금융무결성 증빙, 기존 국고/연금/국채/국부펀드 저장구조를 먼저 검사한다. **국고 원장, 은행 원장, 지갑 원장을 서로 독립적인 진실 DB로 만들지 않는다.**

실제 스키마에 없을 때만 제안하는 보조 테이블: treasury_budget_versions(예산판본), treasury_commitments(지급약정), treasury_disbursement_batches(지급 묶음), treasury_disbursement_items(개인별 지급 의도·영수증), treasury_source_evidence(세입증거), treasury_cash_forecasts(전망), treasury_reconciliation_runs(대사), monetary_order_consumptions(발행명령 집행 잔여량).

대형 금액은 PostgreSQL NUMERIC을 정본으로 사용하고 API는 정확한 **십진수 문자열**로 전달한다. JavaScript Number·부동소수점을 잔액 계산에 사용하지 않는다. 필요하면 JSONB의 10^9 단위 청크를 표시·전송에 활용하되, 청크마다 별도 잔액 정본을 만들면 안 된다. UUID 사건 ID, idempotency_key, 요청 해시, 정책 버전, 출처 원장 ID, 시간대, 사업 연도, 수혜자 ID, 감사 서명, 변경 금지 제약을 적용한다.

### 거래 순서

웹/안드로이드 → Next 동일 출처 BFF → Nest 인증 세션·RBAC·CSRF 검증 → 내부 DB SECURITY DEFINER 도메인 명령 → economy_post_transaction → 불변 도메인 영수증·Finance Integrity 증빙·아웃박스 **한 트랜잭션** → 검증된 결과 반환.

앱 DB 계정과 PUBLIC에는 금전 계정·원장·금고·연금·민감 증명서의 원시 INSERT/UPDATE/DELETE 권한을 부여하지 않는다. 앱은 제한된 기능별 저장 프로시저만 EXECUTE한다. 외부 인터넷에서 코어 내부 API를 직접 호출할 수 없어야 한다. 동일 키의 같은 요청은 동일 영수증을 반환하고 키만 같고 내용이 다르면 충돌로 거부한다.

모든 이동에서 거래 전·변화량·거래 후 금액, 양쪽 계좌, WLD 단위, 정책판본, 원장 트랜잭션, 이벤트 아웃박스, 감사지문을 저장한다. 실패 시 일부 기록만 남지 않도록 전체 롤백한다. 단일 DB 안의 SHA-256만으로 DB 최고권한자 위조를 완전히 방어할 수 없으므로 외부 서명·독립 백업 검증을 요구한다.

## 9. 금융 불일치·장애·복구 기획

대사 항목:
1. 거래별 복식부기 합계 0.
2. 각 계좌의 시작금액 + 전표의 순변화 = 종료금액.
3. 계좌 잔액과 해당 시점까지 모든 원장의 일치.
4. 국고 현금, 세입/세출·약정·배당 영수증의 일치.
5. 전체 WLD 공급량과 발행/소각 인증서의 일치.
6. 국채 부채·투자자 채권 및 원금·이자 지급의 일치.
7. 연금·보험 적립금·약정·수급 내역의 일치.
8. 은행 대출, 담보, 이자, 유동성의 일치.
9. 국부펀드 평가액, 실현 수익, 국고 이체의 중복 없는 일치.

제안 운영주기: 금융이벤트 즉시 증빙 검사, 시간당 부분 대사, 매일 독립 전체 대사, 정기 백업 독립 복원. 이는 **새 설계안**이며 현재 예약작업 실행 여부를 주장하지 않는다.

**정상 상태:** PASS, VERIFIED_EMPTY(정상 검증된 잔액 0). **데이터 누락:** UNKNOWN, STALE. **진짜 불일치:** DRIFT. **과거 미검증:** LEGACY_UNVERIFIED. **사고 조사 중:** QUARANTINED.

국고 실제 잔액 0은 결함이 아니다. 비율 분모 0은 N/A로 표시한다. 그런데 DB 접속 오류나 대사 누락은 0이라고 표시하지 않는다. 정상 대사가 끝나면 해당 경고를 해제하고, 영수증이 없으면 사용자의 실제 입금 여부를 확정됐다고 표현하지 않는다.

불일치가 발생하면 관련 **신규 고위험 지급 경로만** 멈추고 정상 검증된 읽기 기능과 관련 없는 기능은 유지한다. 사고 시작 원장을 찾고, 증빙·백업을 봉인하고, 격리된 복원 DB에서 재현하고, 필요한 경우 근거 있는 **새 보정 거래**를 만든다. DB 강제 0 맞추기, 운영 데이터 초기화, 누락 지급 위조, 과거 거래 삭제는 자동 복구로 실행하면 안 된다.

두 번째 디스크는 DB 저장과 백업 역할을 안전하게 분리하되 **원장 정본이 두 개로 갈라지지 않도록** 한다. WAL·fsync, 백업 시각, 복원 무결성, 모의 장애, RPO/RTO 실측이 필요하다. 개발 DB의 0.0.0.0:5433 바인딩은 별도 네트워크 보안 확인 대상으로 적고 현재 수정됐다고 주장하지 않는다.

## 10. 세부 API·관리자·일반 사용자 화면

아래는 신규 구현 시 검토할 **제안 API**다. 기존 실제 라우트와 충돌하거나 중복되면 기존 계약을 우선 수정한다.

- GET /api/v1/treasury/public-overview: 국고 현금·약정·지출·증빙시각·검증상태.
- GET /api/v1/admin/treasury/revenue, /budgets, /commitments, /disbursements: 세입/예산/약정/결제 조회.
- POST /api/v1/admin/treasury/budget/preview: 시뮬레이션만.
- POST /api/v1/admin/treasury/budget/authorize: 세션기반 관리자 승인.
- POST /api/v1/admin/treasury/disbursement/settle: 실제 재원 검증 및 정산.
- GET /api/v1/admin/treasury/reconciliations: 원장 증빙 및 오류.
- GET /api/v1/admin/central-bank/summary, /orders: 통화정책/명령 조회.
- POST /api/v1/admin/central-bank/orders/preview, /authorize: 발권 사전평가·승인.
- POST /api/v1/internal/mint/execute: 내부 전용 발행 집행; 외부 공개 금지.
- GET /api/v1/me/fiscal-benefits: 본인 지원금·지급 영수증.

응답 상태는 VERIFIED, VERIFIED_EMPTY, PENDING, DENIED, POLICY_LIMIT, REPLAY_CONFLICT, PROOF_UNAVAILABLE, STALE, LEGACY_UNVERIFIED를 구분한다. 503을 빈 배열이나 잔액 0으로 변환하지 않는다.

**관리자 11개 화면:** 국고 개요, 세입·세금, 예산편성, 지출·지원금, 국채·부채, 국부펀드·공기업, 국민연금·보험, 중앙은행 통화정책, 조폐국 발행·소각 인증서, 원장 일치·감사, 장애·동결 제어. 공통으로 실제 금액/예상액/약정액·정책버전·출처·검증시각·마지막 성공 거래를 보여준다.

**이용자 화면:** 공개 국고 현황 및 최근 정산된 공개 지출, 세금이 포함된 거래 상세, 복지 신청 자격과 상태, 내 국고 지급·환급 영수증, 국채·연금·보험 계좌와 실제 지급 여부, 최신 데이터 기준시각, 오류 문의. 다른 사용자 개인정보와 내부 계정 증빙은 공개하지 않는다. 모바일 안드로이드도 동일한 정확한 WLD 문자열·인증·계정 전환·캐시 정책을 사용한다.

## 11. 경제 분석과 AI 정책 기능

국고 수입과 지출, 확정현금과 사용약정, 재정 적자·부채, 7/30일 수입전망, 사업별 집행률, 실제 수혜자 수, 과세 부담, 가격지표 표본, 소비·투자 유통속도, 자산 분포, 통화 발행/소각 및 투자 실현손익을 관제한다. 표본 부족이나 누락 시 경제성장·인플레이션 수치를 임의 만들어내지 않는다.

AI는 정책 수정이나 복지·예산 배분을 **추천·모의계산**할 수 있다. 추천에는 데이터 품질, 시나리오, 위험, 배분효과, 정책판본, 적용 한도, 되돌림 방법을 표시한다. AI 단독 발권, 국고 지급, 무제한 자동 증액, 원장 수정은 금지한다. 고위험 기능 이상 발견 시 신규 거래를 일시정지하는 방어적 제어는 허용 가능한 별도 정책 후보이지만 정상 확인 없이 자동 해제하지 않는다.

시뮬레이션에는 국고 0 WLD, 세수 감소, 세금 환급 급증, 은행 인출 집중, 국채 만기 집중, 연금 지급 재원 부족, 국부펀드 폭락, 이벤트 중복, 서버 중단, DB 장애, 오래된 프론트 캐시, 관리자 세션 교체, 통화량 변조 시도를 포함한다.

## 12. 구체적인 개발 순서와 시험 조건

| 단계 | 작업 범위 | 완료 판정(반드시 실제 시험) |
|---|---|---|
| P0-1 | 최신 실행 SHA/DB 권한·기능 목록·기존 과거 불일치 검증 | 읽기 전용 조사, Test/운영 DB 대상과 시점 구별, 원본 백업 |
| P0-2 | 국고 실제 현금 분류와 Finance Integrity 연결 | 복원 DB 대사, 0 WLD 정상표시, 20자리 이상 WLD, 100회 중복·동시 요청, 권한 위조 거부 |
| P0-3 | 세금 징수→예산 예약→다수 이용자 지급 | 부족재원·환급·서버 중단·대상자 일부 실패·재시도에서 중복 입금 0 |
| P0-4 | 관리자·공개·회원·모바일 지급영수증 연동 | 세션·CSRF·no-store·정확한 실패/정상 0/미검증 표시 확인 |

코드를 실제로 변경할 때는 별도 브랜치·개별 RED/GREEN 테스트·최신 main 재확인·양언어 작업로그·내부/GitHub 업데이트·공식 Test 동작 확인 뒤 운영승격한다. **v1912는 이번에 기획 문서만 작성한다.** 미승인 금융거래를 테스트라며 운영에서 수행하지 않는다.

## 13. 채택 전 확정해야 할 사항

예산별 상한과 우선순위, 조건부 준비금 계산과 비상해제, WLD 표현 정밀도, 세율별 유예기간, 개인 복지 수혜 기준, 국채·연금 지급 계약과 한도, AI 자동제안 범위, 민감정보 공개 정도, 대사 및 백업 주기를 세부 정책으로 결정해야 한다. 현실 기관을 그대로 복제하기보다 **서비스가 실제로 정산 가능하고 이용자에게 정확히 보여주는 설계**를 우선한다.
