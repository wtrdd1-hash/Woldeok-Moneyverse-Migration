## 1. 사용자에게 보장하려는 최종 상태

### 1.1 일반 회원
1. 송금/구매/정산/주식 주문/국채 상환/PvP/대출상환을 실행하면 결과가 **확정 성공·확정 실패·정산 확인 중** 가운데 하나로 표시된다.
2. 성공 시 서버가 생성한 불변 거래 식별자, 금액, 계좌 변동, 시점, 해당 기능명 및 원장 상태를 확인한다. 요청만 접수됐거나 화면 토스트만 뜬 상태를 성공으로 표시하지 않는다.
3. 타임아웃 후 동일 버튼을 다시 눌러도 하나의 멱등 키가 한 번의 경제적 결과에만 연결되어야 한다. 상태 불명이면 조회 화면으로 전환하고 자동 재결제를 하지 않는다.
4. 금액은 서버/API/저장소까지 정확한 정수 문자열이나 BigInt로 처리한다. 2^53을 초과하는 자산을 JS Number로 자동 변환하지 않는다.
5. 신용등급에는 사용자별 검증 가능한 실제 활동 데이터만 적용한다. 신뢰 가능한 이력이 없으면 **계산 불가/예시 시뮬레이션**이라고 명확하게 표시한다.
6. 사용 불가 기능은 버튼 제거가 아니라, 접근권한·유지보수·잔액 부족·정산 보류 사유와 복구 가능한 다음 행동을 표시한다. 단, 정책상 공개하지 않아야 할 보안 임계값은 감춘다.

### 1.2 관리자
1. 국고 화면은 원장과 금고의 서로 독립적인 수치를 비교한 뒤에만 `RECONCILED`라고 표시한다.
2. 차액이 0이 아니면 `DISCREPANCY`, 검증 DB/쿼리 실패면 `UNAVAILABLE`, 비교 시작 전이면 `PENDING`, 기준 데이터가 부족하면 `INCOMPLETE`를 표시한다. 최근 검증 시각·원장 high-water mark·정책 버전·금고 원천 시각을 함께 제공한다.
3. 검증 불가/불일치 시 고위험 자동 보조금·불명확 지급·발행은 멈추고, 기존 잔액 열람·고객 지원·검증용 읽기 기능은 유지한다.
4. 관리자 변경 명령은 권한 검사, 2차 인증(step-up), CSRF, 요청 목적/사유, 멱등 키, 불변 감사 영수증 없이는 실행되지 않는다.

### 1.3 방문자·해외 사용자
1. 한국/미국/일본/중국의 금융 정보는 단순 번역문이 아니라 관할 법·세제·통화·시차·근거 날짜가 다른 **현지 독자용 글**이어야 한다.
2. KR/EN/JA/ZH의 실제 HTML 제목·요약·언어·정규 URL·대체언어 링크·sitemap이 각자의 컨텐츠와 일치해야 한다.
3. 가상 WLD와 실제 금융 정보, AI 생성 요약과 검수된 원고, 계산 예시와 보장된 결과를 혼동시키지 않는다.
4. 운영 중지, 발행 실패 또는 SEO 색인 미완료를 성공·상위 노출처럼 꾸미지 않는다.

### 1.4 운영자
운영 배포는 동일 소스 SHA의 프론트/백/DB 스키마·마이그레이션 출처와 이미 로그인된 사용자 세션 보전, 자동잡 단일 소유, 금액 무결성, 최신 백업 복원 및 장애 시 즉시 되돌리는 절차까지 재현할 수 있어야 한다.

## 2. 전체 아키텍처 개편 방침

**회원/앱 → 프론트 BFF(인증/CSRF) → 백엔드 도메인 서비스 → 제한된 SECURITY DEFINER 명령 → 동일 DB 트랜잭션의 계좌·전표·도메인 상태·Outbox·감사 → 영수증** 구조를 모든 금융 기능에 일관 적용한다.

- **금액 변동 단일 진입점:** 앱/관리자는 원시 원장 작성 권한을 받지 않는다. 인증된 서버 도메인 명령만 actor+거래 목적+사전검증된 idempotency key로 제한 SQL 함수를 호출한다.
- **역사적 SQL 복사 금지:** `001-economy-core.sql`은 초기 설계 참고이며, 뒤 마이그레이션에서 `ledger_postings`의 필드 등이 변했다. 먼저 운영/복원본 실 스키마를 확인하고 이를 기준으로 명령 어댑터를 설계한다.
- **삼중 독립 대사:** (A) 원장 분개↔계좌 잔액, (B) 국고 재정 전표↔금고/약정/시스템 계좌, (C) 총 WLD 공급량↔승인된 조폐/소각 증명서. 같은 쿼리 결과를 좌우로 복제하는 행위 금지.
- **동일 스냅샷:** 독립 비교 항목은 같은 DB 트랜잭션 스냅샷 또는 동일 원장 상한 식별자까지 잘라 비교한다. 동시 거래 때문에 생긴 시차를 실제 불일치로 오탐하지 않도록 한다.
- **단계적 권한 축소:** 새로운 도메인 함수를 먼저 제공하고 호출 코드를 전환한 뒤, 복원 Test에서 성공/거부 사례를 통과하면 마지막으로 기존 앱 권한을 회수한다. 세션 저장소의 필수 제한된 쓰기 권한까지 무분별하게 없애지 않는다.
- **불변 금융기록:** 거래·감사 기록 삭제/조용한 수정 금지. 과거 결손은 격리된 원장 대사 사건으로 기록하고, 승인한 경우 별도 상계·정정 전표로 처리한다. 금고가 부족하다고 임의 WLD를 발행하지 않는다.
- **백그라운드 작업:** v697 신·구 백엔드 간 자동뉴스/시세/Outbox/SWF 작업 주체를 내구성 있는 lease/epoch·멱등 실행 기록으로 하나만 인정한다.
- **기능 상태 진실성:** 기능을 `설계/구현/테스트 검증/운영 확인/일시중지/검증 불가` 등 별도 상태로 관리하고 관리자 API 관제, 실제 메뉴, 지원/공지 문구와 일치시킨다.

## 4. 도메인별 상세 수정 원칙

### 4.1 계정·OAuth·세션·2FA
- 실제 인증 provider 콜백, 세션 생성/갱신/회수, 미성년/동의, 관리자 역할, 재인증(step-up), 로그아웃 및 타 기기 상태를 확인한다.
- `/app-api/v1/account/identities` 미로그인 401은 정상이나 로그인 후 200/데이터 범위는 별도로 검증한다.
- 회원 A가 회원 B 자료를 읽거나 수정하는 요청, 관리자 기능에 회원 쿠키로 접근하는 요청, CSRF 누락, 인증 중간 실패, 시스템 재시작 후 기존 쿠키 유지, 2FA 만료를 음성 테스트로 만든다.

### 4.2 지갑·국고·중앙은행·발행/소각
- 이용자 보유 WLD, 계좌 예치, 국고 재정 금고, 중앙은행 발행, 폐기·소각 계정, 동결/에스크로를 분리하고 **총 공급 변화 = 승인 발행 − 승인 소각**을 유지한다.
- 국고 수익의 출처는 세금/거래 수수료/기부/국채 상환/이월 등의 문서화된 원장 전표로만 인정한다. 표시 자산과 지불 가능 현금, 보호 적립금과 약정금 이중 집계를 배제한다.
- 이전 이력에서 출처 불명 입금/정산 누락이 발견되면 공개 지급/자동 발행으로 덮지 않는다. 별도 이슈·사유·수정 권한·감사 승인 후 상계한다.

### 4.3 카지노·1:1 승부존
- 기존 코드는 이미 하나의 PG 트랜잭션, 계좌 잠금, `randomInt` 적용이라는 개선이 있다. 이것을 없애지 않고 정산 부분을 **패자 차감·승자 수익·국고 수수료의 총합 0 전표**로 대체한다.
- 예: 양측 베팅 각각 10,000 WLD일 때 총 팟20,000, 수수료600, 승자 수령 기준19,400. 단 기존 코드가 승자 자기 판돈을 실제 hold하는지 여부를 먼저 분석해 **두 방식 중 단 하나**의 재무 계약을 확정해야 한다. 중복 차감 금지.
- 방 상태 `waiting→locked/settling→settled` 등은 실제 DB 제약·명령과 일치. 두 명이 동시에 참가, 같은 멱등 키 재전송, 서버 crash, 국고 계좌 없음, 승자가 자기 방에 진입, 수수료 반올림 경계 등을 테스트한다. 정책/연령/국가별 규제·광고 제약 승인 전 고위험 기능 확대 금지.

### 4.4 주식·은행·대출·국채·연금·FX·사업·마켓·경매
- 각 경로의 사전 조건, 잔액 인출, 결제 상대 계좌, 수수료 귀속, 자산/채권 생성, 완료/취소/환불/만기/부분체결, 중복과 실패 시 되돌리기를 거래 명령 단위로 재작성한다.
- 주식 리그 참가비, 경매 입찰/차액 환급, 국채 발행/매수/상환·이자, 연금 납입/매칭/연금지급, 환전/스프레드 및 SWF 수익은 원장 근거 없는 WLD 증가가 없도록 한다.
- 기존 WLD `bigint`/정수 문자열로 크기·소수점·마이너스·정수 오버플로를 검증하고, 금액 정책상 임의 최고 보유한도는 도입하지 않는다. 개인별 거래 한도는 별도 위험 정책과 구분한다.

### 4.5 직업·보상·상점·게시판·알림
- 단위 성공 후 실제 원장 지급이 생기는지, 버튼이 최종 영수증까지 연결되는지, 실패 시 로딩/낙관적 UI가 성공을 꾸미지 않는지 확인한다.
- 파일 기반 DAO 투표/그랜트·임의 고정 사용자 보상은 DB 유일 키와 서버 범위 트랜잭션으로 이전 설계한다. 기존 데이터 import 시 중복과 기존 승인 이력을 먼저 대사한다.

### 4.6 관리자 및 보안
- 메뉴 노출 여부와 backend의 실제 권한/2FA 판단은 독립. 프런트 숨김만으로 보안 완료가 아님.
- 재무 명령은 상세 감사 로그에 actor, reason, operation id, 정책 버전, 처리 상태와 영수증을 남기고, 공개 화면에는 개인 및 보안 민감값을 전시하지 않는다.
- 중요 조작이 실패했는데 성공 토스트/그래프에 반영하지 않으며, 복구 단계와 문의/사건 번호를 표시한다.

### 4.7 SEO·국가별 언어 및 검색
- v710 소유자가 진행하는 블로그 구현과 동일 파일 편집 금지. 후보가 병합되면 QA 책임자가 `/blog`, `/en/blog`, `/ja/blog`, `/zh/blog`와 실제 기사 URL별 HTML title/description/article/canonical/OG/alt 확인.
- 한국의 KRW 세법, 미국의 USD/IRS, 일본의 JPY/국세청, 중국의 CNY/현지 법령은 인용 근거·적용일·비적용/면책 범위로 구분. 사용자의 접속 국가 자동설정은 사용자 수동 언어 선택을 덮어쓰거나 검색 크롤러를 무한 IP 리디렉션시키지 않는다.
- Google 검색 색인은 제출했다고 보장되지 않으며, 4.9점 별점 같은 구조화 데이터는 실제 검증된 사용자 평가와 검색 정책 없이 삽입하지 않는다.
- 사이트맵은 인덱싱 허용·200 응답·자기 canonical·실제 본문이 있는 URL만 포함한다. IndexNow/GSC 제출 영수증, 실제 URL 색인 확인, 노출/클릭/검색 키워드 통계를 각각 구분한다.

### 4.8 Discord·Android·운영
- Discord는 `node --check` 구문 검사, 별도 모듈 의존성의 재현 가능 설치, API 키 누락 시 실패 처리, 실제 음성 채널 권한/재연결/봇 API 장애/스폰서 차단 테스트 분리.
- Android는 Gradle `versionName`과 `ApiClient.APP_VERSION` 단일 원천화, debug Test 도메인과 release 운영 도메인 차단, HTTPS+허용 호스트·쿠키·CSRF·계약 DTO·네트워크 재시도 동작과 본인 인증 상태를 실기기 검증.
- 운영은 v697 새 백엔드/옛 서비스의 Outbox·시장뉴스·SWF 스케줄러 소유권 이전을 내구성 있는 임대(lease), epoch/fencing token, 실행 키/DB outbox 기록으로 보호. 새 서비스가 뜨기 전에 기존 프로세스를 먼저 죽이지 않으며, 롤백 시 스케줄러 중복 동작을 차단한다.

## 6. 필수 품질·운영 승인 게이트

- **G0 사전 게이트:** 최신 GitHub/운영 소스/기획서 SHA, 기존 PR 충돌, 테스트 DB 격리, 사용자 데이터 백업 및 복원 근거, 수정 실패시 복구 책임자 확인.
- **G1 코드 게이트:** 의존성 lockfile, TypeScript, Next/Nest 운영빌드, ESLint 오류0/새 경고0, 기밀 탐지, API 계약 일치 및 관련 기능 단위 테스트 모두 성공.
- **G2 DB 게이트:** Production 복원본의 격리 Test PostgreSQL 17에서 모든 순차 마이그레이션 체크섬과 결손 이력 정리, 앱 계정의 금지된 직접 쓰기 거부, 적법 명령 성공 및 다른 사용자의 계좌 조작 거부.
- **G3 금액 보전:** 사전·사후 계좌합계/원장·금고·통화량 식과 실제 수수료/지급이 정확히 일치. 정수 큰 값, 최소·최대, 잔액 부족, 2명 동시 참가, 동일키 리플레이, 중간 crash/타임아웃, 되돌림/환급 검증.
- **G4 UI/API E2E:** Guest/회원/관리자/2FA의 실사용 버튼부터 원장까지 검증, 모바일/태블릿/데스크톱 반응형, 모든 실제 경로 5회, WCAG 2.2 터치/키보드/포커스, 화면 오류·장애·권한 부정 경로. 단순 페이지 200이나 SSR HTML만으로 판정 금지.
- **G5 외부/잡/SEO/앱:** 구·신 백엔드 간 scheduler 동시 실행0, Outbox 유실/중복0, 국가별 본문·canonical·hreflang 검사, 실제 검색 제공자 응답, Android Test 서명/실기기 쿠키/로그인, Discord 의존성·음성 환경 확인.
- **G6 운영 승격:** CI 완료, 동일 Git SHA의 Test 프론트·백엔드·스키마, 기존 로그인 세션 보존, 최신 백업/복원 리허설, 임시 포트에서 기동, Nginx 원자적 교체, 공개 기능/버전/원장 연속 관측 5회, 롤백 보존. DB 문제가 생겨도 검증되지 않은 운영 DB 덮어쓰기는 금지.

### 중단·되돌리기 결정
- 미대사 WLD 1 이상, 직접 수정 권한 남음, 예기치 않은 PUBLIC 실행, 중복 과금, 승인 없는 WLD 발행, 인증 우회, 필수 DB 테스트 스킵, 현재 Test/Production SHA 불일치, 세션 손실, 자동잡 2중 실행이면 해당 금전 기능의 운영승격 **즉시 차단**.
- 애플리케이션 오류는 Nginx/서비스 포인터를 이전 검증 릴리스로 교체할 수 있어야 한다. DB 스키마 변경은 이전 migration 수정을 금지하고 정방향 보정으로 복구한다. 복원은 실제 데이터 손실 영향 검토와 명시적 승인 후에만 수행한다.

## 7. 개발 전 확정해야 할 설계 의사결정

1. 원장 미대사 시 **신규 위험 거래만 제한**하고 기존 데이터 조회/지원 요청은 계속 제공한다는 정책.
2. 기존 국고 원장/금고의 이중기장 연결과 누락 과거 기록을 고치는 승인 체계.
3. PvP 판돈 hold 방식/수수료 반올림과 승인될 표준 DB 함수의 범위.
4. 실제 마이그레이션 적용 이력(운영 최대 268이라는 v697 기록)과 원본 269~271, v701 긴급 권한 수정의 후속 합법적 이력 조정. 이미 적용된 SQL 변경 금지.
5. 국가별 세제/콘텐츠 법률 검토 및 가상 카지노/광고/보상 정책 승인.
6. 신·구 서버 작업 소유권 단일화, 사고 감지·복구 담당, 긴급 중지/운영 승인 책임.
