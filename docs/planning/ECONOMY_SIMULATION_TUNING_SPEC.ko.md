## 0. 목적

Moneyverse는 기본적으로 플레이 횟수에 임의의 하드캡을 두지 않는다. 따라서 경제 안정성을 일일 행동 제한에 의존해서는 안 된다. 이 문서는 faucet/sink 데이터, 자산 분포, 코호트 행동, 시나리오 예측을 이용해 경제정책을 측정·시뮬레이션·미리보기·조정·승인·배포·관찰·롤백하는 방법을 정의한다.

이 문서는 자동 잔액 변경을 허용하지 않는다. 시뮬레이션은 참고용이다. 실제 정책 쓰기 기능은 별도 런타임 구현과 출시 절차를 거쳐야 하며 검증, 감사, 롤백이 필수다.

## 1. 현재 런타임 현실과 남은 공백

현재 통합 PR `#189` Economy Scenario Lab에는 읽기 전용 결정론적 예측기가 있다. 현재 M2, 최근 24시간 발행량, 최근 24시간 소각량, 1~365일 기간, 발행/소각 변화율을 기준으로 계산하며 WLD 정밀도는 정수 문자열과 `BigInt`로 유지한다. 정책 쓰기 경로가 없고 장기 예측에는 행동 변화가 반영되지 않는다는 경고도 포함한다.

이 기능은 첫 단계로 유효하지만 완전한 경제모델은 아니다. 아래 기획은 이번 문서 변경에서 런타임을 건드리지 않고 향후 확장 계약을 정의한다.

## 2. 경제 회계 분류

시뮬레이션에 사용하기 전에 모든 가치 이동을 다음 중 하나로 분류한다.

- `faucet`: 새로운 사용 가능 WLD가 유통에 들어옴
- `hard_sink`: 사용 가능 WLD가 영구적으로 유통에서 제거됨
- `transfer`: 유저/시스템 계정 사이로 이동하지만 전체 유통량은 줄지 않음
- `converter`: 한 자원이 다른 자원으로 변환됨. 실제 제거된 부분만 sink로 계산
- `hold`: 일시적으로 유동성이 잠기지만 향후 다시 유통될 가능성이 있음
- `treasury`: 시스템 보유 WLD도 비재유통 계정으로 명시하지 않는 한 공급량에 포함

유저 거래소 GMV, 주식 거래량, 유저 간 송금 자체는 소각으로 계산하지 않는다. 실제 수수료·소각 부분만 hard sink다.

## 3. 필수 기준 데이터

각 시뮬레이션 스냅샷에는 최소 다음을 기록한다.

- `snapshot_at`, `policy_version`, `season_id`, 가능하면 런타임 SHA/config 버전
- 유통/M2 성격 WLD 공급량
- 1시간/24시간/7일/30일 발행량
- 1시간/24시간/7일/30일 hard sink
- transfer volume 별도 집계
- hard-sink ratio = `hard_sink / faucet`
- 평균/중앙/P90/P95/P99 유동 잔액
- 상위 1%/10% WLD 점유율
- 소비처별 소각 비중과 상위 3개 소비처 집중도
- 코호트별 구매일수와 소비처 사용 폭
- 신규 유저 D7/D30 유동 잔액
- 고자산 유저 잔액 증가율
- 사업체 총마진 및 유지비 부담 분포
- 거래소·주식시장·클럽·도시 프로젝트 수수료/소각
- 시즌·이벤트 소각량
- 보호한도 발동률
- 한계보상/보상감소 적용률
- 측정 가능한 경우 악용탐지 오탐률

M2와 하루 흐름만 사용하는 시나리오는 화면에서 반드시 `simple_projection`으로 표시한다.

## 4. 표준 시나리오 기간

### 30일 — 운영 조정
단기 라이브옵스, 신규 소비처, 보상 이벤트, 시즌 전환을 검토한다. 세 기간 중 신뢰도가 가장 높다.

### 90일 — 시즌/분기 스트레스 관점
여러 이벤트 주기를 지나도 발행/소각, 사업 수익성, 자산집중이 유지 가능한지 확인한다.

### 180일 — 구조적 위험 관점
장기 복리성 증가나 소비처 고갈을 탐지한다. 방향성 참고로만 사용하고 높은 모델 위험 경고를 표시한다.

7일/365일 보조 관점은 추가할 수 있지만 30/90/180일을 표준 비교 단위로 둔다.

## 5. 시나리오 행렬

매 기획 검토에서 최소 다음을 계산한다.

1. **Baseline**: 현재 발행·hard sink 흐름 유지
2. **Growth**: 활성유저·발행량 증가, 소비처 채택률은 동일
3. **Sink expansion**: 일반 플레이를 줄이지 않고 소비처 채택/가격조합 개선
4. **Reward pressure**: 이벤트·시즌·작업 보상으로 faucet이 일시 상승
5. **High-wealth acceleration**: P95/P99 잔액이 중앙값보다 빠르게 성장
6. **Low-engagement contraction**: DAU 하락으로 고정비·유지비 부담이 상대적으로 커짐
7. **Abuse shock**: 악용으로 발행량 또는 transfer velocity가 급증

하나의 직선 예측을 확정 전망처럼 보이지 말고 시나리오별 가정을 명시한다.

## 6. 모델 단계

### Layer A — 결정론적 흐름 예측
현재 단순식:

`예상공급량 = 현재공급량 + 일수 * (예상일일faucet - 예상일일hard_sink)`

방향성 영향 미리보기에만 사용한다.

### Layer B — 코호트 모델
최소 다음으로 분리한다.

- 신규/활성화
- 초기 정착
- 중간 자산
- 고자산
- 명예 자산
- 비활성/복귀

각 코호트별 활성일수, 일일 faucet, 일일 sink, 구매일 확률, 소비처 구성, 이탈/복귀 행동을 모델링한다.

### Layer C — 동적 반응 모델
가격/보상 변경에 대한 행동 반응을 고려한다. 예를 들어 명예 상품 가격을 올렸다고 소각량이 선형으로 증가한다고 가정하지 않는다. low/base/high 탄력성 범위로 비교한다.

### Layer D — 확률/스트레스 모델
실데이터가 충분해지면 활동량, faucet, sink 구매율, 사업결과, 이벤트 효과에 제한된 분포를 적용해 반복 시뮬레이션한다. 단일 랜덤 결과 대신 중앙값과 P90 불리한 결과를 보고한다.

## 7. 경제 상태와 트리거 밴드

아래는 기획용 트리거이며 절대규칙이 아니다.

### GREEN — 관찰
- 순발행이 안정적이거나 성장단계에서 의도적으로 양수
- 중앙/P90 구매력이 정상
- 상위 1% 점유율이 빠르게 가속하지 않음
- 성숙 유저에게 항상 최소 5개 의미 있는 소비처
- 고자산 유저에게 최소 3개 자발적 명예 소비처
- 특정 소비처가 지속적으로 전체 소각의 약 40% 이상을 독점하지 않음

조치: 긴급변경 없이 콘텐츠 주기를 유지한다.

### AMBER — 제안 필요
예시:
- 30일 순발행이 이전 기준보다 의미 있게 가속
- 중앙값은 정체인데 P95/P99만 계속 상승
- 상위 1% WLD 점유율이 여러 관찰기간에서 지속 상승
- 상위 3개 소비처 집중도가 경고범위를 넘음
- 고자산층이 실제로 살 만한 것이 부족
- 신규/중앙 코호트의 필수진행 구매가능성이 악화

조치: 버전이 붙은 조정 제안을 만들고 런타임 변경 전에 시뮬레이션한다.

### RED — 개입 검토
예시:
- 확정된 악용/무제한 faucet
- 원장 reconciliation 불일치
- 이벤트 예상 범위를 벗어난 단기 대규모 발행
- sink 변경이 신규/중앙 유저의 회복을 막는 수준
- 조작/악용 때문에 지표 자체가 오염됨

조치: 무결성 봉쇄를 최우선으로 한다. 보안·시스템·시장 무결성을 지키기 위한 보호한도는 가능하지만 일반 플레이 캡처럼 위장하면 안 된다.

## 8. 조정 우선순위

인플레이션이나 자산집중이 커질 때 다음 순서를 우선한다.

1. 꾸미기·수집·주거·클럽/도시·명예 소비처 추가/갱신
2. 소비처 발견성과 사용자 가치 개선
3. 실제 활동에 대응하는 사업·물류·제작 서비스 비용 확대
4. 선택형 고가 가격사다리나 도시 프로젝트 기여곡선 조정
5. 공개된 범위 안에서 시장/등록/서비스 수수료 조정
6. 반복 저가치 파밍에 한계보상 감소 적용
7. 마지막에 악용·시스템·시장무결성을 위한 좁은 보호한도 검토

일괄 몰수성 세금, 임의 일일 행동캡, 숨은 상한은 기본 해결책으로 사용하지 않는다.

## 9. 변경폭 가드레일

경제 config는 작은 단계로 조정하고 관찰한다.

기본 기획 가드레일:

- 일반 catalog/sink 가격: 한 조정에서 보통 ±10% 이내
- 광범위 faucet/보상 변경: 악용 수정이 아니라면 보통 ±10% 이내
- 신규유저 필수 가격: 인상 전에 구매가능성 검증 필수
- 고가 명예상품은 신규 tier/SKU 추가 시 더 큰 가격차를 둘 수 있지만 이미 약속한 보상을 몰래 재가격하지 않음
- 전역 고위험 변경은 가능하면 canary/제한 코호트 또는 proposal-only 모드로 시작

이 값들은 운영자 변경폭 가드레일이며 사용자 플레이 횟수 제한이 아니다.

## 10. 가격/소비처 탄력성 실험

조정 가능한 소비처에는 다음 실험 기록을 남길 수 있어야 한다.

- `experiment_id`
- 대상 코호트
- 정책 버전/config hash
- 이전/새 가격 또는 수수료
- 노출 시작/종료
- 구매 전환율
- 유저별 구매일수
- 유저별 WLD 소각량
- 리텐션/세션 가드레일
- 문의·불만 비율
- 신규유저 구매가능성 영향
- P2W/경쟁무결성 검토 결과

필수 상품을 개인별로 불투명하게 다른 가격으로 책정하지 않는다. 코호트 실험도 문서화되고 되돌릴 수 있어야 한다.

## 11. 소비처 포트폴리오 요구사항

각 소비처에는 최소 다음을 작성한다.

- 이름과 sink code
- 기능과 사용자 가치
- 목표 자산/유저 세그먼트
- 초기 가격 또는 가격곡선
- 반복 가능 여부
- `hard_sink` / `transfer` / `converter` / `hold` 분류
- 영구/기간성 가치
- P2W 여부
- 원장 transaction type
- analytics event
- 운영 config key
- 악용 가능성
- 성공/퇴역 조건

WLD를 많이 없앤다는 이유만으로 좋은 소비처가 아니다. 리텐션, 구매가능성, 체감가치도 함께 유지해야 한다.

## 12. 경제 대시보드

최소 운영 지표:

- faucet, hard sink, 순발행, hard-sink ratio
- transfer volume 별도
- 평균/중앙/P90/P95/P99 유동잔액
- 상위 1%/10% WLD 점유율
- 소비처별 소각비중과 상위 3개 집중도
- 코호트별 구매일수와 소비처 폭
- 고자산 잔액 증가율
- 신규유저 구매가능성
- 보호한도 발동률
- 한계보상 적용률
- 악용탐지 오탐률
- 현재 정책/config 버전
- 최신 시나리오 스냅샷과 가정

transfer GMV를 burn으로 표시하면 안 된다.

## 13. 운영자 흐름

1. 변경불가 기준 스냅샷 저장
2. 문제와 영향 코호트 정의
3. 30/90/180 시나리오 선택
4. 읽기 전용으로 후보 변경 미리보기
5. 기대효과와 가드레일 위험 기록
6. 변경 종류에 따라 제품/보안/법률 검토
7. 실제 config/write는 별도 개발 브랜치에서 구현
8. isolated Test에서 exact SHA/config 검증
9. 가능하면 좁은 범위로 출시
10. 정해진 평가기간 관찰
11. 유지/추가조정/롤백 결정
12. changelog/worklog에 근거 기록

이 문서는 자동 self-tuning을 활성화하지 않는다. 충분한 과거 데이터로 안정된 임계값, 가역적 제어, 낮은 오탐률이 확인된 뒤에만 향후 검토한다.

- `economy_tuning_proposals`
- `economy_experiment_assignments`

## 15. UI/UX 요구사항

### 데스크톱
기준/가정 패널, 30/90/180 비교표, 자산분포 카드, 소비처 포트폴리오 차트, 별도 제안영역을 배치한다.

### 태블릿/모바일
넓은 표는 지표 카드로 전환한다. 가로 스크롤 없이 `시뮬레이션 실행`에 접근 가능해야 한다. 긴 가정은 접기/펼치기 영역으로 둔다.

### 상태
loading/skeleton, baseline 없음, 일부지표 누락, stale data, 잘못된 입력, 서버오류, 권한거부, offline, maintenance, 완료 상태를 정의한다.

### 접근성
- 경제상승/하락을 색상만으로 표시하지 않음
- `+/-`, 텍스트, 접근성 라벨을 함께 사용
- 키보드 조작과 visible focus
- 차트 내용의 텍스트/표 대체
- 동적 결과 변경 시 적절한 live region 제공

관리자가 가정을 입력 중일 때 자동새로고침으로 값을 날리면 안 된다. 새로운 기준데이터가 들어오면 비파괴 `새 기준 데이터 사용 가능` 알림을 제공한다.

## 16. 분석 이벤트

최소 이벤트:

- `economy_scenario_opened`
- `economy_scenario_run`
- `economy_scenario_exported`
- `economy_tuning_proposal_created`
- `economy_tuning_proposal_approved`
- `economy_policy_rollout_started`
- `economy_policy_rollback`
- `sink_purchase` + sink family/code/burn amount
- `protection_limit_triggered`
- `marginal_reward_applied`

비밀번호, 토큰, 개인정보가 포함된 전체 요청 body 등은 로그에 남기지 않는다.

## 17. 악용과 무결성

관측 경제데이터로 조정하기 전에 확인된 악용 클러스터를 제외하거나 별도 표시한다. exploit 때문에 faucet이 급증했다고 일반 유저 가격을 올려서 균형을 맞추면 안 된다.

필수 확인: 다계정 파밍, 자동화 보상, duplicate/replay 악용, 거래소 wash trading, 주식 self/circular trading, 비정상 정산.

## 18. 수익·법규·SEO 영향

이 명세는 서비스 내부 WLD와 simulated/game-only 자산만 다룬다. 현금환전, 실제 증권, 예금, 실질 투자수익을 만들지 않는다.

유료 수익화가 조정시스템을 통해 직접 WLD·주식·랭킹 우위를 판매하면 안 된다. 광고수익 지표를 경제지표와 같이 분석할 수는 있지만 광고비·스폰서 비용이 WDX 가격, 랭킹, 경제결과를 직접 결정해서는 안 된다.

공개 검색페이지를 추가하지 않는다. 경제 시나리오/관리자 화면은 인증된 operator-only이며 `noindex`를 유지해야 한다. 직접 SEO 영향은 중립이다.

향후 실제 현금 구매, 환전 가능성, 규제 금융상품 성격이 추가되면 시뮬레이션에 넣기 전에 별도 법률 검토가 필요하다.

## 19. 리서치 노트 — 2026-09-13

### Microsoft PlayFab Economy V2 — 공식 플랫폼 문서 — 구현 근거로 채택
2026년 최신 문서는 멱등성 transaction, 고동시성 inventory/economy 작업, transaction history, 명시적 서비스 제한을 강조한다. 채택 시사점: Moneyverse는 멱등성, 정수 안전 회계, pagination/history read model, 시스템 보호한도를 일반 플레이 캡과 분리한다.

### Unity Remote Config / Game Overrides — 공식 LiveOps 문서 — 운영 패턴 근거로 채택
최근 Unity 문서는 환경별 remote settings, 예약/타깃 override, config version/hash 일관성, A/B 가능한 LiveOps 변경을 설명한다. 채택 시사점: Moneyverse 경제조정도 버전화·환경분리·미리보기·가역성·측정을 기본으로 하고 프론트 상수로 임의 변경하지 않는다.

### Unity Economy 서비스 상태 — 공식 문서 — 참고만 함
Unity 공식 문서는 2026-09-08부터 신규 Unity Economy 프로젝트 가입을 받지 않고 기존 구성 프로젝트만 계속 사용할 수 있다고 명시한다. Moneyverse는 Unity Economy에 의존하지 않으며 LiveOps/config 설계 패턴 참고에만 사용한다.
