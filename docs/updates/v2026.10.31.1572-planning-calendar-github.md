### Purpose, alternatives, member flow and states
- **Problem:** the current /inventory view lists owner holdings but does not provide a day-based forecast of when multiple held items expire. A member should be able to plan before expiry without falsely assuming that a reminder has been delivered. This is a read-only inventory aid, not an alert delivery or purchase feature.
- **Options:** (A) filter existing inventory client-side: inexpensive but can mistake an upstream failure for an empty list and is not safe for 10,001 holdings; (B) rely on unimplemented reminder-preview F675-194: couples an inventory view to consent/mute/digest and gives a different eligibility definition; (C) **chosen** owner-scoped DB aggregate and bounded per-day details, independent of reminder opt-in. No email/push, auto-renew, equip, purchase, WLD or ledger changes.
- **Audience/entry:** authenticated consent-current member only. From /inventory → /inventory/expiry-calendar. Default next 7 KST calendar dates; switch to next 30 dates; choose a date to open its detail list. CTA “7 days”, “30 days”, “View items”, “Refresh”, “Back to inventory”. Explain “Expiry forecast is not an alert-delivery record”; nonexpiring holdings remain in ordinary inventory.
- **Truthful states:** LOADING, VERIFIED_DAYS, VERIFIED_EMPTY (only from successful owner DB response), VERIFIED_DAY_EMPTY, MORE_ITEMS, STALE_DAY (409; refresh and restart), AUTH_REQUIRED, CONSENT_REQUIRED, SOURCE_UNAVAILABLE (503), RATE_LIMITED (429), and ACCOUNT_CHANGED (discard stale response). A failed read must never display “no expiring items”. On feature OFF show no navigation or call. Date and count screen-reader announcements, clear focus after filter/detail changes, reduced motion, 44px targets, 320px width/200% zoom, WCAG 2.2 AA; Next and Android parity.
- **Scope:** one user_items row is one catalog **type**; quantity is a separate **unit** count. Include only owner rows with quantity>0, expires_at IS NOT NULL, expires_at>one DB asOf, and expiry in [KST today 00:00, KST today+windowDays 00:00), with 7 or 30 inclusive dates. Midnight exactly at end belongs to the next window and is excluded. A row expiring at 00:00 KST belongs to that date. Group by Asia/Seoul calendar date, not browser timezone; PostgreSQL timestamptz microseconds are authoritative, not rounded JavaScript Date. If item expires during viewing, next fresh read may remove it; this is a forecast, not an immutable historical receipt. A missing expiry is not an expiry forecast.

### API, SQL ownership, cursor and consistency contract
- **Nest endpoints (proposed):** authenticated/consent/CSRF owner-only POST /api/v1/shop/expiry-calendar/summary with {windowDays:7|30}; POST /api/v1/shop/expiry-calendar/day with {kstDate:YYYY-MM-DD,limit?:20|50,cursor?:opaque}. Derive actor from session; never accept owner ID. Next server boundary and Android /app-api/v1/shop/expiry-calendar/* use identical validated schemas. Request body <=2KiB; proposed 20 owner reads/minute with separate burst cap to measure. Strict date must be within selected 30-day horizon. 200 with {status:'VERIFIED',asOfUtc,timeZone:'Asia/Seoul',windowDays,days:[{kstDate,typeCount,unitCount,earliestExpiryUtc}],totalTypes,totalUnits} and day {status:'VERIFIED',kstDate,asOfUtc,items,nextCursor?,totalTypes,totalUnits}; verified empty is 200 only after authoritative query. 400 invalid/oversize, 401 unauthenticated, 403 consent/CSRF, 409 STALE_DAY, 429 quota, 503 DB/schema/ACL/unknown. No caching or fallback-to-empty.
- **DB boundary:** forward-only owner-scoped SECURITY DEFINER functions (provisional shop_owner_expiry_calendar_summary_v1(actor,window_days) and shop_owner_expiry_calendar_day_v1(actor,kst_date,limit,cursor_fields)); fixed search_path, migrator ownership, explicit EXECUTE to moneyverse_app only. Never GRANT direct SELECT/INSERT/UPDATE/DELETE on user_items, shop_catalog, receipt, identity, or finance tables. Use one primary-DB statement snapshot and one DB asOf for each response; do not pretend separate HTTP requests share a snapshot. Join catalog by UUID after filtering owner; no arbitrary client SQL. Index candidate (user_id,expires_at,catalog_id) WHERE quantity>0 AND expires_at IS NOT NULL only after EXPLAIN (ANALYZE,BUFFERS) on 10,001 synthetic holdings and insert-cost review. No new table needed in V1. Type counts are COUNT(*) bigint for distinct owner+catalog PK rows, unit counts SUM(quantity)::bigint, serialized as exact decimal strings if outside JS safe integer range.
- **Stable day pagination:** default 20/max 50, ordered by (expires_at ASC,catalog_id ASC). An opaque HMAC cursor binds actor, KST date, last exact-microsecond expiry and UUID, complete-day deterministic fingerprint over sorted (catalog_id,exact expiry,quantity), schema version, issuedAt and 120-second expiry. A new day read recomputes fingerprint on one statement snapshot; if changed or cursor expired, return 409 STALE_DAY and refresh, never silently claim a complete stable result. Cursor must not embed item names or session secrets; rotate signing key. Fingerprint/EXPLAIN cost and max response size are acceptance gates, not assumed acceptable. Do not use acquired_at as holding-generation evidence. If fingerprint or cursor verification cannot be implemented safely, keep flag OFF; no fake nextCursor.
- **Privacy and operational boundaries:** Cache-Control private,no-store; X-Robots-Tag noindex; Referrer-Policy no-referrer on all 200/4xx/5xx at Nest, Next, Android gateway, and page. Vary Cookie when appropriate; no sitemap, crawler indexing, query-string item IDs, raw owner item names in analytics or admin. Protect against cross-account response reuse and parameter tampering; CSRF and same-origin/session boundaries. No write transactions, no reminder preference changes, no ledger/WLD/holdings mutations. Any operator metrics aggregate >=20 members only; day-view, empty, retry, stale cursor, 429/503, p95 latency and 7/30 conversion are proposed KPIs. p95<300ms is an unmeasured target, not a result.
