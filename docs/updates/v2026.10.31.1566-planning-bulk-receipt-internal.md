### Proven specification gap and alternatives
- **Risk, not confirmed production defect:** v1564 promises same-idempotency-key replay of a committed batch but checks a 120-second preview token before receipt lookup. A first apply can commit while its HTTP response is lost; retry at T+121 seconds then rejects a completed batch as expired. A digest of raw signed preview bytes/issuedAt would also reject an equivalent refreshed preview as a different request. No owner receipt lookup endpoint is specified. UNIQUE(owner,key) alone cannot resolve this.
- Rejected: retry with a new key (duplicate mutation risk); treat timeout/receipt absence as definite failure (fabricated certainty); extend all preview tokens indefinitely (stale write risk). **Choose** canonical logical-intent digest, receipt-first replay, and owner-only read-only receipt-status. Historical committed receipt does not guarantee current mute state.

- **Stable request_digest v1:** SHA-256 of domain-separated length-delimited canonical serialization of owner UUID, action, sorted distinct thresholds, sorted distinct catalog UUIDs, each DB-owned holding generation and exact PostgreSQL microsecond expiry, and expected preference revision. Exclude preview HMAC bytes, issue timestamp, nonce, request arrival time and ephemeral session ID. Server verifies signed claims/DB values; never use JavaScript Date to construct an expiry precondition. Current session must match preview for **new writes**, while an authenticated owner can read their historical receipt after session rotation via receipt-status.
- **Replay ordering:** authenticated owner+consent+CSRF → bounded syntax/UUID/duplicate checks → verify signed preview integrity and owner (without conflating expiry with integrity) → transaction-scoped owner+key serialization → read immutable committed receipt and compare canonical digest → matching receipt returns same result without writing, even after T+120s, global OFF or later expiry/generation changes → different intent with same key 409 KEY_REUSED_DIFFERENT_INTENT and zero writes → if no receipt, check preview freshness/current session/global ON/preference revision/holding generation/exact expiry/ownership and quota → all-or-nothing mute+receipt transaction. Expired or stale **uncommitted** request 409 with zero changes. Fresh preview can reuse same key only if canonical intent unchanged; changed intent needs a new key after explicit review. Signed token never authorizes a new write after expiry.
- **Lock and persistence:** owner+idempotency-key transaction serialization first, then owner preference row, holdings sorted by catalog UUID, mute rows sorted identically, then receipt; align with individual/digest workers before implementation.
