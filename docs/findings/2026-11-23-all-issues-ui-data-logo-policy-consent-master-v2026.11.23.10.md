## 3. Three authentication methods share ONE server-authoritative consent gate
- **Google OAuth**, **Discord OAuth**, and **local email/password** (including register and subsequent login) must all display terms/privacy links and the latest mandatory terms/privacy consent status; OAuth provider identity verification is **not** a substitute for Moneyverse consent.
- Require explicit affirmative, separate Terms and Privacy acknowledgment as the owner's product policy (and age/other required items as applicable), not checked by default; avoid coercing consent to **optional** processing/marketing. Validate lawful basis and whether each purpose truly requires consent through legal review. Record independent version ID, actor/session, consent timestamp, notice/diff/effective date, locale and server audit receipt. Do not publish personal details.
- Current repository has **partial existing mechanisms**: `frontend/src/app/login/consent-form.tsx` links to `/terms`, `/privacy`; `frontend/src/components/consent-guard.tsx` renders stale-version step-up; `backend/src/auth/bootstrap.controller.ts` publishes `termsVersion` and `privacyVersion` and `viewer.consentCurrent`; `backend/src/auth/auth.controller.ts` accepts `PUT /auth/consent` under session and CSRF; `backend/src/auth/guards/consent.guard.ts` rejects not-current consent with 428. These Next/Nest paths **do not prove the current Spring runtime covers all three login paths**.
- **Six-month recurring consent**: owner's requested **new policy / NOT VERIFIED IMPLEMENTED**. Trigger at each **six calendar months** after the member's latest fully accepted required consent timestamp, even if document versions are unchanged. Calculate on server using timezone-aware UTC instants and calendar-month semantics, not guessed 180-day or client-only local storage. Check at sign-in and on session resume/privileged actions; when due, show explicit renewal notice with both current links and require affirmative acceptance before protected product interactions. Keep account/session identity intact where safe; avoid unnecessary OAuth reauthentication or silent logout. Verify exact migration/session model and grant access to policy reads and logout.
- **Policy updates trigger immediate notice and re-consent**: when published Terms or Privacy version **materially changes** or its required basis/consent scope changes, announce the summary of modifications, old/new version, publication/effective date and link to each full text. Prompt the **same user in all three login methods** before the new terms-dependent protected use; do not wait for the next six-month date. Preserve prior acceptance audit as history. Non-material editorial edits may have notice-only handling after policy/legal review; do not falsely assert every change always legally requires consent.
- If new policy is unavailable, stale, inconsistent or API/DB fails, **fail closed for protected operations** with actionable notice and policy links, without false success, destroying identity, or blocking public legal documents. Server API must enforce gating independently of client-side modal.
- Existing login and mobile contract must remain aligned with `/auth/policy`, `/auth/viewer`, `/auth/consent` and published versions; harmonize Spring authoritative implementation rather than re-enabling Node runtime merely to meet the policy.
