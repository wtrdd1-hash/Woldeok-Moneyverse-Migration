## 2. 코드에서 확정된 원인 후보 및 동작

### A. 대시보드의 **오류를 0건으로 바꾸는 표현 문제 — 소스 확인**
- `frontend/src/app/dashboard/page.tsx`: `requireMember()` 다음 `apiOrNull`로 `/api/v1/wallet?recent=6`, `/api/v1/stocks/watchlist`, `/api/v1/stocks/portfolio`, `/api/v1/stocks/history`, `/api/v1/stocks/alerts/events?limit=5`를 병렬 호출한다.
- 지갑 응답 null이면 `WLD 보유` 값은 `—`다. **잔액이 0이라는 표현이 아니라 조회 불가 표현**이다.
- 그러나 `const watched = watchlist?.stocks ?? []`, `const holdings = portfolio?.holdings ?? []` 다음 요약 카드에 `String(watched.length)`, `String(holdings.length)`를 사용한다. 따라서 원천 API 장애와 정상적인 0건을 구분하지 못하는 **UI 코드 결함은 확인**된다. 별도 하단 영역은 null의 경우 `LoadFailure`를 보여주므로 상단 요약과 불일치 가능성이 있다.
- 수정 시 확인된 실제 0만 0으로 표시하고, 응답 오류·스키마 오류·인증 만료는 별도 상태·재시도 UI로 표시해야 한다. WLD 잔액 추정·캐시를 근거 없는 현재 잔액으로 표기 금지.

### B. 지갑 전체 fallback — 소스 확인, 운영 실패 원인은 미확인
- `frontend/src/app/wallet/page.tsx`: `/api/v1/wallet?recent=50`, 은행 대출, 보상, 가상 주식 포트폴리오 조회.
- `if (!wallet)`이면 첨부한 `지금은 지갑을 불러올 수 없어요.` 페이지를 반환한다.
- 이는 **화면에서 지갑 핵심 조회가 유효하게 완료되지 않았음**을 의미하지만 원장 잔액 변동이나 데이터 손상을 증명하지 않는다. `401/403/404/429/5xx`, 서버 렌더링 오류, 스키마 불일치, API 라우팅·세션·DB·타임아웃을 구분해야 한다.

### C. 채권 시장 검증 거부 — 의도된 안전 차단 유지
- `frontend/src/app/bonds/page.tsx`: `publicApi('/api/v1/bonds/markets', 30)` → `verifyBondMarkets` 실패 시 경고 및 청약 차단.
- `frontend/src/app/bonds/market-integrity.ts`: `overview`/채권 배열, 발행량·잔여량, UUID/코드, 상태, 중복, 금액 형식 등을 검사한다. `disclosed_at`가 5분보다 오래됐거나 미래 1분 초과이면 거부한다. 100건 초과도 거부한다.
- 따라서 **API가 200을 반환해도** 형식 오류, 서버 시간/캐시 신선도 문제로 해당 경고가 발생할 수 있다. 실제 요청/응답의 개인 데이터 없는 필드 메타와 서버 시계 확인 필요.

### D. 전직 상태 **POST 이후 GET 확인** 구조 — 중간 성공 가능성

- **중요:** 오류는 POST에서 발생했거나, POST는 반영됐는데 후속 GET이 404여서 발생했을 수도 있다. 스크린샷에는 응답 상태·요청 추적 정보가 없다. **직업이 안 바뀌었다고 단정하거나 무작정 전직을 반복하지 않는다.** 전직 영수증·실제 프로필 상태를 대조할 것.
