# v2026.10.18.804 — Immutable ledger journal direct-privilege lockdown

**Status:** Security hardening candidate. Exact live Production application release remains v717, and 19 unexplained balance projections are NOT certified. See [operator worklog](../worklog/2026-10-18-ledger-privilege-v804.md).

## Risk
Actual Production role `moneyverse_app` had direct `INSERT, UPDATE, DELETE, TRUNCATE, TRIGGER, REFERENCES, MAINTAIN` on canonical `ledger_transactions` and `ledger_postings`. This permits bypassing ledger-entry/domain receipts or destroying historical postings if app credentials are compromised. Current Production v717 compiled backend and current main backend source read these tables but contain no direct data modification SQL against either table.

## Containment
New numbered migration `277-core-ledger-app-privilege-lockdown.sql` does exactly one transactional permission change: revoke **ALL** table privileges for `moneyverse_app` on those two immutable journal tables and grant back **SELECT** only. Existing ledger function owners and scoped SECURITY DEFINER functions are unchanged; no table rows, treasury funds or member balances are touched. This is intentionally not a blanket revoke on `accounts`, `account_balances`, or `system_treasury_vaults`, since remaining direct-writer flows require separate ledger-first migrations.

## Test evidence
RED then GREEN regression on migration source, database package suite **9 passed / 3 skipped**. Verified original Production snapshot SHA256, restored its **schema+ACL only** into separate Test PostgreSQL 17 disposable database (no member data), saw baseline overly broad grants, applied 277 successfully, re-applied idempotently, and confirmed app SELECT on both tables but INSERT/UPDATE/DELETE/TRUNCATE blocked. Function `economy_post_transaction` retains SECURITY DEFINER owner `moneyverse_migrator`; application direct execute on that generic function was already restricted by prior design.
