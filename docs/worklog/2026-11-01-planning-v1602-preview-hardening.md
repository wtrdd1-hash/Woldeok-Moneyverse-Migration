### Source-verified gaps and decisions

**D1 — Web preview has no specified browser transport (P1).** `frontend/src/app/account/notifications/page.tsx` is a server component guarded by `requireMember()` and uses `apiOrNull()` for the unrelated engagement preference. `apiOrNull()` deliberately maps API errors to null; it cannot be used to prove a zero count. The proposed Nest `GET /api/v1/shop/expiry-digest/preview` is not directly callable from a client island through the server-only `frontend/src/lib/api.ts`. **Decision:** Dev A owns a narrow same-origin **GET `/api/shop/expiry-digest/preview`** Next route at `frontend/src/app/api/shop/expiry-digest/preview/route.ts`, forwarding the current request's session through the existing server-side API helper, with explicit typed `ApiError` propagation (401/403/429; all unverified upstream/parse/clock errors 503). No fallback `[]`, `null`, `0`, success-shaped mock, anonymous cached result, CSRF write, opt-in or notification creation. A client-only `expiry-digest-preview-panel.tsx` is embedded under the existing notification settings; it fetches this BFF with `cache:'no-store'`, validates `sourceStatus==='VERIFIED'`, canonical nonnegative decimal strings and a real UTC microsecond timestamp, and distinguishes VERIFIED_ZERO from SOURCE_UNAVAILABLE. BFF and client tests must prove upstream 200 malformed JSON/HTML/null never becomes a verified count.

**D2 — Android gateway can inherit cacheable upstream shop headers (P0 privacy gate).** `frontend/src/lib/app-gateway.ts:48-74` admits the `shop` group, while `frontend/src/app/app-api/v1/[...path]/route.ts:501-513` copies upstream headers and forces private/noindex only for `shop/purchases`, not `shop/expiry-digest/preview`. `handle()` around lines 565-603 also lacks an exact preview override. **Decision:** Dev C must match only `['shop','expiry-digest','preview']`, require GET (HEAD handled explicitly without a reusable cached entity), validate the exact success payload before passing it to Android, and force `Cache-Control: private, no-store`, `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff` on 200, 400, 401, 403, 405, 429, 503, 502/504 and malformed upstream 200. Strip `ETag`, `Last-Modified`, `Expires` and cache validators; reject or ignore conditional request validators so 304 cannot authenticate an old member's response. Do not change public `shop/items` and `shop/public-catalog` caching by broad group matching. Validate the final edge (including CDN/proxy) and Android account-switch isolation; source risk is **not proof of a Production disclosure**.

**D3 — A verified read is not indefinitely current (P1).** A six-digit PostgreSQL `statement_timestamp()` describes the read, not the display time. On receipt show “verified at” and use a monotonic UI timer: after **60 seconds** mark the panel STALE and require an explicit Refresh to claim current counts; when returning from a hidden tab or offline state, do not silently relabel old values VERIFIED. Keep the old value only with a visible stale label, never as an active zero. Use `AbortController` plus monotonically increasing request/session generations to discard late responses after refresh, logout, consent withdrawal or account change. Never use client `Date` to determine the two expiry windows; SQL owns `(asOf,asOf+24h]` and `(asOf+24h,asOf+72h]`. A slow response or unparseable `asOfUtcMicros` must be unavailable, not verified. 60 seconds is a **proposed UX policy**, not a measured freshness SLA.

**D4 — Actor UUID is not a database identity, and timeout settings can leak across a pool (P0 security gate).** `packages/database/migrations/071-shop-catalog-schema.sql:14-16` defines `user_items` PK `(user_id,catalog_id)` with `quantity>=0` and `expires_at timestamptz`, revoking app table access; migration 123's `shop_my_items_v2(p_actor uuid)` is a `SECURITY DEFINER` function that trusts the supplied actor. An app principal with direct EXECUTE on a new `shop_expiry_digest_preview_v1(p_actor uuid)` can supply another valid UUID: a Nest guard alone cannot make a direct app-role spoof-negative test pass. **Decision:** do **not** grant that function to the shared app principal until the security owner chooses and proves a real identity-bound database boundary (e.g. independently authenticated per-principal execution), or explicitly documents and accepts the weaker service-trust model with separate credentials and compensating controls; do not mislabel service checks or a writable GUC as independent DB proof. In either model prohibit direct `user_items` SELECT, require two-owner cross-actor negative tests and revoke PUBLIC. The proposed 2s SQL budget must be enforced without persistent session `SET` on pooled connections: use a verified per-transaction `SET LOCAL statement_timeout` inside READ ONLY transaction or a safely configured dedicated pool/role, with timeout and pool-reuse regression. The aggregate uses a single SQL statement/snapshot, owner predicate, `quantity>0`, nonnull `expires_at`, and exact microsecond bounds; count one PK catalog row once, not total quantity or `effect_expires_at`. Use EXPLAIN on 10,001 synthetic holdings before considering `(user_id,expires_at)` index; 10 requests/owner/minute plus coarse abuse protection and 429 Retry-After are **test targets**.
