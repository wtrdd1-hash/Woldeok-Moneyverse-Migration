### User need, verified source gap, choices
- **Audience and purpose:** authenticated, consent-current members need a quick, trustworthy answer to “Which owned items are nearing their holding expiration?” without reading an unbounded inventory or first implementing the proposed expiry calendar. Display next 24h, following 24–72h, and following 72–168h as **disjoint elapsed-time** bands, distinct catalog-item kinds, total owned units, and nearest holding expiration. No reminder delivery, payment, upkeep settlement, equip, item consumption or WLD transfer is inferred or initiated.
- **Source:** `frontend/src/app/inventory/page.tsx` calls `requireMember()` then `apiOrNull('/api/v1/shop/holdings')`, and converts upstream failure into `[]`; `inventory-view.tsx` has category tabs and equipped preview but no urgency summary. Nest `shop.controller.ts` delegates authenticated holdings to `shop.repository.ts`; migration **071** defines `user_items` with owner/catalog PK, nonnegative integer quantity and nullable `expires_at`. Migration **123** defines `shop_my_items_v2(p_actor)`, filters owner, quantity>0 and unexpired holdings, but calls `clock_timestamp()` separately and returns `effect_expires_at` independently from effect receipts. A holding expiration is **not** an effect expiration, arrears proof, active-use guarantee or alert delivery. F675-199 calendar, F675-200 ICS, F675-201 saved views and F675-202 default preference are all **proposals, not deployed dependencies**.
- **Alternatives:** A, aggregate current unbounded holdings in browser: rejected for 10,001+ item scale and inherited false-empty failure. B, scheduled per-member cache: rejected for stale truth, cross-account privacy and unnecessary background jobs. **Chosen C:** owner-only bounded read-only PostgreSQL aggregate function, typed Nest GET, web/Android gateway parity, zero new table and no monetary/item writes. No feature dependency on F675-199–202.

### Exact API and database contract — PROPOSED, NOT IMPLEMENTED
- **GET** `/api/v1/shop/expiry-urgency` authenticated owner and current consent only, no client-supplied `userId`, `asOf`, category or arbitrary SQL filter. Response `{status:'VERIFIED_COUNTS'|'VERIFIED_EMPTY',asOf:ISO8601Microseconds,timezone:'Asia/Seoul',bands:[{id:'H0_24'|'H24_72'|'H72_168',kindCount:decimalString,unitCount:decimalString}],total7d:{kindCount:decimalString,unitCount:decimalString},nextExpiryAt:ISO8601Microseconds|null}`. All numeric counts are **canonical nonnegative decimal strings**, including >2^53; exact ISO timestamp strings retain PostgreSQL microseconds and are converted to localized display only at the UI boundary. `200` is possible only after complete validated DB results. Reject missing/negative/noninteger/overflowed or inconsistent band/total fields as `503 SOURCE_UNAVAILABLE`, not `[]`. Read limit proposed 30 requests/min per member, `429` with bounded retry guidance; no idempotency receipt or transaction mutation for GET.
- **Single-source SQL:** additive `public.shop_my_expiry_urgency_v1(p_actor uuid)` `STABLE SECURITY DEFINER SET search_path=pg_catalog,pg_temp`; use one READ COMMITTED statement with a single materialized `statement_timestamp()` `asOf` value. Scan only `public.user_items` rows where `user_id=p_actor`, `quantity>0`, `expires_at IS NOT NULL`, `expires_at>asOf`, `expires_at<=asOf+interval '168 hours'`. Disjoint boundaries: `(asOf,asOf+24h]`, `(asOf+24h,asOf+72h]`, `(asOf+72h,asOf+168h]`; exact boundary belongs to the earlier band. `count(*)::bigint` counts **distinct catalog kinds** because owner/catalog is PK; `sum(quantity::bigint)` is computed without JS Number loss, serialized to decimal strings, and `min(expires_at)` is nearest expiry. Total7d equals the exact sum of three bands. `NULL` expiry is **excluded/unknown duration**, not a verified permanent item; expired holdings are excluded. Do not use `effect_expires_at` or coalesce a failed source to zero. A statement snapshot is consistent **only for that one request**; no cross-HTTP snapshot/commit-time guarantee. No new persistent table, materialized view, or scheduled job.
- **ACL/index/transaction:** function owner migrator, `REVOKE ALL ... FROM PUBLIC`, explicit narrow app-role `EXECUTE` only; no direct app-role `user_items` read/write grants, and no use of `p_actor` as proof of authentication—Nest must derive it from the validated session. No transaction writes or ledger effects. Existing PK can serve owner filter; inspect `EXPLAIN (ANALYZE, BUFFERS)` with synthetic 10,001 holdings before considering an optional `(user_id,expires_at)` partial index. A concurrent index requires a separately reviewed nontransactional migration path; never promise no lock without evidence. Allocate a forward-only migration number **after** #2233 migration-318 collision is resolved; do not edit applied checksums.
- **Privacy, SEO, admin, analytics:** actual Nest→Next→Android app-api→Nginx HTTP responses, including errors, must enforce `Cache-Control: private, no-store`, `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`. No owner identifiers, exact quantities, URLs, tokens or timestamps in telemetry, public cache or logs. Aggregate admin KPI only for cohorts >=20: verified load, 503/429 rate, p95 latency and drilldown; target p95 <250ms at 10,001 holdings and 0 shared-cache responses are **proposed targets, not measurements**. No admin member drilldown or new admin write role.
