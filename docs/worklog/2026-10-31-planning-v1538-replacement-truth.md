### Source-level contradiction and user impact
- Migration 071 defines owner+catalog primary key, nonnegative quantity and nullable holding expires_at. Migration 114's inventory_equip_item(p_actor,p_catalog_id,p_slot,p_equip) verifies quantity>0 and allowlisted slot, **but does NOT verify that p_slot matches shop_catalog.category, nor that expires_at is in the future**. Its two UPDATE statements lack a documented per-owner serialization lock/unique slot constraint. A caller can therefore request an incompatible slot or equip an already-expired holding if no later code guards it. This is a source-level gap, NOT proof of actual abuse.
- Migration 114's profile_get_cosmetics(p_target_user_id) is granted PUBLIC EXECUTE, selects is_equipped=true by slot with LIMIT 1 (badge aggregate), and does **not** check quantity or expires_at. A stale/expired or duplicate equipped row can therefore still appear on a public cosmetic profile. This is a public display consistency issue, NOT evidence of unauthorized private inventory access.
- Migration 123's shop_my_items_v2(p_actor) **does** require quantity>0 and (expires_at IS NULL OR expires_at>clock_timestamp()); it omits expired holdings even if is_equipped=true. Thus owner inventory and public cosmetic profile can disagree. Neither read model proves that a proposed replacement can be equipped. The preview must NOT use the filtered holdings function alone to validate all flagged equipped rows or infer successful equip.
- The migration 114 check allows equipped_slot NULL on any row; no invariant requires is_equipped=true iff equipped_slot is non-NULL. Validate both directions, including is_equipped=false with a non-NULL equipped_slot; do not silently normalize or hide anomalies. Existing equip write path is owned by B/DB; this planning run does not change it.
