### Screen/CTA/state and permissions
- On an authorized case show current reminder (or none), due time in the viewer's locale with explicit KST/UTC offset, and Set reminder / Reschedule / Clear reminder. Presets 1h, tomorrow, 7d plus a validated explicit date-time. A reminder is private to the operator who created it; other administrators cannot see or change it solely because they can view the case. A revoked operator cannot retrieve it. No client-supplied adminId or memberId. If a case is resolved, show Resolved — review reminder manually; never automatically clear or reopen.
- My follow-ups has Due, Upcoming and All filters, at most 20 active reminders per administrator, ordered by (due_at ASC,thread_id ASC); the existing support queue remains intact and retains status priority. Due is computed from one DB statement_timestamp() snapshot, not a persisted status. Response scope=ACTIVE_OPERATOR_MAX20 and asOf server time; do not imply full history or a durable multi-request snapshot. Empty means successful authorized query with no matching active reminders, not an outage. LOADING, EMPTY, READY, SAVING, DUE, UPCOMING, CONFLICT, REPLAYED, OFFLINE, FORBIDDEN, UNAVAILABLE and SESSION_EXPIRED are distinct; preserve selected case and form on recoverable errors. No countdown urgency manipulation.
- Nest SessionGuard/AuthenticatedGuard/ConsentGuard/AdminGuard/AdminSessionGuard and recent admin step-up on every read/write; CsrfGuard on writes. SQL independently checks current operator role and thread existence, and actor UUID is NOT independently authenticated by SQL. The v1674 arbitrary-admin-UUID trust boundary and v1670 role-revocation serialization remain P0 gates before flag ON. Never grant moneyverse_app direct DML on reminder, receipt, support or financial tables. Member API/Android must not expose reminder existence, due times, aggregate counts or error distinctions; unauthorized responses are uniformly private.

### Exact proposed API and errors (NOT RUN)
- GET /api/v1/admin/support/followups?view=due|upcoming|all returns {asOf,scope:'ACTIVE_OPERATOR_MAX20',items:[{threadId,subject,status,dueAt,revision,overdue}]} with at most 20 records from a single SQL statement; due uses dueAt<=asOf. Subject/status are fetched only after admin case authorization. No total historical count or cursor is needed under the 20-active cap. GET /api/v1/admin/support/threads/:threadId/followup returns {active,dueAt|null,revision} and ETag strong quoted decimal revision; an absent record has revision 0, cleared tombstone retains its last revision. Inaccessible case returns 404.
- PUT /api/v1/admin/support/threads/:threadId/followup accepts only {dueAt: RFC3339 offset-aware timestamp}, Idempotency-Key: UUID and If-Match: strong quoted decimal revision (including "0"). UTC normalization occurs server-side; a fresh request's dueAt must be >=15 minutes and <=30 days from the DB transaction clock, inclusive, with second precision; reject naive timestamps, invalid DST local times, sub-second or overflowing inputs. Return {active:true,dueAt,revision,replayed:false} and ETag; 201 for first activation, 200 for reschedule or unchanged new-key no-op.
- DELETE /api/v1/admin/support/threads/:threadId/followup takes no body and the same two headers, returns {active:false,dueAt:null,revision,replayed:false}. Clearing an already inactive reminder with a fresh key is a durable no-op (200, no revision/event change). A same-key exact replay after a later clear/reschedule returns the original historical result with replayed:true, never reactivates or changes current state; authenticate first and compare immutable canonical request digest before fresh due-window or CAS checks. Same actor/key with changed action, target, dueAt or expected revision => 409. Missing headers => 428, stale revision => 412, bad data => 422, quota => 409 LIMIT_REACHED, rate limit => 429, dependency unavailable => 503; never map auth/DB faults to an empty queue. 401/403/404 preserve owner privacy. Next BFF /app-api/v1 forwards If-Match, Idempotency-Key and ETag without exposing internal credentials.
- All success and error responses: Cache-Control: private, no-store; X-Robots-Tag: noindex,nofollow. No public sitemap, canonical, share card or indexed case metadata.

### Forward-only PostgreSQL contract, indexes and concurrency
- Use the next actually available unique migration number (do not modify applied 196). Proposed support_admin_followups has admin_id UUID REFERENCES users(id), thread_id UUID REFERENCES support_threads(id), active BOOLEAN NOT NULL, due_at TIMESTAMPTZ NULL, revision BIGINT NOT NULL CHECK(revision>=1), created_at/updated_at/cleared_at TIMESTAMPTZ, PRIMARY KEY(admin_id,thread_id), CHECK(active=(due_at IS NOT NULL)), CHECK(active OR cleared_at IS NOT NULL). No row represents revision 0; clearing retains a tombstone and increments revision only on a real change. Never delete tombstones while CAS/replay protection is required. Partial index (admin_id,due_at,thread_id) WHERE active; no index on message bodies. Cap at 20 active rows per admin; never silently evict an old reminder.
- Proposed support_admin_followup_receipts has (actor_id,idempotency_key UUID) UNIQUE, thread_id, action, expected_revision BIGINT, canonical HMAC request digest, immutable original HTTP result/revision/dueAt and nullable event_id, created_at and reviewed retention deadline. Keep only minimum metadata; no note, message body, email or member contact details. HMAC secret lives outside DB, with documented key rotation and replay window. Receipt is inserted for a successful mutation AND a successful no-op. An append-only minimal audit event is written only on actual changes. Never assert infinite retention without policy approval.
- Transaction order: authenticate real session and CSRF in Nest → lock operator users row under the shared role-revocation protocol → DB current-role recheck → lock target support_threads row → serialize actor/key receipt → lock followup row/tombstone → check strong expected revision and 20-active quota while holding the operator lock → write row, immutable receipt and optional audit event atomically. If an audit write fails, rollback all. On same-key replay, after current authorization and digest check, return immutable historical outcome without applying a write even if dueAt is now in the past or revision changed. Concurrent first inserts use PK conflict serialization; simultaneous set/clear cannot produce two active rows or exceed 20. If operator identity cannot be bound safely across Nest/DB, fail closed and keep flag OFF. SECURITY DEFINER functions pin search_path, explicitly qualify relations, REVOKE PUBLIC and grant only reviewed EXECUTE to moneyverse_app; no direct table SELECT/UPDATE/DELETE/TRUNCATE/TRIGGER grants.
- Privacy lifecycle: deletion/retention/legal-hold ordering must cover support_messages, support_admin_followups, receipts, audit and support_threads/users (migration 196 has non-cascading user FKs). Revoke hides reminders immediately, but approved deletion/pseudonymization and replay tombstones must be reconciled; do not promise instant physical erasure or retain operator identity indefinitely. No automatic status, assignee, message, member notification, WLD, item, or ledger changes.
