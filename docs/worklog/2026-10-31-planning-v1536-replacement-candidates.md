### Source truth and product decision
- Migration 071: user_items PK(user_id,catalog_id), quantity >=0, expires_at nullable; catalog has mutable name, category and active flag. Migration 114: eight equipped slots (frame, background, effect, nameplate, title, badge_1/2/3); no per-owner unique equipped-slot constraint and no category/slot coherence check. Existing inventory_equip_item accepts caller slot and performs two UPDATEs. Migration 123: shop_my_items_v2 exposes current holdings and upkeep/effect status; NULL expiry is not proof of perpetual ownership, arrears=0 is not proof of payment.
- Actual Next /inventory inventory-view displays active cosmetics and performs POST /api/v1/shop/holdings/:id/equip. Nest GET /api/v1/shop/holdings calls owner-scoped shop_my_items_v2; no member replacement candidate preview route exists on the inspected main. The predecessor F675-188 expiry radar and F675-189 equipped impact are unmerged DRAFT/OFF. This feature must not display a dead CTA before both dependencies are enabled.
- Chosen feature: for an affected equipped slot, let the owner inspect OTHER ALREADY-OWNED, same-category, currently unequipped holdings as manual review candidates. No auto-equip, loadout preset duplication (#1142), calendar/ICS duplication (#1267), purchase upsell, refund, WLD transaction, guaranteed equip eligibility, upkeep settlement, or future effect claim. The member may navigate to the existing inventory to manually equip only after source revalidation.
- Alternatives: (A) client filter over current /inventory (rejected: false-empty on outage, unsound expiry clock and cross-page staleness); (B) owner-scoped read-only SQL + strict API (selected); (C) automatic replacement and payment (rejected: unapproved money/equipment mutations).

### API, SQL, DB invariants, pagination, and transaction
- Nest GET /api/v1/shop/holdings/expiring/equipped-impact/replacements; Next BFF GET /api/shop/holdings/expiring/equipped-impact/replacements; Android GET /app-api/v1/shop/holdings/expiring/equipped-impact/replacements. Query slot, withinDays=7|30, optional pageSize 1..50 (default 20), optional opaque cursor. Reject duplicates, unknown fields and actor UUID. SessionGuard, AuthenticatedGuard, ConsentGuard; actor requireUserId(request), session requireSession(request).id; server-side flag inventory_equipped_replacements OFF.
- Proposed forward-only SECURITY DEFINER public.shop_my_equipped_replacement_candidates_v1(p_actor uuid,p_slot text,p_within_days integer), fixed search_path pg_catalog,pg_temp, schema-qualified relations, owner WHERE ui.user_id=p_actor inside function; revoke PUBLIC EXECUTE, grant moneyverse_app EXECUTE only; no direct SELECT/INSERT/UPDATE/DELETE grants. App role must not read raw user_items/catalog by bypass. SECURITY DEFINER actor argument alone is not a cryptographic session identity proof: HTTP guard must bind actor to authenticated session, and threat-model a compromised SQL caller.
- One DB-authoritative statement_timestamp() inside ONE SQL statement, with a single PoolClient READ ONLY REPEATABLE READ transaction if multiple statements are unavoidable. Validate ALL flagged-equipped rows before candidate filtering: duplicate slot (even outside horizon), NULL/invalid slot, category mismatch (badge slots require badge), quantity <=0 => 409 EQUIPMENT_SOURCE_CONFLICT. Expired-but-equipped flag is a warning, NOT proof of auto-unequip. Target slot must actually have a holding expiring in (asOf,asOf+withinDays*24h]; else 409 TARGET_NOT_IMPACTED, not a generic inventory search.
- Candidates: same category as slot, ui.quantity>0, ui.is_equipped=false, ui.catalog_id != target equipped catalog_id, ui.expires_at IS NULL OR ui.expires_at>asOf. Include inactive catalog owned rows, label them; NULL expiry UNKNOWN, never "permanent". Do not treat suspended=false, arrears_due=0 or an effect receipt as verified equip entitlement. If actual equip eligibility requires additional business rules, display REVIEW_ONLY and do not assert success.
- Sort by (sc.name COLLATE "C" ASC, sc.id ASC); keyset cursor HMAC-SHA256 bound to actor, session, slot, withinDays, asOfUtc, validUntilUtc, sourceFingerprint, lastName and lastCatalogId; TTL <=15min. Strict cursor parsing and constant-time MAC compare, key rotation. Fingerprint covers FULL owner equipped set and FULL same-category candidate set (including outside current page): catalog_id, quantity, category, current name, expiry microseconds, is_equipped, catalog active. Recompute per request; any change => 409 SOURCE_CHANGED; do not pretend cross-request snapshot isolation.
- validUntilUtc=min(asOf+60s, earliest candidate known expiry, target impacted equipped expiry, earliest future equipped horizon-entry boundary). At DB now>=validUntilUtc, reject stale 409 including VERIFIED_EMPTY; cursor expired 410. No partial page if source invalid, no LIMIT 1 to conceal duplicates, no precision loss in UTC microseconds. Use existing PK (user_id,catalog_id), catalog PK(id), existing equipped index; propose an additional index only after EXPLAIN ANALYZE on 10,001 synthetic holdings shows a regression. No new table or mutation.
- **Cursor-page clock contract:** first page pins asOfUtc=the single statement_timestamp(); a subsequent page supplies the server-verified signed cursor asOfUtc to the read function, while that SAME statement captures fresh dbNow=statement_timestamp() to check dbNow<validUntilUtc and re-evaluate full-set source fingerprint against pinned asOf. The cursor may not reset asOfUtc, validUntilUtc, horizon or sort. A function returning all 10,001 rows to Nest for JS pagination is prohibited: SQL keyset applies p_after_name/p_after_catalog_id and p_limit<=51, while the fingerprint/invariant subquery still covers the full owner set. Source changes or time boundary return 409 before emitting any partial page; p95 must be measured against the real SQL plan.
- Strict 200 DTO: {asOfUtc,validUntilUtc,slot,withinDays,candidates:[{catalogId,currentName,quantity,holdingExpiresAtUtc|null,catalogActive,reviewStatus:'REVIEW_ONLY'}],nextCursor:null|string,sourceStatus:'VERIFIED'}. Errors 400/401/403/409/410/429/503 with stable error codes. No payment, idempotency key, money ledger transaction, outbox write or background job in this feature.
