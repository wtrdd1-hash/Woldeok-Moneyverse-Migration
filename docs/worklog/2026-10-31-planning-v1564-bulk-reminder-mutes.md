### Purpose, target, choices and entry
- **Purpose:** an owner with many held items can safely mute or restore the 7-day and/or 1-day expiry reminder for up to 50 explicitly selected holdings at once. This reduces repetitive per-item work without changing inventory ownership, expiry, purchases, WLD or ledger balances. Target: authenticated member with current consent, never a staff impersonation or another owner's items.
- **Verified source:** migration 071 defines `public.user_items` composite PK (user_id,catalog_id), nonnegative quantity and nullable expires_at; migration 123's `shop_my_items_v2` is a filtered read model. `backend/src/shop/shop.controller.ts` has guarded GET /shop/holdings but no bulk reminder mutation. `frontend/src/app/inventory/page.tsx` currently treats failed `apiOrNull` as an empty inventory. Existing F675-192–196 notification/holding-generation proposals are not yet implemented; the new bulk feature MUST remain blocked until their exact schemas, mutes and workers are independently proven.
- **Alternatives:** A) repeat single-item POST 50 times risks partial updates and races; B) an unbounded 'select all search results' would silently mutate thousands and create high lock contention; **choose C)** one bounded owner-scoped atomic operation over 1–50 visible, explicitly selected items. No background job, no bulk 10,001-item mutation and no extra notification channel.
- **Entry:** /inventory → /inventory/expiring/reminders/items → 'Manage several items' → /inventory/expiring/reminders/items/bulk. Select visible rows (maximum 50, no hidden all-pages selection), choose Mute/Restore and threshold 7 days/1 day/both, then Review changes → Confirm. 'Clear selection', 'Back', and post-commit 'Reverse by new request' are distinct accessible CTAs; never imply rollback of already-committed events.
- **States:** LOADING, GLOBAL_OFF (link to settings, no mutations), VERIFIED_EMPTY, SELECTING, REVIEWING, SAVING, VERIFIED_COMMITTED (changed/unchanged counts), STALE_SELECTION (409, reselect), INVALID_SELECTION (400/413), RATE_LIMITED (429), AUTH/CONSENT_REQUIRED, SOURCE_UNAVAILABLE (503), UNKNOWN_COMMIT (timeout after submit; reconcile idempotency receipt before retry). Never show source failure as zero holdings or a successful mute.

### Owner API and exact contracts
- Reuse the F675-195 owner-scoped paginated mute list/read model. New Nest `POST /api/v1/shop/expiry-reminders/mutes/bulk/preview` and `POST /api/v1/shop/expiry-reminders/mutes/bulk/apply`; SessionGuard+AuthenticatedGuard+ConsentGuard+CsrfGuard on both, server-derived actor UUID only. No private state in GET query, URLs, logs or analytics. Android `/app-api/v1/...` routes preserve identical actor, status and privacy semantics.
- Preview body `{action:'mute'|'restore',thresholds:[7]|[1]|[7,1],holdings:[{catalogId:UUID,expectedHoldingToken:string}],expectedPreferenceRevision:string}` with 1–50 **distinct** catalog UUIDs, <=16KiB total, deterministic UUID ordering. Reply `{selectedCount,willChangeCount,alreadyMatchingCount,previewToken,expiresAtUtc,preferenceRevision}`; 120-second HMAC token binds owner+session+action+thresholds+sorted exact item tokens+revision+issued time, without exposing underlying microsecond expiry in JavaScript Date.
- Apply body is the same selection plus `previewToken` and `idempotencyKey:UUID`. Response `{receiptId,changedCount,unchangedCount,committedAtUtc,preferenceRevision}`. On stale revision, changed generation/expiry, expired token or missing owner holding, return 409 and change **zero** rows; never partially succeed. 400 malformed/duplicates/empty, 401 unauthenticated, 403 missing consent/CSRF, 413 oversize, 429 quota, 503 unverified schema or DB. A network timeout is UNKNOWN, not failed or committed, until receipt reconciliation.
- Limit 5 apply batches per owner per minute, 50 items each, with bounded server-side token verification and no unbounded `IN` queries. No public SEO page; private/no-store/noindex/no-referrer for 2xx/3xx/4xx/5xx including the Next edge and Android proxy. Owner switch invalidates in-flight results and tokens.

### DB, locking, index, consistency and abuse protection
- **Prerequisites:** Backend B must first implement and verify F675-195's DB-owned monotonic holding generation across 0→positive, same-expiry reacquisition, expiry change and all purchase/reward/consume writers. Exact PostgreSQL timestamptz microseconds are authoritative; JS Date is never a write precondition. Reuse parent per-item mute rows and global opt-in/revision; no speculative migration number or direct `moneyverse_app` table grants.
- Add only if needed an owner+idempotency_key UNIQUE bulk receipt with request_digest, commit counts and committed_at; `CHECK(changed_count>=0 AND unchanged_count>=0 AND changed_count+unchanged_count<=50)`; owner+catalog_id UNIQUE on mute rows and owner+updated_at index for recent receipt reconciliation. All owner reads/mutations via fixed-search_path `SECURITY DEFINER` functions, explicit revoked table privileges and narrowly granted EXECUTE. Validate `p_actor` from authenticated Nest session; SQL actor argument alone is not authentication.
- **One transaction:** acquire owner preference row/revision lock → validate global opt-in ON → validate signed preview and idempotency request digest → lock selected holdings in ascending catalog UUID order → validate quantity>0, not expired, exact generation+expiry, and current revision → lock selected mute rows in same order → write all requested thresholds and one receipt → commit. The existing digest/individual worker must follow compatible lock order; a mute committed before worker commit suppresses pending delivery, a restore after 09:00 digest slot does NOT retroactively qualify for that slot. If any check fails, rollback the entire selection.
- Replaying the same owner+idempotency UUID with the same request digest returns the same committed receipt without extra writes; same UUID with different digest returns 409. On concurrent apply, UNIQUE receipt and serializable/explicit locking semantics must be proven in isolated PG17, not assumed. Do not disclose whether another owner's catalog holding exists; enforce owner-scoped 404/409 without cross-owner information. Never write account_balances, ledger_postings, Treasury, item quantity or effect expiry.
- **Operator/KPI:** no raw owner IDs, item names or per-owner history in admin dashboards; expose only cohort>=20 member aggregates (bulk preview→confirm conversion, committed/unchanged, 409/429/503, p95 response time, privacy rejection counts). Proposed p95<300ms for 50-row preview/apply is a target, not a measured result; test and adjust before rollout.
