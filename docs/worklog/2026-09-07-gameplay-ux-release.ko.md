## 주요 발견

### 작업
- 새 DB에서 레거시/현재 작업 카탈로그의 활성 과제 수가 달라질 수 있었습니다.
- 과거 배정 경로가 활성 직업 기대값을 우회할 수 있었습니다.
- 서로 다른 두 레벨 공식이 같은 EXP를 다른 레벨로 해석할 수 있었습니다.
- 일반 레거시 작업 보상이 병렬 WLD 공급원처럼 동작했습니다.
- 네트워크 응답이 느리면 정산이 끝났어도 완료 모달이 멈춘 것처럼 보일 수 있었습니다.

### 카지노
- 서버 영수증은 패배인데 테마 애니메이션이 잭팟을 보여줄 수 있었습니다.
- 지급 수치가 서버 조건이 아니라 프론트엔드 문구에 중복 하드코딩되어 있었습니다.
- 최근 게임 기록이 작은 일반 지갑 피드에 잘못 의존했습니다.
- 자체 잠금 문구가 실제 플레이 잠금/자기 배제라는 의미를 충분히 설명하지 못했습니다.
- 관찰된 회원 현금/작업 보상 규모에 비해 플랫폼 노출 한도가 너무 느슨했습니다.

### 은행
- 표시/수동 예금 금리와 자동 금리가 서로 어긋났습니다.
- 매우 작은 이자가 1 WLD로 강제 올림되어 반복 청구될 수 있었습니다.
- 예금 시점 처리 때문에 새로 변경된 잔액에 과거 경과 시간이 적용될 위험이 있었습니다.
- smart-loan 경로가 기존 신용등급 대출 정책을 우회했습니다.

### 배포 / 소스 드리프트
- 테스트된 런타임/보안 수정 일부가 스택에 직접 적용됐지만 `main`에 보존되지 않아 다음 배포가 되돌릴 수 있었습니다.
- CI 런타임 버전이 Production보다 뒤처졌습니다.
- 강화된 Host 동작과 오래된 로컬 스모크 테스트가 충돌했습니다.
- 수동 Production 백업이 실수로 Test 배포 디렉터리를 기본값으로 선택할 수 있었습니다.
- Test 마이그레이션 체크섬 하나가 초안이었고 Production/소스에는 기준 형태가 있었습니다.

## 해결 전략
1. 오래된 문서보다 실제 서버/DB 상태를 우선합니다.
2. 사용자 데이터/원장 이력을 보존합니다.
3. 발견된 동작을 회귀 테스트로 전환합니다.
4. 새 PostgreSQL 17.11 DB에서 검증합니다.
5. Test에서 canary를 수행합니다.
6. Production 백업을 생성하고 검증합니다.
7. Production에 배포합니다.
8. 다음 배포가 수정사항을 되돌리지 않도록 소스를 `main`에 반영합니다.
9. 공식 GitHub Test/Production 워크플로를 실행하고 커밋 태그 이미지를 확인합니다.

## 최종 게임플레이/경제 기준
### 작업
- 직업 8개 × 현재 과제 3개 = 활성 과제 24개
- 회원당 활성 직업 1개
- 하나의 레벨 공식과 반복 가능한 과제 보상
- 타임아웃에 안전한 멱등성 완료 UX

### 카지노
- 공개 핵심 게임 기준 RTP 95%
- 1회 10–200 WLD
- 일일 플랫폼 베팅 노출 2,000 WLD
- 일일 실현 손실 노출 1,000 WLD
- 회원 자체 제한/자기 배제는 더 엄격하게 설정 가능

### 은행
- 표시/정산에 하나의 이자 계약
- 강제 최소 1 WLD 지급 없음
- 잔액 변경 시 누적 시간 재설정
- 새 대출은 신용등급 정책 사용
