## v1424 / F675-162 — Verified, opt-in member collection showcase (FEATURE ADDITION / DRAFT / RELEASE HOLD)

### 1. Observed behavior, user need, scope and exclusions
- In frontend/src/app/collections/curation-retention-flow.tsx, the showcase modal copies a fixed /collections?showcase=arch-1063 link regardless of member or selection. The collections page does not implement a public resolver for that query. DEFAULT_PIECES render immediately; failed fetch may show browser localStorage content. Neither a copied URL nor cached display proves server ownership.
- backend/src/collection/collection.repository.ts calls ensureSeedPieces() on GET and inserts four example awards when a member has no rows; it also directly SELECTs and UPDATEs public.user_collections. Migration 232 defines a unique (user_id,code) row but no trusted award event, issuer identity, or proof binding. These are **code-backed trust and privacy design gaps**, not evidence of an exploited Production incident.
- **Goal:** allow a member to choose genuinely evidenced collection pieces and deliberately create a revocable, expiring unlisted showcase link, without exposing private notes, financial balances, or other members' assets. **Audience:** authenticated consenting member; a recipient holding an unlisted link; authorized admin only for provenance/audit, never to fabricate awards. **Success:** no fake verified claims, no cross-account leakage, correct revocation/expiry, mobile parity and accessible states.
- **Out of scope:** creating or granting collection awards, WLD rewards, financial transfers, inventory marketplace, public searchable galleries, third-party verification or irreversible deletion of already viewed material. Existing seeded pieces must remain explicitly UNVERIFIED until independent evidence can be reconciled; do not silently backfill a verified flag.

### 2. User journey, screen/CTA/state contract
1. Member enters /collections (authenticated) and sees a clearly separated **private collection** and **Share verified showcase** action. Show loading, error, verified count and unverified count. Never render DEFAULT_PIECES or localStorage as certified ownership; if network fails, show an unavailable state with retry and no publish CTA.
2. Open a privacy dialog: verified-only picker, name/alias preview (default pseudonymous), explicit opt-in checkbox, default 7-day expiration (no indefinite link), warning that recipients may retain screenshots, and a clear **Create private link** CTA. Disabled if there are zero independently verified pieces or provenance verification is unavailable.
3. After successful create, server returns one 192-bit random URL token once. UI offers **Copy link**, **Preview**, **Revoke**, expiration timestamp, and a manage-links view (maximum five concurrently active). Copy failure is reported; no success toast before clipboard confirmation. Browser refresh lists metadata only, never the original bearer token; rotate/create new token if lost.
4. Recipient opens /collections/showcase/[token]. Server returns only allowlisted, currently verified snapshot fields (display alias, piece name, rarity, award date rounded to day, vetted public provenance summary). No member ID, note, internal evidence ID, account data, financial balance, raw storage key, or private URL. Show expired, revoked, unavailable and not-found as a uniform non-enumerating public 404. Feature OFF also denies public reads.
5. Member can revoke in /collections at any time. UI confirms, persists server acknowledgement and invalidates cached link previews; a prior download/screenshot cannot be recalled. Logout/account switch immediately clears previous member links, tokens, preview and in-flight responses. Read-only preview does not itself publish.
6. Operator can inspect aggregated issuance evidence and abuse signals with audit access, but cannot override absent evidence into VERIFIED, reveal token secrets or access members' notes through public showcase APIs. Public pages are noindex/nofollow with no social previews of member-private content.

### 3. API contract and authorization
- Existing GET /api/v1/collections and PUT /api/v1/collections/:id stay backward compatible but must stop implicit write-on-GET and distinguish display-only seeded records from verified issuance. No broad app-role table grants as a shortcut.
- Authenticated GET /api/v1/collections/showcases returns member-owned metadata only: showcaseId, status, createdAt, expiresAt, revokedAt, verifiedPieceCount, never raw token. Authenticated POST /api/v1/collections/showcases body {pieceIds: uuid[1..20], displayAlias?: string, expiresInDays: 7, idempotencyKey: uuid} returns {showcaseId, shareUrl, expiresAt, replayed:false} on first create. On exact idempotent replay, return original result metadata but **do not re-emit bearer token**; client must create a new token if lost. Reuse of key with changed payload is HTTP 409. Authenticated DELETE /api/v1/collections/showcases/:id body {idempotencyKey:uuid} returns {showcaseId, revokedAt, replayed}; repeated identical revoke is stable.
- Public GET /api/v1/collections/showcases/public/:token is rate-limited and no-store, with uniform 404 for absent/expired/revoked/feature-off. Do not leak whether a member or piece exists; token length, encoding and rate limits are validated before DB lookup. Next.js route /collections/showcase/[token] is a thin no-store BFF and must not embed the token in logs or analytics.
- App API /app-api/v1/collections/showcases and /app-api/v1/collections/showcases/:id mirror authenticated web contracts with session binding; public token view is browser-only unless Android has an explicit deep-link safe resolver. Version the shared contract and route map; CSRF/session/consent guards for writes; no caller-supplied actorId.

### 4. PostgreSQL model, constraints, indices, transactions and trust boundary
- Proposed migration, number assigned only by development owner after checking main migration tip: append-only collection_award_receipts(id uuid PK, owner_id uuid FK, piece_id uuid FK, issuer_type enum, source_kind enum, source_event_id text, evidence_digest bytea, awarded_at timestamptz, verified_at timestamptz nullable, revoked_at timestamptz nullable, created_at); UNIQUE(source_kind,source_event_id,owner_id,piece_id), CHECK evidence_digest length and timestamps. No automatic receipt generation for legacy seed pieces. Verified means an authenticated issuer/source event is independently resolved, not a user-editable provenance string.
- collection_showcases(id uuid PK, owner_id uuid FK, token_digest bytea UNIQUE NOT NULL, alias text CHECK length 1..40, created_at, expires_at, revoked_at, request_id uuid, request_hash bytea); CHECK expires_at > created_at AND expires_at <= created_at + interval '7 days'; UNIQUE(owner_id,request_id). Store token SHA-256/HMAC digest only, not raw token. Add (owner_id, created_at DESC,id DESC), (expires_at) partial active index, and UNIQUE token digest. collection_showcase_items(showcase_id FK ON DELETE RESTRICT, award_receipt_id FK ON DELETE RESTRICT, ordinal int CHECK 1..20, PRIMARY KEY(showcase_id,award_receipt_id), UNIQUE(showcase_id,ordinal)).
- **Create transaction:** lock actor's stable owner row FOR UPDATE to serialize five-link quota; check active member, feature ON, 1..20 unique receipt IDs, independently verified and not revoked, same owner; verify evidence chain; insert showcase and selected receipts with immutable request hash, all-or-nothing. Do not issue WLD, call economy functions, mutate collection balances or create proof as a side effect.
- **Read transaction:** derive digest from validated opaque token, lock showcase row FOR SHARE (or equivalent ordered locking) and recheck expiry/revocation/flag; only join owner-verified, non-revoked receipts and sanitized display fields. If any selected award has been revoked, fail closed or omit it with a visible redacted status; never serve stale verified claims. **Revoke transaction:** lock showcase row FOR UPDATE and persist revocation, invalidating later reads; define concurrent in-flight read semantics, with no-store to avoid post-revoke caching. Feature OFF denies public reads immediately.
- SECURITY DEFINER functions with SET search_path = pg_catalog, pg_temp and explicit schema-qualified objects; authenticate actor from server session and validate membership inside functions. REVOKE direct SELECT/INSERT/UPDATE/DELETE on showcase/proof tables from moneyverse_app and PUBLIC; grant only needed EXECUTE. Audit both privileges and no-op/foreign-owner refusals in isolated real PostgreSQL; do not grant direct access to fix a 42501.

### 5. Admin, security, privacy, SEO, analytics, accessibility
- Admin dashboard: verified-source counts, orphan/invalid evidence counts, active/revoked/expired links, abuse rate, issuer review and immutable audit; no raw token, no private notes, no unapproved manual award grant. Separate operator and superadmin permissions, record operator ID and reason for evidence revocation.
- Abuse controls: entropy >=192 bits, constant-time token digest comparison where relevant, per-IP and per-account rate limits, enumeration-resistant 404, request UUID payload binding, CSP and safe link handling, strict Referrer-Policy: no-referrer, Cache-Control: private/no-store on owner and no-store on public, no third-party scripts on token pages, no token in request telemetry, screenshots or error traces. Protect against CSRF, XSS in alias and provenance, link preview bots, account switching and expired tokens.
- SEO: private /collections remains noindex; token pages set robots noindex,nofollow,noarchive and X-Robots-Tag, no sitemap or canonical to a token URL, no indexable OpenGraph member data. Analytics record aggregate verified-preview/create/revoke/expiry and failure counts without token, actor ID or raw evidence; baseline to be measured, target zero unauthorized disclosures, 100% revoke enforcement and zero false VERIFIED labels.
- WCAG 2.2 AA: keyboard focus trap and return, accessible dialog name, live region for copy/revoke feedback, visible expiry and state, touch targets, no color-only status, responsive 320px viewport, screen-reader-tested 404 and error states. Android app-api behavior must not diverge from web.
