### Verified design gap and alternatives
- v1560 correctly defined a 09:00 KST digest and half-open 7d/1d decision windows, but it derives the decision day and eligibility from **post-lock execution clock**. A delayed worker at 09:07 and an on-time worker at 09:00 can select different threshold boundaries; a retry around KST midnight/decision date can mis-key a batch. The signed receipt and UNIQUE owner/day prevent duplicates, **not** inconsistent membership or false missed-window claims. This is a specification risk, not a confirmed deployed bug.
- **Chosen:** immutable **scheduled decision slot** `decisionDateKst` + DB-computed `slotAtUtc` (09:00 Asia/Seoul; presently 00:00 UTC) for every window and batch key; use post-lock `clock_timestamp()` separately for current-source validation and execution cutoff. Reject alternatives: client-derived Date (timezone/precision drift), using worker start time as window anchor (retry drift), automatic backfill (stale/misleading alerts), and sending a partial digest after a timeout (false completeness). Worker runs are at-least-once; committed inbox is at-most-once per owner/slot, **not** guaranteed delivery.
- **Proposed bounded execution gate:** accept processing only while DB time `slotAtUtc <= now < slotAtUtc+15 minutes`; 15 minutes is an **unmeasured configurable proposal**, not an SLO. Recheck DB time immediately before atomic commit. Before slot → WAIT; at or beyond cutoff → MISSED_NO_SEND with verified worker/slot evidence; no catch-up. If the database is down or no worker ran, mark UNKNOWN/UNVERIFIED, never infer MISSED from missing inbox rows. Two workers racing on same owner/slot must converge to one terminal outcome; a retry within grace may resume only after a rollback, not double-commit.
- **Exact eligibility math:** for each immutable holding expiry E, threshold 7d qualifies at slot S iff `E-168h <= S < E-144h` (equiv `144h < E-S <= 168h`); threshold 1d iff `E-24h <= S < E` (equiv `0 < E-S <= 24h`). Use PostgreSQL timestamptz microseconds, fixed UTC hours and DB timezone conversion; do not convert expiry to JavaScript Date. Example: at S=2026-11-01 00:00:00Z, E=S+168h qualifies 7d, E=S+144h does NOT; E=S+24h qualifies 1d, E=S does NOT. ±1µs tests are mandatory.

### Preference/holding races and owner UX
- **Prevent late opt-in:** store server-verified `digest_enabled_since_utc` for the current uninterrupted ON interval. A slot is eligible only if enabled_since < S and the global preference remains ON when the owner transaction locks and commits. Enabling/re-enabling at or after 09:00 applies from the next decision slot; disabling/mode switch to individual at any time before commit suppresses unsent digest immediately. A post-commit change never retracts a committed inbox. Store `mode_revision` and an idempotency-key/payload binding; 409 stale, 503 missing history. This avoids retroactive enrollment after a late worker starts.
- **Prevent retroactive unmute/acquisition:** per-holding `generation_started_at`, `expiry_version_changed_at` and `last_unmuted_at` (or equivalent auditable transition evidence) must predate S for inclusion; a mute set before commit always suppresses. A newly acquired holding, expiry changed, or unmute at/after S is deferred to the next slot, not silently included in a delayed run. If these provenance fields cannot be proved across migrations 071/072/103/165 and all writers, **BLOCK** digest rather than fabricate an as-of snapshot. All owner preferences, holding generations, mutes and receipts rechecked under a documented lock order before commit; no cross-owner leakage.
