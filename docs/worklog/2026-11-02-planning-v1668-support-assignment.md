## Purpose, target and verified source gap

**Purpose:** prevent two administrators unintentionally duplicating support work and make explicit handoff visible without locking members out of replies. **Target:** authorized administrator in `/admin/support`; members retain the existing `/support` conversation without an assignee identity, response-time guarantee or new monetary entitlement. **Evidence:** migration 196 `support_threads` has status/subject/last_message_at but no assignee or assignment revision; `admin_support_threads` orders open → waiting_user → resolved; Nest AdminSupportController exposes list/messages/reply/status, not assignment. AdminSupportView has no Claim/Transfer controls. Read-only live PostgreSQL 17.11 query: 3 threads/6 messages, no `assigned_admin_id` or `support_assignment_events`, `moneyverse_app` effective account_balances UPDATE/TRUNCATE true. These are a verified capability gap and permission risk, **not proof of an actual duplicate-response incident**.

## Alternatives and chosen scope

**A. Client-only 'handling' badge:** rejected because it cannot coordinate two admins or survive refresh. **B. Hard exclusive lock / auto-expiring lease:** rejected because a disconnected operator could block replies and expiration could trigger unsafe takeover. **C. Recommended V1:** durable, **advisory** one-assignee-per-thread with DB-serialized CAS, explicit handoff/takeover and audit. Assignment never changes who may read/reply/status-change under existing administrator authorization. No automatic assignment, no SLA or priority escalation, no member-facing staff identity, no WLD/item/ledger write. Category triage F675-222 is optional enrichment, not a prerequisite for safe assignment.

## Roles, entry points and UI/CTA states

Authenticated + consent-current + AdminGuard + recent AdminSessionGuard administrators open `/admin/support`; filters: All, Unassigned, Assigned to me, Assigned to others, Stale (assigned to no-longer-authorized account, or unchanged for >=24h; 24h is **visual warning only**, not expiry). Thread detail shows assigned operator **only to admins**, assignment revision and verified updated time. Buttons: **Claim** (unassigned), **Release** (self), **Transfer** (current assignee → verified active admin), **Take over** (other assignee; mandatory reason enum `handoff_unavailable|coverage|escalation`, explicit confirmation), **Refresh** on 409, **Retry** on 503, disabled pending on submission. Transfer target must be selected from verified active-admin picker, not arbitrary user UUID. Unassigned/verified-empty, loading, unauthorized, revoked role, stale data, 409 conflict, 429, 503 and unknown-source are distinct states. Never silently claim a case or infer assignment from who last replied. Keep original open→waiting_user→resolved ordering and within-status last_message_at DESC,id DESC; assignment filters do not reorder unless explicitly opted in.

## Proposed HTTP contracts (all admin-only, private)

`GET /api/v1/admin/support/assignments?status=&assignment=all|unassigned|mine|others|stale&cursor=` returns bounded 50+1 list with `threadId`, `status`, `assignmentState`, `assigneeDisplay` (admin only), `assignmentRevision` as decimal string, `assignedAt`, `assignmentUpdatedAt`, `nextCursor`, `sourceRevision`; no message body in list, no fabricated counts. Reuse existing status-rank sort and source-proof cursor rules from F675-222 only if implemented; otherwise a standalone verified bounded read function. Cursor binds admin/session, normalized filters, rank, microsecond last_message_at, UUID, source revision, 5-min expiry; AES-256-GCM authenticated encryption with key rotation, 409 on source change, 410 expired, never partial success. Avoid `/threads/:id/messages/:messageId` route collision.

`POST /api/v1/admin/support/threads/:id/assignment` claims unassigned case. `PUT /api/v1/admin/support/threads/:id/assignment` transfers/takes over with `targetAdminId`, `reason` when takeover; `DELETE /api/v1/admin/support/threads/:id/assignment` releases only self unless explicit audited takeover path. All mutations require `expectedAssignmentRevision` (base-10 string), UUID `idempotencyKey`, CSRF and recent admin session. Responses return `threadId`, `assignmentRevision`, `assigneeId` (admin only), immutable `eventId`, `outcome`, `changedAt`; same-key/same-canonical-payload replay returns original receipt even if current revision advanced. Same key different payload → 409 `IDEMPOTENCY_CONFLICT`; different key stale revision → 409 `ASSIGNMENT_CHANGED`; unknown thread → non-disclosing 404; invalid → 400, unauthorized → 401/403, throttle → 429, DB/source failure → 503. Do not respond 200 with unverified empty assignment.

## DB schema, constraints, indexes, permissions and transaction semantics

Forward-only migration after **current unique migration head** (do not reserve a conflicting number) adds `support_thread_assignments(thread_id uuid PRIMARY KEY REFERENCES support_threads(id), assignee_admin_id uuid NULL REFERENCES users(id), assignment_revision bigint NOT NULL DEFAULT 0 CHECK >=0, assigned_at timestamptz NULL, updated_at timestamptz NOT NULL)`; one current assignment per thread by PK; null assignee is explicit verified-unassigned, not 'never checked'. Backfill existing threads as unassigned revision 0, no invented owner. Add `support_assignment_events(event_id uuid PK, thread_id, actor_admin_id, previous_admin_id, next_admin_id, operation enum, reason enum nullable, revision bigint, created_at, UNIQUE(thread_id,revision))` and immutable `support_assignment_receipts(actor_admin_id,idempotency_key,operation_version,request_hmac,key_version,event_id,receipt_payload,created_at, retention_state, UNIQUE(actor_admin_id,idempotency_key))`. Receipt must not contain member subject/body; keyed HMAC over canonical actor/thread/operation/target/reason/expected revision prevents low-entropy dictionary attacks. Retention and account-erasure rules require explicit review; preserve minimal tombstone to prevent replay after message/event purge; never retain raw member content indefinitely.

Transaction: authorize actor and target against `admin_current_roles` in the same transaction; acquire support thread row lock then assignment row lock in stable order compatible with reply/status/category migration, verify expected revision and existing immutable receipt **before** applying CAS, check self-release/transfer/takeover policy, write exactly one new event + receipt + revision increment, append existing `admin_append_audit_event` with IDs and reason enum (no message text), commit atomically. Same-key replay returns historical receipt without reapplying, even if current assignee changed. Same-state no-op with a fresh key returns verified current state and **does not** emit a fake transfer event. Role revocation does not silently rewrite data on GET; show `STALE_ASSIGNEE` and require explicit audited takeover. Verify deadlock/retry SQLSTATE and 100 concurrent writers. Index `(assignee_admin_id, updated_at DESC,thread_id)` plus queue status-ranked index only after EXPLAIN; avoid global version hot row and unbounded OFFSET. SECURITY DEFINER with pinned search_path, explicit actor role checks, revoke PUBLIC, grant only EXECUTE to app; **no direct app table DML**.
