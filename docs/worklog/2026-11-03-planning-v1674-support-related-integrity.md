### Source-confirmed failure modes and decisions

1. **Actor UUID is not proof of a principal.** Applied migration 196 admin_support_threads checks admin_current_roles(p_actor), but p_actor is a caller-supplied UUID. Nest SupportController derives it from requireUserId(req) behind Session/Authenticated/Consent/Admin/AdminSession guards. SQL role lookup can validate the *supplied* account's current role; it does not cryptographically authenticate the caller or independently bind an HTTP session. Do not claim otherwise. P0 security review must test arbitrary-actor function calls as moneyverse_app, assess role-spoof blast radius, and approve an authenticated principal-binding design or explicitly document residual trusted-backend boundary before feature ON. No new direct app-role table grants; preserve CSRF and private edge.
2. **Fresh-key no-op lacks an explicit durable receipt.** v1672 says a new key against an already-active pair returns 200 but only specifies immutable receipts for changes. Without a no-op receipt, the same key retried after unlink may accidentally re-link. Every accepted link or unlink request, including verified no-op, persists an immutable keyed receipt with original HTTP outcome and optional event_id NULL. Replay checks current authentication and key+canonical payload first, returns original historical result with replayed=true and never changes current state. Changed payload under same actor/key => 409; do not forge a new audit event on replay.
3. **Unconditional link can revive a stale relationship.** v1672 POST has no pair revision precondition; an operator looking at an old screen could re-link after another operator unlinks. Both mutations now require a strong pair revision precondition, including tombstones for previously unlinked pairs. A never-seen pair starts at revision 0; link creates revision 1, unlink increments it, relink increments again. Pair revision never decreases or resets; retain the minimum tombstone needed for safe CAS and approved retention. A stale request is 412, not a silent success. A fresh-key already-active no-op still records a receipt, with no revision/event change.
4. **DELETE with JSON body is not a reliable edge contract.** Supersede v1672 DELETE JSON body: both POST and DELETE require Idempotency-Key: UUID and If-Match: strong quoted pair revision (including rev-0). POST JSON only {relatedThreadId}; DELETE path identifies both threads, with no request body. Missing preconditions => 428; stale => 412; same key changed operation/pair/revision => 409. Return ETag and exact integer revision string. Nest/Next BFF/Android-denial and reverse proxy tests must prove both headers survive; reject weak ETags, unknown fields, malformed UUID and overflow. All mutations are staff-only and CSRF-protected.
5. **Same-owner relationship must survive lifecycle changes safely.** Migration 196 support_threads.user_id and support_messages.sender_user_id reference users without ON DELETE CASCADE. The proposed pair FKs alone cannot guarantee member erasure. Before enabling, specify retention/legal hold, deletion ordering across messages, pairs, receipts, audit and users; use audited pseudonymization where retention requires it and purge relation metadata otherwise. Prevent unsupported support_threads.user_id reassignment (or atomically detach and audit all related edges before reassignment); a mutable owner would otherwise make a historical same-member link cross-member. Check both endpoint owners on EVERY read and write, not only creation. Role revocation uses the same transaction lock protocol as v1670; role changes and link writes cannot race without a reviewed linearization point.
6. **Candidate search is intentionally partial.** Existing index support_threads_user_recent_idx is (user_id,last_message_at DESC,id DESC); no relation table or owner-prefix index exists. Recent-20 candidate picker may omit older matching cases and is not a full archive. Return scope=RECENT_20, hasMore only if a bounded 21st row was actually observed, no total count or 'no other cases' claim; optional NFC/trimmed literal prefix q (3–80 chars) escapes LIKE metacharacters and cannot search other owners. EXPLAIN a 10,001-row same-owner dataset; add a reviewed owner-scoped expression index only if evidence requires it. Status changes/reordering do not assert cross-request snapshot completeness.
