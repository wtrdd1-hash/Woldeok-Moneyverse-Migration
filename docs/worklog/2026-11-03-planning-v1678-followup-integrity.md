### Verified scope and newly identified design hazards
- Source: migration 196 defines support_threads and support_messages with non-cascading user references, no follow-up table; AdminSupportController provides list/messages/reply/status only, and derives actor via requireUserId(req) under Session/Authenticated/Consent/Admin/AdminSession guards. SQL checks a supplied actor UUID's current roles but does not independently bind it to the HTTP session. Treat arbitrary-actor execution and role-revocation serialization as P0 gates, not as solved. The original v1676 one-private-reminder-per-admin-and-thread product scope, max 20 active, no member exposure and flag OFF remain unchanged.
- **Historical replay is not current resource state.** The v1676 contract returns the immutable original PUT/DELETE result on same-key retry, potentially after another request has rescheduled or cleared the reminder. Returning that historical revision as a normal current-resource ETag or painting the historical dueAt as live would corrupt operator expectations. A replay must include replayed:true, originalRevision and original outcome/status, but MUST NOT issue an ETag implying current state; set currentStateVerified:false and require an authorized fresh GET before the UI updates the reminder card. Preserve the original status code for the replay, with Replay-Status: replayed and Cache-Control: private,no-store; never perform a new mutation, emit a second audit event, or treat replay as a fresh due-window validation. Fresh successful mutations retain strong current ETag. The Next BFF must preserve this distinction end-to-end.
- **Canonical request fingerprint and key rotation were underspecified.** Bind the immutable receipt to authenticated actor UUID, target thread UUID, method, API contract version, strong expected revision, and canonical UTC second dueAt (or null for DELETE); reject unknown fields and fractional seconds before fingerprinting. Two RFC3339 offsets representing the same instant are the same semantic request; a different instant or operation with the same actor/key is 409. Use an HMAC key identifier and a documented dual-key verification/rotation window; do not rehash an old receipt under the new key and silently accept mismatches. Never log HMAC secrets or raw support content. A replay outside the approved retention horizon is NOT guaranteed; require explicit retention/legal-hold approval, minimum anti-reuse tombstone policy and KEY_EXPIRED/409 behavior while the tombstone exists. Do not promise perpetual replay protection after permitted erasure.
- **Clock and DST semantics need a single authority.** Capture a single DB clock value per mutation and use that value for both inclusive 15-minute/30-day bounds and returned asOf; define seconds precision by comparing normalized UTC seconds to an explicitly truncated DB clock, so microseconds cannot make an exactly-15-minute request unpredictably fail. A bare RFC3339 offset uniquely identifies an instant but does not identify an IANA zone, so backend cannot certify that a local civil time was nonexistent during DST. The UI must validate a chosen IANA zone's gap/fold before constructing the offset-aware timestamp, with ambiguous folds explicitly disambiguated. DB due/upcoming list continues to use one statement snapshot; browser clock must not decide persisted due state.
- **Do not overclaim analytics.** Opening a due list is not proof an administrator reviewed a case. Replace v1676 'due items reviewed' KPI with 'due-list views' and, only where a first-party authenticated case-open navigation event is explicitly recorded, 'cases opened from due list'. No inferred SLA compliance or resolution improvements; anonymize with cohorts >=20, suppress actor/thread/subject in telemetry. Zero member-visible disclosure remains the privacy target.
