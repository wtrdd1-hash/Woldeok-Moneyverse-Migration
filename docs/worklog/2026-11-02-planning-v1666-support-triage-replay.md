### Source-backed corrections and scope
- **Create-key replay is not payload proof.** Applied migration `196-user-admin-support-chat.sql` defines `support_threads.create_key uuid UNIQUE`; `support_create_thread(actor,key,subject,body)` (lines 54–64) returns the existing thread for a matching key and actor **without comparing subject or first message body**. Its initial `support_messages.idempotency_key` uses the same key, and the first message may later be purged. Thus a new categorized endpoint must not inherit the legacy “same key means same payload” assumption. This is a source-proven *possibility*, not an observed Production incident.
- **Queue ordering parity.** Existing `admin_support_threads` (migration 196) sorts **open → waiting_user → resolved**, then `last_message_at DESC,id DESC`. v1664's proposed category queue sorted only by recency, silently changing operator priority. Preserve status-rank ordering unless an explicit status filter is applied. Status changes and message writes may move rows across pages; no stable cross-request MVCC snapshot is promised.
- **Category origin is immutable.** v1664's single mutable `category_source` would be overwritten by `admin_reclassified`, erasing whether the initial category was member-selected or a legacy default. Separate immutable initial category provenance from current category and change audit. Development PG17.11 READ ONLY: 3 threads, 6 messages, no category column; `moneyverse_app` direct UPDATE on `account_balances` remains true (P0 #993). Do not infer Production incident or DB role parity.
