### Source evidence, user value, alternatives
- **Verified source:** `frontend/src/app/account/notifications/page.tsx` already has a member-gated notification settings page and a separate existing goal-notification preference; it does not provide an expiry preview. `frontend/src/app/inventory/page.tsx` calls `apiOrNull('/api/v1/shop/holdings')` then converts missing data to `[]`, so it cannot establish verified zero when the upstream fails. `backend/src/shop/shop.controller.ts` guards GET holdings with Session/Authenticated/Consent guards; `shop.repository.ts` reads `public.shop_my_items_v2(actor)` from migration 123. `frontend/src/app/app-api/v1/[...path]/route.ts` explicitly protects selected private families but not every shop/holdings path. These are source findings, not proof of a Production privacy incident.
- **Goal:** let an authenticated, consent-current owner see what a **hypothetical** daily expiry digest would count **now**, before deciding whether to enable F675-205. Existing F675-203 urgency summary and F675-205 worker are unimplemented proposals; this feature must not claim their rollout, send a notification, save a preference, or create an inbox receipt.
- **Alternatives:** (A) reuse the full unbounded holdings payload in the browser: rejected (false-empty, scale, client-clock precision); (B) persist a preview snapshot: rejected (stale data, retention and consent burden); **(C) selected:** a bounded owner-scoped PostgreSQL read aggregate behind a typed Nest GET. If F675-203's aggregate is already implemented at development time, reuse that verified authoritative query rather than create duplicate counting logic. No new table or financial write.

### Member flow, UI and exact response
- **Entry:** `/account/notifications`, below the proposed daily expiry digest preference. CTA **Preview expiry digest** → **Refresh preview** → **Open inventory**. Preview works with digest preference OFF and does **not** opt the user in. Explain: “Current inventory estimate only. Counts can change; scheduled notifications are not guaranteed.” Show the two bands, source timestamp and last verified refresh; no item names, catalog IDs, balances, quantities, raw owner IDs or simulated inbox messages.
- **Bands:** one PostgreSQL `statement_timestamp()` `asOf` in UTC, precision six fractional digits. Distinct catalog kinds in **(asOf, asOf+24 hours]** and **(asOf+24 hours, asOf+72 hours]**, including `quantity>0` and nonnull held-item `expires_at` only. Exclude already expired, `effect_expires_at`, upkeep, suspended-status inference and ledger/financial events. One `user_items` PK (owner,catalog) row counts once per band. Counts are **canonical nonnegative decimal strings**, not JS floating numbers. Boundary examples: expires exactly at asOf → excluded; exactly at +24h → first band; +24h+1µs → second; exactly +72h → second; +72h+1µs → excluded.
- **States:** FLAG_OFF (existing page unchanged), LOADING, VERIFIED_NONZERO, VERIFIED_ZERO, REFRESHING, AUTH_REQUIRED, CONSENT_REQUIRED, RATE_LIMITED, SOURCE_UNAVAILABLE, OFFLINE and SESSION_CHANGED. A 503/timeout/unknown timestamp must never become zero or a “no expiry” success badge. A verified preview is a point-in-time read, **not** a frozen future digest or a guarantee that the 09:00 worker will run. Expired session/account switch clears the panel, not just its spinner.

### API, DB authority, privacy, abuse and performance
- **Nest:** proposed `GET /api/v1/shop/expiry-digest/preview` with SessionGuard + AuthenticatedGuard + ConsentGuard and actor derived solely from the authenticated request. No actor UUID, filter or body accepted; unexpected query parameters → 400; no CSRF write token or idempotency key for GET. `200 {sourceStatus:'VERIFIED',asOfUtcMicros:'YYYY-MM-DDTHH:mm:ss.ffffffZ',count0To24h:'0',count24To72h:'0'}`. 401 unauthenticated, 403 consent, 429 rate limited, 503 DB/schema/clock unknown. Retry is a fresh read, never a replay of a previous success.
- **SQL:** forward-only migration only if required, with numbering coordinated after competing migration **318**; proposed `public.shop_expiry_digest_preview_v1(p_actor uuid)` SECURITY DEFINER, migrator-owned, fixed `search_path=pg_catalog,pg_temp`, schema-qualified tables, explicit PUBLIC EXECUTE revoke and reviewed role-specific EXECUTE. One read-only statement, owner predicate inside SQL, strict microsecond comparator, no dynamic SQL. **P0 security gate:** an actor UUID argument and caller-writable session GUC are not independent DB identity proof. Demonstrate effective app-role negative table grants and two-owner direct EXECUTE spoof-negative tests, or block the new grant/feature until a reviewed identity-bound function boundary exists. Do not grant direct `user_items` SELECT or notification-table rights to make preview work.
- **Resource limits:** proposed 10 requests/member/minute, 2s SQL timeout and p95 <300ms **TEST TARGETS, not measurements**. Use `EXPLAIN (ANALYZE, BUFFERS)` on 10,001 synthetic holdings and review existing owner/expiry indexes; add an index only with measured benefit and no redundant duplicate. PostgreSQL one-statement snapshot and timestamp, no cross-request snapshot claim, no write transaction/locks/receipt. No dependency on unproven `in_app_notifications` DDL (that is F675-205's separate P0 blocker).
- **Privacy/SEO:** HTTP success **and errors** at Nest, Next BFF, app-api and public edge must return `Cache-Control: private, no-store`, `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`; no sitemap or public canonical for private preview. No member UUID, item/expiry detail, raw query, response payload or auth token in logs/analytics. Android app-api parity, no disk cache, cancel/discard stale responses on logout/account switch; 320px, 200% zoom, 44px touch targets, keyboard labels/aria-live, reduced motion, WCAG 2.2 AA, KO/EN meaning parity.
- **Admin/KPI:** aggregate-only preview attempts, verified-zero share, 401/403/429/503, p95 and stale-session response drops; suppress cohorts <20 distinct members. Targets: zero cross-owner disclosure, zero item/WLD/ledger mutations, zero false-empty on upstream failure, zero public-cache responses. No per-user preview dashboard, no external notification and no marketing inference.
