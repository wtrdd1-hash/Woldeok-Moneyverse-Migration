### Verified source and design corrections

1. **Fresh no-op is not idempotent without a receipt.** v1668 says a fresh-key request that leaves assignment unchanged returns verified current state without an event, but its proposed receipts point to a non-null event_id and no durable receipt is specified for no-op. A delayed retry after a later assignment change could perform an unintended mutation, and reuse of that key with changed payload could evade detection. **Correction:** persist a unique immutable receipt for EVERY accepted key, including outcome=UNCHANGED with nullable event_id; no-op does not increase assignment_revision, create a transfer event, or append a false status-change audit. Request digest includes actor, thread, operation version, target, reason, expected revision and normalized body. The first successful no-op response is replayed byte-for-byte in business fields after the actor passes current authorization; the response is explicitly historical and must not masquerade as current assignment. Same key/different payload → 409; concurrent same-key contenders serialize through unique index and row locks. Receipt expiry/erasure requires a minimal keyed tombstone preserving replay exclusion; do not promise infinite retention of personal data.
2. **Role-check TOCTOU across revoke.** Applied migration 007 admin_current_roles reads public.user_roles joined to active public.users without taking a lock; migration 196 admin_support_reply and admin_support_set_status check this predicate before updating the thread. v1668 proposes checking actor and target roles in the assignment transaction, but a concurrent role revoke can race unless grant/revoke and assignment share a documented serialization protocol. **Correction:** DB implementation must coordinate lock ordering with the existing role mutation paths: lock relevant actor/target identity/role rows in deterministic UUID order before support thread → assignment → receipt/event, re-evaluate active roles under lock, and ensure role grant/revoke participates in the same protocol (or use an equivalent reviewed serializable mechanism). If role mutation paths cannot be coordinated, block the rollout; a best-effort second SELECT is not proof of revocation safety. Nest recent admin session/consent/CSRF and SQL active role checks both remain mandatory. A revoked actor may not retrieve a historical receipt via replay; do not reveal target identity.
3. **Deletion/retention and nullable assignee.** Migration 196 support_threads.user_id and support_messages.sender_user_id reference users without ON DELETE CASCADE. Proposed support_thread_assignments.assignee_admin_id also references users without a deletion strategy; erasing a user or revoking a staff account may fail or retain unnecessary staff identifiers. **Correction:** define explicit order and legal retention policy for member thread/messages, assignment current row, event/audit, receipt and staff identity. Never add blanket CASCADE to financial or audit tables. On authorized erasure, preserve only lawful non-reversible dedup tombstones; make current assignee NULL and mark STALE/ERASED only via audited explicit transition. Test FK RESTRICT, inactive/erased admin, member erasure, event/receipt retention and replay after purge. Missing source must be UNKNOWN/503, not a fabricated unassigned case.
4. **Queue proof and stable sort.** v1668 requires a sourceRevision but does not define its producer; an MVCC snapshot within one request cannot be carried across independent HTTP requests by merely encoding a timestamp. Do not claim lossless all-time pagination without a verifiable mutation watermark. Design a scoped durable queue change sequence covering support reply/status, assignment, retention and deletion, or explicitly label pagination LIVE_BEST_EFFORT with refresh and no completeness claim until proven. Keep existing open → waiting_user → resolved ordering, DB microsecond timestamp + UUID, 50+1 bound and authenticated 5-minute cursor. Avoid unreviewed global hot-row counters; benchmark chosen mechanism. A stale/invalid cursor is 409/410, never silent partial success.

### Revised member/admin UX, API, DB, security and operations contract

**Audience/entry:** authorized staff at /admin/support; member /support remains unchanged and does not show assignee. Staff sees Claim/Release/Transfer/Take over, assignment revision, explicit historical replay badge, stale target warning and Refresh after conflict. No automatic claim/expiry, no SLA/monetary privilege. Keyboard and screen reader announce 409 refresh, 403 revoked, 503 unverifiable; 320px/390px/200% zoom and 44px target checks. Android app-api, if privileged staff access exists, validates response and session generation, never caches staff data. Private no-store/noindex/nofollow/noreferrer/nosniff at actual edge including errors; no staff/member identifiers in analytics.

**Write API:** retain v1668 POST/PUT/DELETE /api/v1/admin/support/threads/:id/assignment and expectedAssignmentRevision decimal string + UUID idempotencyKey; strict schema rejects unknown fields. On first request, current actor auth + role lock → thread lock → assignment row → canonical request digest lookup/insert → CAS → event/audit only if state changes → immutable receipt (including UNCHANGED) in ONE transaction. Event_id is nullable only for UNCHANGED, CHECK enforces (outcome=UNCHANGED AND event_id IS NULL) OR (outcome=CHANGED AND event_id IS NOT NULL); receipt unique(actor_admin_id,idempotency_key), key_version, HMAC, stored response, created_at, retention_state. No-op with stale expected revision returns 409 rather than laundering a stale request into success. Same-key same-payload replay returns the stored historical outcome even after later changes but only while actor currently authorized; different payload 409. Explicit 400/401/403/404/409/410/429/503; 404 non-disclosing. Never rely on a browser button disable for deduplication.

Use actor/target role checks in PostgreSQL; lock protocol and immutable audit must be reviewed against existing admin_append_audit_event global chain lock. DB indexes on receipt actor+key, assignment assignee+updated_at and queue ordering require EXPLAIN with >=10,001 synthetic threads. Protect key rotation, FK deletes and old receipts.
